# KF1 수정계획서 — 델타 스펙 수정 루프 (브라운필드를 1급으로)

## 0. 요약

기존 코드 수정 작업에 게이트가 지나갈 경로를 만든다: `/spec delta "<한 줄 요구>"` →
`SPEC.delta.md` 1장(ADDED/MODIFIED/REMOVED) → 구현 → Stop에서 델타 범위 대조(D4) 검사 →
통과 시 기계 병합으로 `SPEC.md`에 누적. 검사기 `framework/spec-delta.mjs`(D1~D5, `verify`·`merge`)와
템플릿 `framework/delta-template.md`를 새로 만들고, `spec-gate.mjs`·`commands/spec.md`를 확장한다.
약속하지 않는 것: 수정 대상 자동 탐지, Edit 차단, 병합의 의미 통합. 전부 정적·결정론 — LLM 0패스다.

## 1. Pain Point와 근거

- **조사 F8** (medium·계쟁): 브라운필드/수정이 기존 SDD 툴의 최대 미충족 갭 — 델타 목적 설계는
  OpenSpec뿐이고 그마저 «지켰는지 확인하는 검증기»가 없다. F8c는 반쪽 수정(건드려야 할 대상 일부만
  고침)의 실패를 보고한다.
- **specgate 자신의 공백**: SPEC은 «새 기능을 시작할 때»만 요구되고(`framework/README.md:35` —
  r37 사용자 결정: 게이트 대상 `Write`만), Edit은 안 막는다. 즉 1인 개발자의 일상인 **수정에는
  아무 경로가 없다** — 게이트도, 문서 단위도, 완료 대조도.
- **리포 실측이 예고하는 지점**: `FIELD-GUIDE.md` 예언 P4(빈 파일+Edit 우회)·README 한계 1이
  이미 «수정·우회 경로»를 알려진 구멍으로 적어 놨다. 다만 실사용(jp-trip)은 아직 개시 전이라
  (G3 대기) 이 갭의 발생 빈도 실측값은 없다 — 이 계획은 조사 근거와 구조적 공백에서 출발한다.
- 한 줄 수정에 spec-kit류의 다파일 스펙을 요구하면 F1(지배 비용 = 생성 문서의 인간 리뷰)이
  진입 장벽으로 돌아온다. 그래서 수정의 문서 단위는 델타 1장(~10줄)이어야 한다.

## 2. 목표 / 비목표

**목표**

1. 수정 작업의 문서 단위 = 델타 1장. 커맨드 1회로 진입하고, 읽을 것이 ~10줄을 넘지 않는다.
2. MODIFIED 항목의 `` `파일:심볼` `` 필수 필드로 **«구현 전 열거»라는 행위**를 강제한다(D2).
3. 완료 전 대조를 델타 범위로 좁혀 요구한다(D4 = C4의 델타 범위판) — 본 SPEC 전체 재대조를
   요구하지 않는다(FIELD-GUIDE P2 «제일 먼저 끄고 싶어질 것»의 회피).
4. 통과한 델타는 SPEC.md에 기계 병합돼 스펙이 존속한다 — 원 요청의 «Spec-First → Spec-Anchored 이동».
5. 콜드스타트(스펙 0 레거시)에 전체 백필을 요구하지 않는다 — 첫 델타가 곧 첫 SPEC이고,
   SPEC.md는 «도구를 거친 변경의 누적»으로 자란다.

**비목표** (목표와 같은 무게)

- 수정이 건드린 기존 함수를 **자동으로 전부 찾아주지 않는다** — F8c가 반증하는 바로 그 지점이다.
- Edit을 막지 않는다. 순수 Edit 수정은 델타 없이도 지나간다(r37 결정의 연장 — §9).
- 병합은 텍스트 재배치다. 문장 간 모순 탐지·의미 통합은 하지 않는다(판단 영역 — 개발 규칙 5).
- «새 기능인가 수정인가»를 기계가 구별하지 않는다.
- SG 번호 부여(KF4 몫)·볼륨 관리(KF5 몫)·드리프트 감시(KF3 몫)를 하지 않는다.

## 3. 현행 기반과의 관계

| 기존 파일 | 이 계획에서 | 이유 |
|---|---|---|
| `spec-verify.mjs` | **파서 유틸 export 추가**(`cellsOf`·`tables`·`stripFences`·`SENT_ID`·`expandRanges`·`mentions`·`POS`) — 동작 무변경 | spec-delta가 표 파싱·ID 계수를 재구현하지 않게(규칙 2) |
| `hooks/spec-gate.mjs` | `decide()`에 델타 분기 추가, selftest 확장 | 판정 시점 배선은 게이트의 단일 책임 |
| `hooks/hooks.json` | **무변경** — matcher `Write`·Stop 그대로 | 델타 분기는 게이트 내부 로직이다 |
| `commands/spec.md` | `delta` 분기 추가(커맨드 수 불변 — 메인 §5-1) | 진입로는 기존 `/spec` 하나로 유지 |
| `spec-template.md` | 무변경. `delta-template.md`가 자매 문서로 ID 규약(S/I/U)을 공유 | |
| `README.md` | 설치물 표에 델타 1행 + 한계 1줄 (라운드 3 말미, 짧게) | 문서는 코드가 돈 뒤(규칙 1) |

새로 만드는 것은 `spec-delta.mjs`와 `delta-template.md` 둘이다. spec-verify에 욱여넣지 않는
이유: 검사 대상 문서의 구조가 다르다(SPEC 4절 vs 델타 3절+대조). «먼저 있는 걸 쓴다»는 파서
공유로 지키고, spec-kit 재구현 금지는 **아무도 안 한 자리**를 확인하고 지킨다 — F8이 명시하듯
델타 포맷의 «검증기»는 OpenSpec에도 없다. 포맷(3절)은 OpenSpec 차용, 검증기가 신규분이다.

## 4. 설계

### 4-1. 동작 흐름 (사이클 1회)

```
/spec delta "쿠폰 중복 적용을 막아줘"
   → SPEC.delta.md 생성 (ADDED/MODIFIED/REMOVED, MODIFIED엔 파일:심볼 — 구현 전)
   → [pre 게이트] 소스 Write 시: 델타 활성이면 D1·D2 검사(위반 시 exit 2)
   → 구현 (Write/Edit/Bash)
   → 델타의 «## 대조» 표를 채운다 (ADDED·MODIFIED 전건, 파일:줄)
   → [Stop 게이트] D1~D5 전건 검사 → 위반 exit 2 / 통과 시 그 자리에서 기계 병합
   → SPEC.md 갱신(또는 콜드스타트 생성) + SPEC.delta.md 삭제 + 로그 1줄
```

### 4-2. delta-template.md 실물 초안 (전문)

```markdown
# DELTA — <한 줄 요구를 그대로 적는다>

<!-- framework/delta-template.md 의 사본. 한 번에 1장 — 병합되면 삭제된다(이력은 git).
     ID는 본 SPEC.md 의 S/I/U 최대 번호에 이어 쓴다. 본 SPEC이 없으면(콜드스타트) S1부터.
     MODIFIED 의 대상은 백틱으로 감싼 `경로:심볼` — 구현을 시작하기 전에 채운다. -->

## ADDED
- S9. <조건>일 때 <주체>는 <관측 가능한 동작>을 한다. (근거: 사용자, YYYY-MM-DD)
- I4. <문장> `[추론]`

## MODIFIED
- S3. <바뀐 뒤의 문장 전문> — 대상 `src/cart.ts:applyDiscount` (근거: 사용자, YYYY-MM-DD)

## REMOVED
- S5. 기각 사유: <왜 이 요구가 빠지는가>

## 대조
<!-- 구현이 끝난 뒤, 완료 선언 전에 채운다. ADDED(S·I)·MODIFIED 전건 — 파일:줄 지목. U행은 제외. -->
| 문장 | 코드 위치 |
| --- | --- |
| S9 | |
```

### 4-3. 문서 문법과 검사 D1~D5 (심각도는 메인 §5-2 배정 그대로 — 번호 부여는 KF4)

| 검사 | 정의 | 심각도 |
|---|---|---|
| D1 | `## ADDED` `## MODIFIED` `## REMOVED` 3절 헤딩이 전부 있는가. 빈 절 허용, 절 자체는 필수. 코드펜스 안 헤딩은 무효(`stripFences` 재사용) | Error |
| D2 | MODIFIED의 각 항목(`- `로 시작하는 불릿 블록)에 백틱 대상이 1개 이상 있는가 | Error |
| D3 | ID가 S/I/U 접두어인가 · ADDED ID가 본 SPEC 기정의와 충돌하지 않는가 · MODIFIED ID가 본 SPEC에 실존하는가(웜일 때) · ID 자체가 없는 항목 | Warning |
| D4 | **ADDED(S·I)·MODIFIED**의 ID 전건이 정의 줄 **이후**에서 재등장하는가(C4 로직 재사용 — ID별 절단). **ADDED `U*`는 제외한다** — 미확정 항목은 구현 대조가 성립하지 않고, 병합 시 §3.2 재확인 목록 몫이다(§4-5). 위치 표기 없는 지목은 C4 준용 경고 | Error |
| D5 | REMOVED가 지목한 ID가 본 SPEC에 실존하는가(문장 정의 + §2.3 U행). 콜드스타트는 판정 불가 — Warning으로 격하 | Error |

**MODIFIED 대상 필드 문법**: `` `<경로>:<심볼>` `` — 경로는 프로젝트 루트 기준 상대·구분자 `/`,
심볼은 식별자(점 경로 허용: `Cart.apply`) 또는 `*`(파일 전체 — 설정 파일 등 심볼 없는 대상).
복수 대상은 백틱 스팬을 여러 개 쓴다. D2 판정 정규식(초안):

```js
const TARGET = /`[\w./-]+\.\w{1,5}:(?:[A-Za-z_$][\w$.]*|\*)`/;
```

**왜 pre는 파일:심볼이고 대조는 파일:줄인가**: 구현 전에는 줄 번호가 없다(있어도 구현이 옮긴다).
심볼이 구현 전에 존재하는 유일한 안정 핸들이고, 줄 지목은 구현 후의 D4 몫이다.

**ID 규약**: 델타의 새 문장은 본 SPEC의 S/I/U 최대 번호에 이어 쓴다(S8까지 있으면 S9부터).
연속성(빈 번호 없음)은 강제하지 않고 **충돌만** D3 경고로 잡는다 — 엄격 연번은 병합 이력이
쌓이면 유지 불가능하고, 검사 가치는 «본 SPEC과 같은 ID 공간»이라는 사실에 있다.
`선택 대기`였던 U행의 확정은 델타로 표현한다: `REMOVED U3` + `ADDED S12 (근거: 사용자, 날짜)`.

### 4-4. spec-delta.mjs CLI

```
node framework/spec-delta.mjs verify <SPEC.delta.md> [--base <SPEC.md>] [--json]
node framework/spec-delta.mjs merge  <SPEC.delta.md> [--base <SPEC.md>] [--dry-run]
node framework/spec-delta.mjs --selftest
```

- `--base` 생략 시 델타와 같은 디렉터리의 `SPEC.md`, 없으면 콜드스타트로 판정.
- exit: `verify` 0 위반없음 / 1 위반있음 / 2 파일없음·사용법 오류. `merge` 0 병합완료 /
  1 검사 위반으로 병합 거부(파일 무변경) / 2 파일없음·병합실패. 1과 2를 가른다(spec-verify 선례).
- export: `inspectDelta(deltaText, baseText|null, label)` · `mergeDelta(deltaText, baseText|null)`
  (순수 함수 — 파일 IO는 CLI와 게이트가 각자 한다). spec-gate가 이 둘을 import한다.

`verify` 사람용 출력(예):

```
spec-delta verify SPEC.delta.md (base: SPEC.md)
  D1 3절 구조      : ADDED 2 · MODIFIED 1 · REMOVED 1
  D2 파일:심볼     : 1/1
  D3 ID 규약       : S9, I4, S3, U3 — 충돌 0
  D4 델타 대조     : 3/3
  D5 REMOVED 실존  : 1/1
  → 위반 0 · 경고 0
```

`--json`(기계용, KF4의 소비 대상 — 필드는 spec-verify의 `inspect()` 결과와 같은 결):

```json
{ "delta": "SPEC.delta.md", "base": "SPEC.md", "coldstart": false,
  "counts": { "added": 2, "modified": 1, "removed": 1, "targets": 1 },
  "d4": { "total": 3, "hit": 3, "miss": [], "vague": ["I4"] },
  "violations": [], "warnings": [{ "check": "D4", "msg": "지목은 있으나 «파일:줄»이 없는 문장 1건: I4" }] }
```

### 4-5. 병합 규칙 (기계적 — ID 기준 append/replace/삭제. 규칙 자체가 «설계 판단» — §10 #1)

| 델타 항목 | 병합 동작 |
|---|---|
| ADDED `S*` | 본 SPEC의 같은 접두어 마지막 정의 줄 뒤에 append |
| ADDED `I*` | 위와 같음(I 공간) |
| ADDED `U*` | 미확정표(6열, `침묵 지점` 헤더로 특정 — spec-verify C3 로직 재사용) 마지막 행 뒤에 행 append **+ §3.2 재확인 목록에도 1줄 append** — 이게 없으면 병합 직후 SPEC이 C5 위반 상태가 되고, 그 차단은 다음 비델타 세션의 Stop에서 터진다 |
| MODIFIED `<ID>` | 본 SPEC에서 그 ID의 정의 줄을 델타 문장으로 교체(ID·리스트 마커 유지). 옛 문장은 git 이력 |
| REMOVED `<ID>` | 정의 줄(또는 U행)·§3.1 대조 행을 삭제 — 이력은 git. **KF5 이후에도 아카이브 이동으로 자동 전환하지 않는다** — 아카이브 진입 조건(구현·검증 완료·파일:줄 지목)을 기각 문장은 원리적으로 못 채운다. «기각 보존» 구획 신설 여부는 KF5와 합동 확정(메인 §10-4) |
| 대조 표 행 | 본 SPEC의 대조 표에 append, MODIFIED ID의 기존 행은 교체(낡은 위치 갱신). **대조 표의 특정(결정론)**: 미확정표(«침묵 지점» 헤더)를 제외하고 첫 열이 문장 ID인 **마지막 표** — 없으면 파일 끝에 2열 표(`\| 문장 \| 코드 위치 \|`)를 신설한다(콜드스타트 골격과 동일 헤더). 재확인 목록의 특정도 같은 방식 — 미확정표 이후에서 `선택 대기` ID가 재등장하는 마지막 리스트 블록, 없으면 파일 끝에 신설 |

- 앵커 폴백 사슬(결정론 유지): 같은 접두어 마지막 정의 줄 → 아무 접두어의 마지막 정의 줄 →
  파일 끝. 본 SPEC은 §0 골격 확정에 따라 헤딩이 다를 수 있으므로 헤딩 텍스트를 앵커로 쓰지
  않는다(spec-verify의 A층 원칙 준용).
- MODIFIED 대상 ID가 본 SPEC에 없으면(콜드스타트 포함) **append로 강등 + 경고 1줄** — 병합은
  전 입력에서 결정론적으로 완료돼야 한다.
- **병합 완료 조건**: 병합 직후 병합 결과 텍스트에 `inspect()`를 재실행해 **위반 0**을 확인한다.
  위반이 나오면 파일을 쓰지 않고 병합 실패로 처리한다(§4-6) — «통과한 델타의 병합이 본 SPEC을
  게이트 위반 상태로 만드는» 경로를 원천 차단한다. M8·G17이 이 조건을 고정한다.
- **콜드스타트 생성**: 본 SPEC이 없으면 병합 결과로 SPEC.md를 새로 만든다 — §0(스펙 소스: 델타
  누적 · 골격 상태 `선택 대기`), §1(S 문장), §2.2(I 문장), §2.3(U행 — 6열 헤더 포함), §3.1(대조 행).
  **10범주 점검표는 만들지 않는다** — 상태(Clear/Partial/Missing)는 판단이고 기계가 채우면 기록
  없는 확정이다(규칙 5·6). 대가: 이 «델타 급» SPEC은 다음 **새 기능** Write에서 C2에 막혀 승급
  (점검표 작성)을 요구받는다. 의도된 동작이지만 마찰로 관측될 수 있다(§9, §10 #4).

콜드스타트 병합 산출물 골격(발췌):


### 4-6. spec-gate.mjs 분기 (decide() 확장 — 결정표)

**원칙: 델타가 활성이면 델타가 활성 문서다.** 델타 사이클 중 본 SPEC의 C1~C3을 병행 검사하지
않는다 — 콜드스타트 누적 SPEC(점검표 없음)이 있으면 수정 루프가 C2에 영원히 막히기 때문이다(§10 #3).

| 모드 | SPEC.delta.md | SPEC.md | 판정 |
|---|---|---|---|
| pre (SRC Write) | 있음 | 무관 | `inspectDelta` → **D1·D2 위반 시 exit 2**, D3은 경고(통과). D4는 stop 몫(r37의 시점 분리 원칙 준용), D5도 병합 전제조건이므로 stop에서 본다 |
| pre (SRC Write) | 없음 | 있음 | 기존 그대로 — C1~C3 |
| pre (SRC Write) | 없음 | 없음 | 기존 차단 + **메시지에 델타 경로 추가**: «…새 기능이면 SPEC.md를, 기존 코드 수정이면 `/spec delta`로 SPEC.delta.md를 써라» |
| pre (비SRC) | 무관 | 무관 | 통과(기존 SRC 필터 그대로 — `.md`는 대상이 아니므로 델타 자신을 쓰는 Write는 안 막힌다) |
| stop | 있음 | 무관 | D1~D5 전건. **위반 시**: 재진입(`stop_hook_active`)이면 통과(가드), 아니면 exit 2. **통과 시**: 재진입 여부와 무관하게 `mergeDelta` → 병합 결과 `inspect()` 위반 0 확인 → SPEC.md 쓰기 → 델타 삭제 → 로그 → exit 0 |
| stop | 없음 | 있음 | 기존 그대로 — C1~C5 (+재진입 가드) |
| stop | 없음 | 없음 | 통과(기존) |

- **재진입 가드는 차단에만 적용된다.** 현행처럼 `stop_hook_active`에서 즉시 return하면 «위반으로
  1회 차단 → 대조 채움 → 재정지»라는 정상 흐름에서 병합이 영원히 안 일어난다. 병합은 차단이
  아니므로 재진입에서도 수행한다 — 반복 차단형 무한 루프는 그대로 막힌다. 단 병합 실패 경로는
  별도 처리다(아래).
- **Stop 훅이 병합 주체다**(기본값 — 대안은 §10 #2). 근거: 원 요청의 중단 예산이 «커맨드 1회»고,
  병합을 에이전트의 별도 행위로 두면 차단·재실행 1회가 추가된다. 병합은 ID 기준 텍스트 재배치라
  결정론이고(같은 입력 → 같은 SPEC.md), 델타 내용 자체는 이미 확정 절차를 거친 문장이므로 병합이
  새로 정하는 것은 없다 — 규칙 6 위반이 아니다. 이력은 git이 진다.
- **병합 실패**(예외·위반 0 확인 실패)는 초회 exit 2 + «병합 실패: <이유> — SPEC.delta.md는
  남겨뒀다»(조용한 유실 금지). **재진입에서는 exit 0 + 같은 내용의 stderr 경고로 격하한다** —
  쓰기 권한 오류·병합 버그처럼 에이전트 행동으로 해소되지 않는 결정론적 실패가 Stop마다 exit 2를
  반복하면, 재진입 가드가 막으려던 무한 루프가 병합 경로로 되살아나기 때문이다. 잔존 델타의
  수동 `merge`가 복구 경로다(G22·G23이 두 분기를 고정한다).
- 병합 성공 로그(기존 `.specgate-log.jsonl` 선례 — 실패해도 병합을 막지 않는다):

```json
{"t":"2026-08-19T09:12:00.000Z","mode":"merge","added":2,"modified":1,"removed":1,"coldstart":false}
```

### 4-7. /spec 커맨드 delta 분기 (commands/spec.md에 추가할 내용 골자)

```
**$ARGUMENTS 가 `delta` 로 시작하면** — 수정 루프다.
1. SPEC.delta.md 가 이미 있으면 **새로 만들지 않는다** — verify를 돌려 상태를 보고하고,
   같은 작업 단위면 기존 델타에 항목을 추가하고, 아니면 기존 사이클 종결(대조 채우고 완료)을
   먼저 제안한다. 방치 델타의 폐기는 사용자 몫이다 — 임의로 지우지 마라.
2. 없으면 delta-template.md 사본으로 만들고, 한 줄 요구를 ADDED/MODIFIED/REMOVED로 쪼갠다.
   MODIFIED 대상 `파일:심볼`은 구현을 시작하기 **전에** 채운다. ID는 본 SPEC 최대 번호에 잇는다.
3. node "${CLAUDE_PLUGIN_ROOT}/spec-delta.mjs" verify SPEC.delta.md 로 확인 후 구현에 들어간다.
```

**델타 1장 활성 원칙의 강제점**: 도구가 아니라 이 문안 + Stop 자동 병합이다(정상 흐름에서는
사이클 끝마다 델타가 소멸하므로 둘째 델타 상황 자체가 드물다). 파일 생성은 에이전트 행위라
결정론 도구로 막을 수 없고, 막으려면 pre 게이트에 «델타 2장» 검사를 넣어야 하는데 파일명이
`SPEC.delta.md` 하나로 고정이라 물리적으로 2장이 성립하지 않는다 — 남는 위험은 «방치 델타 위에
다른 작업을 얹는 것»이고, 이는 1번 문안과 Stop의 D4가 잡는다(§10 #6).

## 8. 의존성과 착수 조건

- **착수 전제(전 KF 공통)**: r38 관문 A-3(플러그인 설치 형태에서 차단 확인) 통과 + G3(실사용
  실수요) 충족 후 실사용 투입 개시. P1 안에서 KF1을 먼저 켤지는 계획이 정하지 않는다 —
  jp-trip 실사용에서 «수정 경로 무게이트»가 실제로 아쉬웠는지가 정한다(메인 §4).
- **KF1 → KF3②**: drift의 `modified` 범주(«MODIFIED 선언됐는데 앵커 미갱신»)는 델타가 있어야
  성립한다. KF3①(실증기)과는 무의존 — 병행 가능.
- **KF1 → KF2(약한 방향)**: KF2의 10-shot 예시 은행이 «과거 델타»를 소재로 쓴다. KF1이 먼저면
  소재가 쌓인다는 것뿐, 선후 강제는 아니다.
- **KF4**: D1~D5의 SG1011~1015 번호는 예약만 돼 있다(메인 §5-2). KF1 출력은 D 라벨로 하고
  번호 부여·mute·`.specgate.json`은 KF4 몫이다(룰 목록 안정 뒤 — 재번호 비용).
- **KF5**: REMOVED는 KF5 이후에도 **기본 삭제를 유지한다** — 아카이브는 «구현·검증 완료» 보존이라
  기각 문장은 진입 조건(파일:줄 지목 등) 미달이다(KF5 §4-2). «기각 보존» 구획 신설 여부와
  아카이브 되살리기(KF5 §10-5)는 KF1 병합 규칙 확정 라운드에서 KF5와 **합동 확정**한다(메인 §10-4).

## 9. 명시적 한계 (반증 지점 병기)

1. **F8은 medium + 계쟁**이다. 브라운필드 갭의 크기 자체가 확정 사실이 아니다.
2. **델타↔본 SPEC 병합 규칙은 «설계 판단»이다**(원 요청 원문). ID 기준 append/replace/삭제는
   외부 선례 없이 여기서 정한 규칙이고, 실사용에서 틀린 병합이 관측되면 규칙이 바뀐다(§10 #1·#2).
3. **«수정이 건드린 기존 함수를 자동으로 전부 찾아준다»는 약속은 하지 않는다** — F8c가 반증하는
   바로 그 지점이다. 에이전트가 열거 단계에서 `listTags`를 놓치면 게이트도 모른다(원 요청 원문).
4. **필수 필드(D2)가 강제하는 것은 «구현 전 열거»라는 행위이지 열거의 완전성이 아니다**(원 요청 원문).
5. **Edit은 여전히 게이트 밖이다.** 델타 루프는 수정에 «경로»를 주는 것이지 수정을 «강제»하지
   못한다 — 순수 Edit 수정은 델타 없이 통과한다(r37 결정 유지 · README 선택 대기 #2의 번복
   조건 «빈 파일+Edit 우회 실측 시»가 이 한계의 출구다).
6. **델타 분기는 본 SPEC 요구를 약화시키는 통로가 된다.** 새 기능을 «수정»으로 위장해 델타
   1장으로 pre를 통과할 수 있다 — 게이트는 새 기능/수정을 구별하지 못한다. 기존 게이트 철학
   그대로 «작정한 우회»가 아니라 «그냥 시작해버리는 것»만 막는다(README 한계 1 준용).
   실사용에서 이 위장의 발생 여부가 관측 항목이다(FIELD-GUIDE 사건 분류 «미차단»).
7. **D4는 C4와 같은 한계를 상속한다** — 재는 것은 «ID를 다시 적었는가»다. 대조 표의 빈 셀·
   «구현 안 함»도 통과하고, 위치 없는 지목은 경고로만 나온다(README·r36 §9-2에 명문).
8. **콜드스타트 누적 SPEC은 «델타 급»이다** — 10범주 점검표가 없어 §2의 침묵 포착 절차를 거치지
   않았고, 다음 새 기능 Write에서 C2 차단으로 승급을 요구받는다. 의도된 동작이지만 오차단성
   마찰로 관측될 수 있다(§10 #4).
9. **효과는 미실측이다.** 차단이 품질을 올린다는 통제 비교는 조사 전체에 없고(조사 Q1),
   KF1은 «양쪽 실패 증거로부터 추론한 설계»지 검증된 처방이 아니다(원 요청 말미).
