# KF3 수정계획서 — 지목 실증기 + 앵커 드리프트 감시

## 0. 요약

`framework/spec-anchor.mjs`를 새로 만든다 — `record`가 C4 지목(파일:줄)의 실존·줄 범위를 확인하고
지목 시점 스팬 해시를 `SPEC.anchors.json`에 기록하며(①, P1), `drift`가 그 앵커 기준으로 missing /
stale / modified 3범주를 exit code와 함께 보고한다(②, P2). 전부 정적·결정론이고(LLM 0), 어떤 훅에도
안 건다. 약속하지 않는 것: **의미 일치** 검증 — 조사 Q2를 푸는 것이 아니라 결정론이 성립하는
범위(실존·해시)로 문제를 깎은 것이다.

## 1. Pain Point와 근거

- **조사 F3** — 에이전트는 검증 태스크를 빈손으로 «완료» 처리한다. 현행 C4·C5의 알려진 한계도 같은
  결이다: 재는 것이 «ID를 다시 적었는가»라 **빈 셀도 «구현 안 함»도 통과한다**(r36 §9-2 — CLAUDE.md·
  README에 명문). `| S3 | src/cart.ts:210 |`이라 적기만 하면 그 파일이 없어도 게이트는 통과다. 여기가
  «가짜 안심의 최저가 층»이고, 가장 값싼 결정론 한 겹으로 제거할 수 있다.
- **조사 F8a** — 스펙은 코딩이 끝나면 죽는다. specgate는 완료 시점(C4·C5)까지만 강제하고 그 이후가
  없다 — 6개월 뒤 돌아온 프로젝트에서 어느 문장이 아직 참인지 알 방법이 전무하다.
- **조사 Q2** — 임의 코드와 산문 스펙의 의미 일치를 결정론적으로 검증한 선례는 조사 전체에 없다.
  그래서 가장 중요한 설계 결정은 **포기한 것**이다(원 요청 KF3 원문): 의미 비교를 포기하고 앵커 해시
  비교로 축소한다. 3범주 어휘(missing/stale/modified)는 조사 F6에서 차용한다.
- **리포 실측** — «파일:줄 없는 지목» 경고 축이 이미 있다(`spec-verify.mjs:151-155`, SKILL.md:77 근거).
  실증기는 그 경고가 가리키는 지점(위치 표기의 실재)을 검사로 승격하며, 파싱은 기존 것을 쓴다(§3).

## 2. 목표 / 비목표

**목표**

1. `record` — C4 지목에서 파일:줄 표기를 뽑아 ⓐ 파일 실존(A1) ⓑ 줄 범위 유효(A2)를 확인하고,
   통과한 스팬의 정규화 해시를 `SPEC.anchors.json`으로 기록한다. 유령 지목은 exit 1로 드러난다.
2. `drift` — 앵커 기준으로 missing(파일 소멸) / stale(해시 변경) / modified(KF1 델타의 MODIFIED
   선언이 있는데 앵커 미갱신)를 보고하고 exit 1을 낸다.
3. 위치 표기가 없어 앵커 못 하는 지목은 A3 경고 + `unanchored` 목록으로 **드리프트 감시 밖임을
   기계가 읽을 수 있게** 남긴다. 라운드마다 `--selftest`(실프로세스, `spec-gate.mjs` 선례)를 함께 낸다.

**비목표 (약속하지 않는 것)**

- **의미 일치 검증이 아니다.** 앵커가 안 바뀌었어도 문장이 거짓이 됐을 수 있다(§9-1·2).
  «게이트를 형식에서 내용으로» 류의 서술은 이후 문서 전부에서 금지다 — 과대다.
- 수정이 건드릴 파일의 자동 탐지가 아니다(KF1도 약속하지 않는 것 — 조사 F8c).
- 게이트 배선도(§4-7), 심볼 수준 추적(리네임·AST — 줄 기반 스팬만, §10 #4)도 아니다.
- SG 번호 부여·CLI 통합이 아니다 — A1~A3·3범주에 SG1021~1026을 붙이는 것은 KF4 몫이다.

## 3. 현행 기반과의 관계

| 기존 것 | 어떻게 쓴다 |
|---|---|
| `spec-verify.mjs` `inspect()` | **C4 지목 파싱을 재사용한다 — 새 파서를 만들지 않는다.** 문장 ID 정의·정의-이후 절단·`POS` 정규식이 이미 있다. `c4.positions` 한 필드를 더하고 spec-anchor는 그 구조화 결과만 소비한다(§4-2). 순수 텍스트 연산이라 fs 접근이 없고, 훅이 매 Write마다 부르는 경로의 비용·실패 모드를 바꾸지 않는다 |
| `spec-gate.mjs` selftest 패턴 | `mkdtempSync` 임시 프로젝트 + `execFileSync` 실프로세스 + exit 대조를 그대로 따른다. 새 픽스처 디렉터리를 만들지 않는다(개발 규칙 4) |
| `judge.mjs` `frozen` 정규화 계열 | 해시 규약이 같은 계열 — **개행 정규화 후 해시**(CLAUDE.md: `Get-FileHash`는 바이트, `frozen`은 개행 정규화 후). 코드 복사는 안 한다(exp*는 동결, 정규화는 1줄) |
| `node:crypto` `createHash` | Node 내장만. 새 의존성 0(개발 규칙 2) |
| `framework/smoke/i1-cart-r1` | 읽기 전용 실물 검증 재료 — 스크래치 사본에서 record 1회, 원본 무접촉(절대 규칙 6) |

**새 파일이 «먼저 있는 걸 쓴다»에 어긋나지 않는 이유**: 이 검사의 시점(완료 후·재방문)과 입력(SPEC +
파일시스템)은 기존 어떤 도구와도 다르고, `spec-verify`는 SPEC 텍스트 단독 검사라는 성격을 유지해야
한다 — `inspect()`가 지목 파일을 열면 pre 훅의 매 Write에 파일 I/O와 새 실패 모드가 들어간다. 그래서
파일시스템을 만지는 부분만 분리하고 텍스트 파싱은 전부 `spec-verify`에 남긴다.

## 4. 설계

### 4-1. 동작 흐름

```
record(구현 완료·§3 대조표 작성 후): inspect(SPEC) → c4.positions → 스팬별 A1·A2
    → 전건 통과 시 스팬 해시를 SPEC.anchors.json에 기록(exit 0) / 위반 시 미기록(exit 1)
drift (재방문·수정 전): 앵커별 현재 파일 대조 → missing/stale/modified 보고(있으면 exit 1)
    → «앵커 그대로»와 «갈라진» 문장이 나뉜다 — 갈라진 쪽만 다시 읽는다
재기록(수정 후): record 재실행(§4-8)
```

### 4-2. 지목 파싱 — `inspect()` 확장 `c4.positions`

`spec-verify.mjs`에 더한다. **판정 축(위반·경고)은 한 건도 바꾸지 않는다** — 기존 `vague`/`located`
계산은 그대로 두고 `positions`는 별도 산출이다(selftest 기대값 6장 무변경이 회귀 기준, §6).

- 위치 정규식: 기존 `POS`의 첫 대안을 캡처판 상수로 승격해 둘이 한 소스를 공유한다 —
  `POS_FILE = /([\w./\\-]+\.\w{1,5}):(\d+)(?:\s*[-–—]\s*(\d+))?/g`.
- 귀속 규칙(결정론): 각 문장 ID에 대해 **정의 줄 이후**의 줄 중, 그 줄이 해당 ID를 언급하고
  (`mentions()` — 범위 표기 `S1~S3` 전개 포함) `POS_FILE` 매치를 가지면 그 줄의 매치 전부를 그 ID의
  지목 위치로 귀속한다. 정의 줄 자체는 제외 — §1 문장의 `(근거: CONTRACT.md:12)` 같은 **근거 위치**가
  구현 위치로 오인되는 것을 막는다. 파일 없는 형태(`` `:12` ``·`:12-34` 단독)는 앵커 불가로 제외.
- 결과: `c4.positions = { S1: [{file:'src/cart.ts', start:12, end:34, specLine:87}], … }` — 끝줄 생략
  시 `end = start`, `specLine`은 지목이 나온 SPEC 줄(위반 메시지용), 중복 스팬 제거.

### 4-3. `SPEC.anchors.json` 실물 포맷

프로젝트 루트, SPEC.md 옆. **커밋 대상이다**(메인 §5-1 — 6개월 뒤 드리프트 감시의 성립 조건).

```json
{ "version": 1, "spec": "SPEC.md", "hashAlgo": "sha256/lf",
  "anchors": {
    "S1": [ { "file": "src/cart/add.ts", "startLine": 12, "endLine": 34,
              "hash": "9f6c0f22…(sha256 hex 64자리 전체)", "recordedAt": "2026-08-19T02:41:07Z" } ]
  },
  "unanchored": ["S9"] }
```

- 문장 ID당 **스팬 배열** — 한 문장이 여러 파일·범위에 걸쳐 구현되는 것이 실물이다(§10 #3).
- `file`은 프로젝트 루트(SPEC.md의 디렉터리) 기준 상대경로, 구분자 `/` 정규화(OS 간 안정).
- `unanchored` = 지목은 있으나(C4 hit) 파일:줄이 없어 앵커 못 한 ID 전건 — **드리프트 감시 밖이라는
  사실을 파일 자신이 기계 가독으로 드러낸다**(§9-3의 한계를 산출물에 병기하는 장치).
- 기록은 매번 전체 재작성(부분 갱신 없음), `anchors` 키 정렬 — `recordedAt`을 제외하면 같은 입력에
  같은 바이트가 나온다(`recordedAt`은 판정에 안 쓰는 메타데이터 — §10 #5).

### 4-4. 해시 규약

스팬 = 파일을 utf8로 읽어 `\r\n`·`\r`을 `\n`으로 정규화한 뒤 `startLine`~`endLine` 줄을 `\n`으로 이은
문자열(끝 개행 없음). 해시 = sha256 hex 전체. **개행 정규화 후 해시**는 리포 `judge.mjs` `frozen`과
같은 정규화 계열이고 이유도 같다 — Windows/Unix 개행 차이(autocrlf 변환)만으로 stale이 나는 **위양성을
원천 차단**한다. 바이트 해시와 값이 다른 것이 정상이고 대조는 이 도구끼리 한다. 개행 외의 정규화(끝
공백 제거 등)는 안 한다 — 규칙이 늘수록 «무엇이 변경인가»가 흐려진다. 포매터 위양성은 §9-4의 한계다.

### 4-5. CLI · exit code · 출력 실물

```bash
node framework/spec-anchor.mjs record <SPEC.md 경로> [--json]   # drift도 같은 형식
node framework/spec-anchor.mjs --selftest
```

exit(둘 다 동일 — `spec-verify` 선례): **0** 위반/드리프트 없음 · **1** 위반(A1·A2) 또는 드리프트
1건 이상 · **2** 파일 없음(SPEC/anchors)·JSON 손상·사용법 오류. 1과 2를 반드시 가른다.
record 출력 실물 — 통과 시와 위반 시(위반이면 **기록하지 않는다** — 전건 통과 시에만 쓴다, §10 #2):

```
spec-anchor record SPEC.md
  지목 12건 · 앵커 가능 10건 · [경고 A3] S9, I4 — 파일:줄 없음, 드리프트 감시 밖
  → SPEC.anchors.json 기록 (10 anchors) · exit 0
--- 위반 시 ---
  [위반 A1] S3 → src/util/tags.ts:40-52 — 파일이 없다 (SPEC.md:91)
  [위반 A2] S5 → src/cart.ts:210-230 — 파일이 88줄뿐이다 (SPEC.md:93)
  → 앵커 미기록 (위반 2 — 지목이 실존과 어긋난다. SPEC §3을 고치고 재실행하라) · exit 1
```

```
spec-anchor drift SPEC.md
  앵커 10건 대조 (기록 2026-08-19)
  missing  1  S3 → src/util/tags.ts (파일 소멸)
  stale    2  S1 → src/cart.ts:12-34 (해시 불일치) · I2 → src/cart/qty.ts:5 (범위 소멸)
  modified 0  (활성 델타 없음 — 이 범주는 SPEC.delta.md가 있을 때만 산다)
  → 코드가 앵커 시점에서 갈라진 문장 3 · 앵커 그대로인 문장 7 · exit 1
```

`--json`은 같은 내용을 `{subcommand, anchors, violations, warnings, drift:{missing,stale,modified},
exit}` 구조로 낸다. KF4의 단일 CLI가 이 JSON을 읽어 SG1021~1026으로 감싼다 — 번호는 여기서 안 붙인다.

### 4-6. 3범주 판정 규칙 — modified와 KF1의 관계

앵커 하나마다 순서대로 판정한다(같은 파일시스템 상태 → 항상 같은 답):

1. `file`이 없다 → **missing**.
2. 파일은 있는데 `endLine`이 현재 줄 수를 넘거나 읽기 실패 → **stale**(사유 «범위 소멸»/«읽기 실패»).
3. 스팬 재해시 ≠ 기록 해시 → 활성 `SPEC.delta.md`의 MODIFIED 절이 이 앵커의 문장 ID를 지목했으면
   **modified**(«선언된 수정, 앵커 미갱신» — 조치: record 재실행), 아니면 **stale**(조치: 문장 재검토).
4. 해시 일치 → 드리프트 아님.

MODIFIED 선언 판독은 **KF1 `spec-delta.mjs`의 `inspect()` 계열 export**를 import한다(메인 §5-1) —
델타 파서를 중복 구현하지 않는다. **KF1 전에는 `SPEC.delta.md`가 없으므로 modified는 항상 0이고
drift는 2범주 퇴화 모드로 돈다**(고장이 아니다). 부수 대조 2건은 경고로만 낸다(exit에 안 싣는다):
ⓐ anchors의 ID가 현행 SPEC에서 사라짐 ⓑ SPEC에 앵커 없는 새 지목 — 둘 다 «record 재실행 권장».
실패 모드: SPEC/anchors 부재·JSON 손상 → exit 2. 문장 ID 없는 SPEC(`c4 = null`) → record는 앵커
대상 0건으로 파일을 안 쓰고 경고 + exit 0(C4 «판정 불가»와 같은 결).

### 4-7. 게이트에 걸지 않는다 (record도, drift도)

- **drift**: 메인 §5-3의 고정 결정 — 명시 실행(또는 나중에 CI) 전용. Stop 훅에 걸면 FIELD-GUIDE 예언
  P2(«제일 먼저 끄고 싶어질 것»)를 재생산한다. 드리프트는 재방문 시점의 정보이지 매 세션의 통과 조건이 아니다.
- **record**: 훅에 걸면 원 요청이 명시한 KF3 예산(«중단 0회»)이 깨진다. Stop에서 C4 통과 직후 자동
  record는 유혹적이지만(가짜 지목이 완료를 막게 된다), 유령 지목이 실측되기 전까지는 추측성 배선이다
  (FIELD-GUIDE §5 — 예언에 없던 개선을 미리 하지 않는다). §10 #1로 남긴다. **그 대가로, record를
  안 돌리면 아무것도 실증되지 않는다** — §9-5.

### 4-8. stale 위양성과 앵커 재기록 절차

줄 기반 앵커의 구조적 위양성: **심볼 리네임·스팬 위 줄 삽입·포매터 정리만으로 stale이 난다** —
해시로는 «의미 보존 변경»과 «의미 변경»을 가를 수 없고, 가르려는 순간 결정론이 깨진다(개발 규칙 5).
완화는 검사를 똑똑하게 만드는 것이 아니라 **재기록을 싸게 만드는 것**이다: ① stale 보고 → 사람이
문장과 현재 코드를 읽고 «여전히 참»인지 판단한다(판단이므로 자동화 안 함) ② 여전히 참이면 SPEC §3의
지목 줄 번호를 현재 위치로 고치고 `record` 재실행 — 전건 재검증 후 전체 재기록이라 부분 꼬임이 없다
③ 참이 아니게 됐으면 그 문장이 곧 수정 대상 — KF1 델타로 들어가는 것이 정상 경로다. stale은
«문장이 거짓이 됐다»가 아니라 **«다시 읽을 우선순위»**다 — 그것이 3범주의 정확한 의미다.

## 9. 명시적 한계 (반증 지점 병기)

1. **실재 확인 ≠ 의미 일치.** 앵커가 확인하는 것은 «그 위치에 그 텍스트가 있(었)다»까지다. 그 코드가
   문장을 참으로 만드는지는 여전히 미검증이다. «형식에서 내용으로» 같은 표제는 과대다 — 이 기능은
   조사 Q2를 푸는 게 아니라 **결정론이 성립하는 범위로 문제를 깎은 것**이다(원 요청 명시 한계 원문).
2. **앵커가 안 바뀐 의미 변화를 놓친다**(원 요청 명시 한계). 스팬 밖 변경(호출부·의존 모듈·설정)으로
   문장이 거짓이 돼도 drift는 침묵한다. drift exit 0은 «문장 전건이 아직 참»이 아니라 «앵커 스팬이
   그대로»라는 뜻이다.
3. **«파일:줄 없는 정당한 지목»은 앵커 대상에서 제외된다.** «실행 확인»·«부재로 충족» 같은 무위치
   지목은 실물에 있고 정당하다(C4가 이를 경고로만 내는 이유). 그 문장들은 A3 경고 + `unanchored`로
   표시될 뿐 **드리프트 감시 밖이다** — 무위치 지목이 많은 SPEC일수록 이 도구의 커버리지는 좁다.
4. **줄 기반 앵커의 stale 위양성** — 심볼 리네임·스팬 위 줄 삽입·삭제만으로 stale이 난다(§4-8,
   selftest d4가 이 동작을 고정한다). 개행 외 정규화를 안 하므로 **끝 공백을 지우는 포매터·전면
   리포맷**도 stale을 낸다 — 의미 보존 변경과 의미 변경을 해시는 못 가른다(가르는 순간 판단이
   들어와 결정론이 깨진다, 개발 규칙 5). 완화는 재기록 절차뿐이고 «여전히 참» 판단은 사람 몫이다.
   재기록이 잦아 마찰이 되면 그것이 §10 #4(심볼 앵커)의 번복 조건이다.
5. **안 돌리면 아무것도 실증되지 않는다.** record는 훅에 안 걸려 있으므로(§4-7) 이 층 자체가
   fail-open이다. record를 건너뛰고 완료를 선언해도 현행 게이트는 통과다. 이 갭을 닫는 배선은
   유령 지목이 실측된 뒤의 결정이다(§10 #1).
6. **효과 실측 0.** 원 요청의 정직한 결말 그대로 — 다섯 기능 중 효과가 실측된 것은 없고, 차단이
   품질을 올린다는 통제 비교도 조사 전체에 없다(조사 Q1). «재방문 시 읽기 대폭 감소»도 기대이지
   관측이 아니며, 통제 실험으로 못 재므로(전환의 대가) 실사용의 아쉬운 지점으로만 반증된다.
7. **modified는 KF1 없이는 비활성**이고, KF1이 와도 델타가 문장 ID를 안 달았으면(D3는 Warning) 그
   수정은 modified로 분류되지 못하고 stale로 나온다 — 범주 경계가 델타 기록 품질에 종속된다.
8. 앵커의 실증은 **record 시점**의 실존이다 — 이 도구는 연속 감시가 아니라 두 시점 대조다.
