# KF2 수정계획서 — 예산제 침묵 인터뷰

## 0. 요약

sdd `SKILL.md` §2에 이미 문안으로 있는 선별 절차(질문 승격 최대 3개)를 `/spec` 플로우에서 도구
지원 형태로 격상한다. 새 코드는 결정론 기록·집계기 `framework/spec-interview.mjs`(log·stats·
--selftest) 하나뿐이고, 질문을 뽑는 판단은 기존대로 `/spec` 세션의 에이전트 턴이 한다(LLM 1패스
상한, 별도 호출 0). 어떤 경우에도 차단하지 않는다 — 게이트는 한 줄도 안 바뀌고, 전건 건너뛰어도
침묵은 `선택 대기`로 남는다. 약속하지 않는 것: 감지 능력 신설·mute 저장(KF4 이후)·예시 은행(가설).

## 1. Pain Point와 근거

- **이 리포의 관측된 갭이 정확히 여기다.** 실사용 1회차 `specHit` 1/4 — 갭은 §4(문장→테스트
  전이)가 아니라 §2(침묵 지점 포착)다(`docs/REPORT4.md`·`docs/REPORT5.md` §6).
- **외부 실증도 같은 방향.** 조사 F4 — LLM은 자율적으로 되묻지 않지만 명시적으로 프롬프트되면
  감지는 가능(ClarifyGPT +~10pp). 도구가 할 일은 감지를 매번 트리거하는 것이다(원 요청 KF2).
- **질문 형식 근거**: 조사 F5b — «왜 모호한가» 한 줄 설명 3.84/5. 각 질문에 이 한 줄을 붙인다.
- **몇 개를 묻느냐가 승부처.** 후보를 다 뱉으면 조사 F1(리뷰 부담으로 죽은 SDD)을 인터뷰 화면에서
  반복한다. 꺼버리는 임계는 아무도 모르므로(조사 Q3 미해결) 완화 3종 — 질문 예산 3개 고정 · 카테고리 단위 mute만(전체 off 없음) · 무시/수락 비율 로컬 기록 후 «mute 권장» 제안만.
- **반증 방향의 자기 실측**: r31 대조군 — 문안 없이도 판정 ③ «충족». 일부 침묵은 모델 기본
  행동으로 채워진다(r31 §1-4). §9-2에서 병기 의무로 다룬다.
- **오염 관측과의 정합**: r35 판정 IV(기본값의 테스트 단언 고착) — Enter 수락의 `[추론]` 유지(§4-3)는 spec-template §2.3 주석의 개입과 같은 방향이다.

## 2. 목표 / 비목표

**목표**

1. 트리거의 도구화 — `/spec`의 SPEC 신규 작성 분기마다 침묵 인터뷰가 빠짐없이 발동한다.
2. 침묵의 이름 붙이기 — 3택 어느 쪽으로 응답해도(무응답 포함) 침묵이 SPEC.md 문면에 남는다.
3. 무시/수락의 로컬 관측 — `.specgate-interview.jsonl`에 결정론 기록·집계, «mute 권장»은 제안만.
4. 중단 상한 고정 — 인터뷰 블록 1회, 질문 최대 3개, 재실행 없음.

**비목표 (목표와 같은 무게)**

1. **차단 없음.** 게이트에 검사를 추가하지 않고, 인터뷰 미수행·전건 건너뜀을 exit code로 막지 않는다.
2. **감지 능력을 만들지 않는다.** 모델이 못 찾는 침묵은 도구도 못 찾는다(조사 F4의 비대칭 그대로).
3. **전체 off 스위치 없음.** 카테고리 단위 mute 제안만 — 설정 저장은 KF4 `.specgate.json` 이후(메인 §5-1).
4. **택소노미 확장 없음.** 점검표 10범주(SKILL.md:43-53) 고정 — 학술 7범주 이식 기각(0-3).
5. **예시 은행 미구현.** 10-shot 콜드스타트(조사 F5a +20.2%) 재사용은 §9-5의 가설로만 둔다.
6. 기존 SPEC 재방문(«있으면» 분기)·델타 플로우(KF1)에서의 발동은 범위 밖 — 신규 SPEC 초안 직후 1회만.

## 3. 현행 기반과의 관계

**이 기능의 실체는 «새 데몬»이 아니다.** 질문 승격 최대 3개·확정 3방식·6열 미확정표·`선택 대기`는 전부
`skills/sdd/SKILL.md` §2에 이미 있다. KF2가 더하는 것은 그 절차가 `/spec`에서 (a) 매번 발동하고
(b) 응답이 기계가 셀 수 있는 기록으로 남는 두 가지다.

| 기존 파일 | KF2에서의 취급 | 근거 |
|---|---|---|
| `skills/sdd/SKILL.md` (79줄) | **무변경.** 선별·확정 절차를 참조만 한다 | `spec-verify.mjs`의 주석과 위반 메시지 문자열(:34·:40-53·:64-68·:74-78·«SKILL.md:77» 등)이 SKILL.md 줄 번호를 참조 — 줄 이동은 검사 정의의 표류다 |
| `commands/spec.md` (22줄) | **확장.** «없으면» 분기에 인터뷰 절차 추가(새 커맨드 없음) | 커맨드 수 불변(메인 §5-1의 KF1 선례와 동일) |
| `spec-template.md` §2.3 | **무변경.** 건너뜀 격하의 수용처 | U표 6열·`선택 대기`가 이미 규약 |
| `hooks/spec-gate.mjs` · `spec-verify.mjs` | **무변경.** Advisory 층은 게이트를 안 건드린다 | 메인 §5-3 경계 원칙 |
| `.specgate-log.jsonl` 선례 | **차용.** flat jsonl · append · 실패 무해(FIELD-GUIDE §1) | 새 포맷 발명 없음 |
| `framework/spec-interview.mjs` | **신규.** log/stats/--selftest | 아래 정당화 |

신규 파일이 «먼저 있는 걸 쓴다»(개발 규칙 2)에 어긋나지 않는 이유: 기존 도구 어디에도 «SPEC 밖 파일의
집계» 자리가 없다 — `spec-verify.mjs`는 SPEC 검사기, `specprobe.mjs`는 SPEC 계수기다. Node 내장만으로
수십 줄이면 되고(새 의존성 0), KF4의 `specgate.mjs`가 나중에 얇게 감싼다(메인 §5-1).

## 4. 설계

### 4-1. 경계 확정 — 무엇이 문안이고 무엇이 코드인가

| 층 | 담당 | 성격 |
|---|---|---|
| 침묵 후보 탐색·질문 선별·질문 문안 작성 | 에이전트(`/spec` 세션 턴, SKILL.md §2 그대로) | 판단 (LLM 1패스) |
| 인터뷰 발동 시점·질문 형식·3택 반영 규칙 | `commands/spec.md` 문안 확장 | 절차 규정 (텍스트) |
| 응답 기록·무시/수락 집계·mute 권장 판정 | `framework/spec-interview.mjs` (신규 코드) | 결정론 (LLM 0, 토큰 0) |

결정론과 판단을 섞지 않는다(개발 규칙 5) — 집계를 에이전트에게 맡기면 같은 기록에 다른 답이 나온다.

### 4-2. 동작 흐름 (`/spec` — SPEC «없으면» 분기)

```
1. sdd 절차로 SPEC §0~§2 초안 작성                   (기존 그대로)
2. node spec-interview.mjs stats                     [KF2] mute 권장 있으면 질문 전에 보고, 이번
                                                      세션에서 승격을 멈출지 묻는다(저장 없음)
3. Partial/Missing 중 질문 승격 최대 3개 선별         (SKILL.md §2 선별 기준 — 판단은 에이전트)
4. 질문을 한 번에 하나씩 (형식 고정 — 아래 예시),
   응답마다 ① SPEC 반영(§4-3 표) ② log 기록(§4-6)    [KF2]
5. 승격 안 된 후보: 화면 출력 없이 §2.3 U표에만       (SKILL.md «기록은 무제한» 그대로)
6. 이후 기존 플로우(구현 → §3 대조 → 게이트)          (기존 그대로 — KF2 개입 없음)
```

질문 출력 형식(터미널):

```
[specgate 인터뷰 1/3 · 범주 6 엣지 케이스·실패 처리]
질문: 항목을 전부 삭제하면 진행률 표시는 무엇을 보여야 하는가?
왜 모호한가: 요청 문장은 «진행률 표시»만 말하고 분모가 0인 상태를 정하지 않았다.
제안 기본값: «0/0 · 항목 없음» 문구를 표시한다
→ 답을 쓰거나 / Enter(기본값 수락) / «건너뜀»
```

«그만 물어»가 오면 남은 질문은 묻지도 기록하지도 않는다(집계 오염 방지) — 후보는 U표에만 남는다.

### 4-3. 3택 응답의 SPEC.md 반영 규칙

| 응답 | SPEC.md 반영 | U표(§2.3) 행 | 기록 `resp` |
|---|---|---|---|
| **답한다** | §1에 S문장 추가 — 근거: 사용자 답변, YYYY-MM-DD (확정 방식 «직접 정의/선택») | 해당 행이 있었으면 상태 `확정`, 문장은 §1로 | `answer` |
| **Enter (기본값 수락)** | §2.2에 I문장 추가 + `[추론]` 표기 유지 (원 요청 원문 — Enter는 위임이지 선택이 아니다) | 행 잔존, 상태 `위임`(YYYY-MM-DD) — 대안·이력을 남긴다(확정 방식 «위임») | `accept` |
| **건너뜀** | 문장 추가 없음 — `선택 대기`로 격하 | 행 상태 `선택 대기` — 이후는 기존 C5가 완료 전 재확인 전건 제시를 강제(KF2 신설 아님) | `skip` |

Enter 수락의 `[추론]` 유지: 사용자가 문장으로 답하기 전까지 그 값은 추론이다(§1-마지막 근거).
`위임` 행은 C5 집계(`선택 대기` 행만 센다)에서 자연히 빠지고 C3는 열 수만 보므로 기존 검사기와
충돌하지 않는다. 리터럴 자체는 §10-3 선택 대기다.

### 4-4. 기록 포맷 — 프로젝트 루트 `.specgate-interview.jsonl`

메인 §5-1 확정 이름. `.specgate-log.jsonl` 선례대로 flat·append·gitignore 권장. 1응답 = 1줄.

```jsonl
{"t":"2026-08-21T09:14:02.113Z","cat":6,"q":"항목을 전부 삭제하면 진행률 표시는 무엇을 보여야 하는가","resp":"skip","u":"U3"}
{"t":"2026-08-21T09:15:40.902Z","cat":3,"q":"필터 초기 상태는 전체인가 오늘인가","resp":"accept","u":null}
```

필드: `t`(필수 — ISO 8601 응답 시각) · `cat`(필수 — 정수 1~10, 점검표 10범주 번호 SKILL.md:43-53,
새 택소노미 없음) · `q`(필수 — 질문 한 줄) · `resp`(필수 — `answer`|`accept`|`skip` 3택) ·
`u`(선택 — 연결된 §2.3 행 ID, `U3` 형태 또는 null).
기록 대상은 **질문으로 승격돼 응답을 받은 것만** — 승격 안 된 후보의 기록처는 U표다(이중 기록 없음).

### 4-5. 집계와 «mute 권장» — 결정론 규칙

무시 = `skip`, 수락 = `answer`·`accept`. **권장 규칙(기본값)**: 카테고리별 파일 순서(=시간 순서)의
**최근 10건** 창에서 `skip` **9건 이상**이면 «mute 권장», 10건 미만이면 제안하지 않는다(콜드스타트
침묵). 창 10·임계 9는 근거 있는 값이 아니라 기본값이다(§10-1). 소비: `/spec` 문안이 인터뷰 전에
stats를 돌려 권장을 보고하고 «이번 세션에서 이 범주 승격을 멈출까»만 묻는다 — **저장은 없다**(§8-3).

사람용 출력은 카테고리별 카운트 한 줄씩(`범주 3: 질문 12 · 답변 1 · 수락 2 · 무시 9 | 최근 10회 중
무시 9 → mute 권장`)과 말미의 권장 요약 한 줄이다. `--json` 출력:

```json
{ "file": ".specgate-interview.jsonl", "total": 27, "malformed": 0,
  "byCategory": {
    "3": { "asked": 12, "answer": 1, "accept": 2, "skip": 9, "recent10skip": 9, "muteSuggest": true },
    "6": { "asked": 5, "answer": 3, "accept": 2, "skip": 0, "recent10skip": 0, "muteSuggest": false } },
  "muteSuggest": [3] }
```

### 4-6. CLI 인터페이스·exit code·Advisory 경계·실패 모드

```bash
node framework/spec-interview.mjs log --cat <1..10> --resp <answer|accept|skip> --q "<질문>" [--u U3] [--dir <프로젝트 루트>]
node framework/spec-interview.mjs stats [--json] [--dir <프로젝트 루트>]
node framework/spec-interview.mjs --selftest
```

- `--dir` 기본값은 cwd. `/spec` 문안에서는 `${CLAUDE_PLUGIN_ROOT}` 경로로 호출 — 기존 spec-verify 호출과 같은 형태, `allowed-tools`의 `Bash(node:*)`로 충분(권한 추가 없음).
- exit code — **판정을 exit에 싣지 않는다**(specprobe와 같은 성격, 메인 §5-3):
  `log` 0 = 기록 성공 또는 기록 실패(stderr 경고 1줄) / 2 = 사용법 오류(cat 범위 밖·resp 미상·q 없음).
  `stats` 0 = 항상(파일 없음 = 빈 집계 — 정상 상태) / 2 = 사용법 오류. `--selftest` 0 전건 일치 / 1 어긋남.
- 인터뷰용 SG 룰 번호는 **없다** — 메인 §5-2 예약 블록에 인터뷰 몫이 없는 것은 의도다(Advisory
  층은 룰셋 밖). KF4가 stats 값을 노출할지는 KF4 문서 몫이다.
- **Advisory 경계(원 요청·메인 §5-3 재확인)**: 어떤 경우에도 차단 없음 — 게이트 파일 무변경, 인터뷰
  관련 exit 1 부재, 3건 전부 skip이어도 아무 장치도 안 걸린다(완료 전 재확인은 기존 C5 몫). **LLM
  1패스 상한** — 인터뷰는 `/spec` 세션 안 에이전트 턴 1회(별도 프로세스·API 호출 0), 재실행·추가
  질문 라운드는 문안으로 금지. log·stats는 토큰 0.

| 실패 모드 | 동작 | 근거 |
|---|---|---|
| jsonl append 실패(권한·잠금) | exit 0 + stderr `기록 실패: <사유> — 인터뷰는 계속한다` | 관측이 플로우를 안 망가뜨린다(FIELD-GUIDE §1 선례) — §10-5 |
| stats에서 깨진 줄 | 그 줄만 `malformed`로 세고 집계 제외, exit 0 | 기록 파일은 도구 밖에서도 손댈 수 있다 |
| 기록 파일 부재 | stats 빈 집계 + exit 0 | 신규 프로젝트의 정상 상태 |
| 에이전트가 log 호출 누락 | 잡을 장치 없음 — 기록이 조용히 빈다 | Advisory라 게이트로 강제하지 않는 것이 설계다(§9-8) |
| CRLF 혼입 | 파싱 시 `\r` 허용 | Windows 실행 환경(리포 실측 환경) |

## 5. 작업 분해 (WBS)

각 라운드의 산출물은 «돌아가는 코드 + selftest»다(개발 규칙 1·4). 판정 문서 라운드는 없다.

**R1 — `framework/spec-interview.mjs` (log · stats · --selftest)**

- 산출물: 신규 파일 1개(Node 내장만, 예상 100~150줄 — 계획 추정치) + `--selftest` 12건(§6 표) 전건
  통과. selftest는 `spec-gate.mjs` 선례대로 실프로세스(`execFileSync`)로 인자 파싱·exit code까지 덮고,
  `mkdtempSync` 임시 디렉터리를 쓰고 정리한다 — 리포 픽스처를 만들지 않는다(개발 규칙 4).
- 종결 조건: 자기 selftest 12건 + 기존 selftest 2종(§6 수용 기준 ②) 무변경 통과. LLM 비용 0.

```markdown

4. 승격되지 않은 후보는 화면에 출력하지 않고 §2.3 표에만 적는다.
5. 인터뷰는 한 번만 한다 — 재실행·추가 질문 라운드를 만들지 않는다(LLM 1패스 상한).
```

## 8. 의존성과 착수 조건

1. **공통 전제**: r38 관문 A-3(설치 형태 차단 확인) 통과 + 사용자 게이트 G3(실사용 실수요) +
   실사용(jp-trip) 투입 개시(메인 §0·§4). A-3 실패 시 모든 KF가 멈춘다.
2. **P1 내 순서는 계획이 정하지 않는다** — 실사용에서 §2 갭이 실제로 아쉬웠는지가 정한다(`specHit` 1/4은 근거일 뿐, 순서 확정은 관측 뒤다).
3. **mute의 단계 분리(순서 고정)**: KF4의 `.specgate.json` **전에는 설정 파일이 없다**(메인 §5-1).
   그 전의 KF2는 기록(`log`)과 제안(`stats`)만 한다 — 세션 안 «이번엔 이 범주 묻지 마»는 대화로
   처리되고 영속되지 않는다. 역으로 KF2는 KF4를 기다리지 않는다 — 제안만으로 완결이다.
4. **KF1과의 관계**: 인터뷰 자체는 독립. 단 §9-5의 예시 은행 가설은 «과거 해소된 선택 대기 행·델타»가 재료라서 KF1 델타가 실사용에서 쌓인 뒤에만 검증 가능하다.
5. **KF4 랩**: `specgate.mjs`가 감쌀 때 기존 서브커맨드·exit code를 유지한다(메인 §5-1 — 얇게 감싼다). 인터뷰에 SG 룰 번호를 부여하지 않는 것이 기본값이다(§4-6).
6. **회귀 조건**: `spec-verify.mjs`·`spec-gate.mjs`·`SKILL.md` 무변경 + 기존 selftest 2종 통과가 각 라운드 종결 조건이다(§6).

## 9. 명시적 한계 (반증 지점 병기)

1. **외부 근거 등급**: 조사 F5는 medium. ClarifyGPT +~10pp·F5b 3.84/5·F5a +20.2%는 전부 다른 과제·다른 도구의 실측이지 이 도구의 효과가 아니다.
2. **자기 실측이 반증 방향이다**: r31 대조군 — 문안 없는 대조군 1런에서도 판정 ③ «충족». 일부
   침묵은 모델 기본 행동으로 채워진다. KF2 효과를 관측·보고할 때는 **«모델 기본 행동일 수 있다»
   (r31 §1-4) 병기 의무**가 있다. 실사용에서는 같은 시드·요구의 대조 런이 성립하지 않으므로(스모크
   설계 규칙 조건 5의 실사용 예외) 이 병기가 상한이다 — 문안 귀속을 실사용 관측만으로 주장하지 않는다.
3. **택소노미 한계**: 학술 7범주 이식 기각(0-3) — 10범주 점검표에 고정하고, 늘린다면 관측된 실패
   유형에서만 늘린다. `cat` 필드도 10범주 밖 값을 받지 않는다.
4. **임계의 무근거**: 과잉 플래깅으로 꺼버리는 임계는 아무도 모른다(조사 Q3 미해결). 질문 3개·창
   10건·임계 9건은 «아는 답»이 아니라 «모르는 값을 강제하지 않기 위한 기본값»이고 §10에 노출한다.
5. **예시 은행은 검증 대상 가설이다**: 과거 해소된 `선택 대기` 행과 델타(KF1 산출물)를 10-shot
   예시로 재사용하면 질문 품질이 오른다(조사 F5a의 이식 가설)는 이 리포에서 미검증이며 v-next
   범위에서 구현하지 않는다 — 검증에는 KF1 델타 축적 + 재료 유무 비교 설계가 먼저 필요하다.
6. **감지 보장이 아니다**: 조사 F4의 비대칭에서 «트리거» 쪽만 보장한다. 모델이 감지 못 하는 침묵은 질문으로도 U표로도 못 올라온다.
7. **경로 한계**: 인터뷰는 `/spec`의 신규 SPEC 분기에서만 발동한다. sdd 스킬 단독 경로·게이트 차단 후 SPEC을 쓰는 경로·기존 SPEC 재방문에는 3택 프로토콜과 기록이 없다(§10-4).
8. **기록의 정직성 한계**: jsonl은 에이전트가 문안 지시로 쓴다 — log 호출을 빠뜨리면 기록이 조용히
   빈다. Advisory라 게이트로 강제하지 않는 것이 설계이고, 그 대가로 stats·mute 권장은 «기록된 것»만 본다(누락은 무시율을 왜곡한다).
9. **skip의 해석 한계**: `skip`이 «질문이 나빴다»인지 «지금은 답을 모른다»인지 구분 못 한다.
   mute 권장이 좋은 질문 범주를 죽일 수 있다 — 저장 없이 제안만 하는 이유다.
10. **중단 +1회의 값어치는 미검증**: F4 발산 차단으로 상쇄되는지는 실사용 관측 항목이다. 관측 신호는 FIELD-GUIDE §6과 같은 결 — 인터뷰를 건너뛰고 싶어진 순간이 데이터다.
