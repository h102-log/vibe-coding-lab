# planedd2priorart — 선행 조사: 차별점 확인 3건 + 이식 상세 1건

## §0. 목적과 산출물

**목적 한 줄**: EDD 트랙이 «미점유 차별점»(결정론-전용 차단 + 구현 전 평가 동결·Red-Check + 출처별
게이트 강도의 결합 — planeddmain.md §1-3)을 선언하기 전에, 딥리서치(2026-08-24)가 미결로 남긴 3건을
원문으로 확인하고, OFT revision-in-ID 대 문장 해시의 트레이드오프를 확정한다.

**이 지시서의 산출물 한 줄**: 판정표 3행(원문 인용 + 사전 등록 3분기) + OFT 트레이드오프 표 + README «다른 점» 문단 **확정본 초안**(반영은 planedd8smoke.md 몫) — 전부 집행 세션의 rN.md에 담는다.

이 라운드는 **조사 라운드다** — 산출물이 문서인 것은 개발 규칙 1의 예외이고, 근거는 이 라운드의
목적 자체가 문안 확정이라는 것이다(planeddmain.md §3-5 R1 — «코드 없는 유이한 라운드»). 그 대신
산출물의 합격 기준을 §5에서 판정 가능하게 좁힌다.

## §1. 배경과 근거

- **차별점 문장은 지금 «잠정»이다.** planeddmain.md §1-3의 초안: *«결정론-전용 차단 + 구현 전 평가
  동결·Red-Check + 출처별 게이트 강도의 결합은 확인된 선례 없음(2026-08-24 기준, arXiv 2606.02755
  확인 전 잠정)»*. 팩 완료 조건 §5 #5(꼬리표를 확정 또는 개정으로)의 종결 라운드가 이것이다.
- **딥리서치가 미결로 남긴 3건**(20소스 · 25건 3표 적대 검증 중): ⓐ arXiv 2606.02755 — 평가 동결
  축 점유 여부 미확인, **유일한 근접 후보**. ⓑ Probity(tdd-guard 후속) — 결정론으로 이동했으면
  차별점 절반이 닫힘. ⓒ spec-kit-v-model 상세(리서치 3-0 ④는 «부분 점유»까지만 판정했다).
- **2차 조사 선확보(감리, 2026-08-24 — 104 에이전트 · 3표 적대 검증)**: ⓑ Probity는 **실존**한다
  (github.com/nizos/probity, ~177★·npm `@nizos/probity`·v1.10.0 2026-07-08)이며 **하이브리드**다 —
  README *«Rules can be deterministic … or AI-validated using official SDKs»*, 간판 룰 enforceTdd는
  *«Uses an AI validator»*(docs/rules.md), FAQ가 AI 룰의 토큰 비용(«add a turn each time»)을 인정 →
  **예상 분기 ②**. ⓒ spec-kit-v-model은 결정론 스크립트 게이트(run-v-model-gate.sh 8단계, 게이트
  경로 LLM 0)이되 **opt-in 커맨드**고 README가 *«hybrid mode … bypasses the V-Model gates»*를 자인,
  37★·2026-05-21 이후 커밋 없음 → **예상 분기 ①**. ⓐ는 2차 조사에서도 실존 미확인(분기 0 후보).
  **판정은 여전히 집행 라운드 몫이다** — §3-0 규약(사전 등록 → 원문 재확인 인용)대로 위 인용을
  재확인해 판정표를 채운다. 재확인이 다르면 그쪽이 이긴다.
- **이식 상세 1건**: OFT revision-in-ID(리서치 확정 ⑧ — 가져올 것 1순위)를 우리는 문장 해시로
  변형해 이식한다(planeddmain.md §3-1 #7, E5 — planedd4verify.md). 두 방식의 트레이드오프를 원문
  기준 표로 만들고 기본값의 **번복 조건을 등록**해야 «조용히 정한 것»이 되지 않는다(개발 규칙 6).
- **왜 사전 등록인가**: 절대 규칙 5는 실험 트랙 규칙이라 여기 적용되지 않지만(절대 규칙 7), 그
  정신이 이 라운드의 성립 조건이다 — 원문을 읽은 **뒤에** 기준을 세우면 «차별점이 있도록» 기준이
  휘는 것을 막을 수 없다. 그래서 §3-1의 판정 기준 3벌을 조사 **전에** rN.md에 옮겨 적는다(§3-0).

## §3. 작업

### §3-0. 사전 등록 (조사보다 먼저)

1. rN.md를 열고 **첫 절에** §3-1의 판정 기준 3벌(기준 문장 + 3분기)을 그대로 옮겨 적는다. 조사
   결과는 그 뒤 절에만 적는다 — 절 순서가 곧 «기준이 먼저였다»의 증거다.
2. **인용 없는 판정은 무효다.** 판정표의 모든 행은 원문 인용(외국어면 원문 그대로 + 출처 URL과
   위치)을 가진다. 인용에 AI 제품명이 포함되면 인용부 안에서만 그대로 두고 본문 서술에는 쓰지 않는다.
3. 소스에 닿지 못하면(404·프록시 차단·검색 0건) **시도한 검색어·URL 전부를 원문 그대로 기록**하고
   해당 분기(«미발견»)로 판정한다 — «없음이 확정됐다»가 아니라 «이 검색 범위에서 발견되지 않았다»다.

### §3-2. OFT revision-in-ID 정독 + 트레이드오프 표

**방법**:

```
WebFetch https://raw.githubusercontent.com/itsallcode/openfasttrace/main/doc/user_guide/user_guide.md
# "revision" 검색 — specification item ID 포맷 절(req~name~N)과 개정 규칙 절을 정독
```

확인할 것 2건(각각 원문 인용): ① revision은 **사람이 수동으로** 올리는가 ② revision을 안 올리고
내용만 고치면 도구가 감지하는가(내용 해시 검사의 존부). ②가 원문에 명시돼 있지 않으면 «명시 없음
(부재 확인)»으로 적는다 — 부재의 확인도 판정이다.

**트레이드오프 표** — 아래를 rN.md에 옮기고, OFT 열의 각 셀을 인용 근거로 확정한다(예상과 어긋나는
셀은 어긋남을 기록하고 실물대로 고친다):

| 축 | OFT revision-in-ID (`req~foo~1`) | 우리 문장 해시 (E5 — planedd4verify.md) |
|---|---|---|
| 개정 감지 주체 | 사람 — 작성자가 ~N을 올린다 | 기계 — 승인 시점 해시와 현재 문장 대조 |
| 표현만 고친 수정 | 개정 아님으로 둘 수 있다(사람 판단) — 마찰 0 | Outdated 위반 — `## 개정` 행 강제(마찰 있음) |
| 의도 없는 수정(실수) | revision을 안 올리면 못 잡는다 | 잡는다 — 사후 손질 차단(REPORT4 §6-1)이 목적이므로 이쪽이 본질 |
| sdd 자산 접촉 | SPEC ID 포맷 변경(S3~2) — sdd 문안·검사기 파급 | 무접촉 — 해시는 EVAL.md 쪽에만 산다 |
| 어느 개정인지 추적 | ID에 이력이 남는다 | 해시만으로는 못 안다 — `## 개정` 절 행으로 보완 |

표가 확정되면 **기본값(문장 해시) 유지**를 선언하고, ~N 도입 조건을 §7 #1의 번복 조건으로 등록한다.
이 라운드에서 ~N을 도입하지 않는다 — sdd 무접촉(planeddmain.md §3-1 #7)이 상위 계약이다.

### §3-3. README «다른 점» 문단 확정본 초안

현행 문단(`framework/README.md` 5~8행)은 spec-kit 대비 1축(«문안이 제안이 아니라 훅으로 차단된다»)
뿐이다. 아래 **기준선 초안 v0**을 rN.md에 옮기고, §3-1 판정 3건의 처리 열에 따라 고쳐 **확정본
초안**을 만든다. 반영(README 실파일 수정)은 planedd8smoke.md 몫이다 — 이 라운드는 초안을 rN.md의
코드블록으로 남기는 데서 멈춘다.

```markdown
**다른 점은 둘이다.** ① **문안이 제안이 아니라 훅으로 차단된다** — spec-kit 계열은 템플릿과
슬래시 커맨드를 주지만 지키지 않아도 아무 일이 일어나지 않는다(fail-open — 헌법 Article III도
테스트 선실패 확인을 «명령»할 뿐 강제 기계가 없다). 여기서는 `SPEC.md` 없이 `src/*.ts`를 쓰려
하면 Write가 **거부**되고, 구현 위치를 지목하지 못한 문장이 남아 있으면 **완료 선언이 막힌다**.
② **차단 판정에 LLM이 없다** — 같은 PreToolUse 지점에서 차단하는 tdd-guard(2.3k★, 2026-08-24
기준)는 차단 판정을 모델에 맡기고 자체 문서·릴리스 노트가 간헐적 오차단을 인정한다(v1.6.9
«intermittent false blocks»). 여기 게이트는 전부 정적 검사라 같은 입력에 항상 같은 답이 나오고,
판단이 필요한 것은 차단하지 않는다(Advisory). 여기에 edd 축이 더하는 것 — 구현 전에 평가를
동결·Red-Check하고(락 + 스냅샷), SPEC 문장의 출처(S/I/U)가 게이트 강도를 정한다(`선택 대기` 지목 =
단언 금지) — 의 결합은 **훅 수준 실시간으로는** 확인된 선례가 없다(부분 선례: spec-kit-v-model의
opt-in 사후 스크립트 게이트 · 후속 Probity도 핵심 판정은 LLM 유지 — 2026-08-24 조사, 판정표
docs/next/…/rN.md).
```

초안 v0는 감리 2차 조사의 예상 분기(ⓑ②·ⓒ①)를 선반영했다 — 집행 라운드의 원문 재확인이 다르게
나오면 그쪽이 이기고, 위 괄호 절을 판정대로 고친다.

초안 규칙 3개: 타 도구 서술은 인용 가능한 사실만(오차단 인정은 tdd-guard 자체 문서 인용으로만 —
폄하 문구 금지) · 통계(★ 수)는 시점을 박는다 · «게이트를 형식에서 내용으로» 류 과대 서술 금지
(plankf3anchor.md §2 비목표의 금지 선례).

마지막으로 «잠정» 꼬리표를 처리한다: 판정 3건이 전부 현행 유지면 «확정(2026-08-24 조사, 판정표 rN)»
으로, 하나라도 삭제·후퇴·병기가 나오면 개정된 문장으로 — 어느 쪽이든 rN.md에 확정 문장 1개를
명시한다(planeddmain.md §5 #5).

## §4. 산출물

- `docs/next/<집행일>/rN.md` 1장 — 다음 다섯 절을 담는다: ① 사전 등록(판정 기준 3벌 — 첫 절)
  ② 판정표 3행(a·b·c — 인용 원문 + 분기) ③ OFT 트레이드오프 표(확정) + 가져올 것 목록(c)
  ④ README «다른 점» 확정본 초안(코드블록) + 차별점 문장 확정본 1개 ⑤ 선택 대기 갱신(§7).
- 코드 파일 0 · `framework/` 수정 0 · README 수정 0.

## §6. 하지 말 것·경계

- **README를 직접 고치지 마라** — 반영은 planedd8smoke.md의 문서 일괄 라운드다(planeddmain.md §3-3).
- **`framework/`에 아무것도 만들지·고치지 마라.** planedd3 이후의 코드 작업을 이 라운드에서 선착수하지 않는다.
- **원문을 읽은 뒤 판정 기준을 고치지 마라.** 기준이 안 맞는 사태가 생기면 판정을 «판정 불가 + 사유»로
  적고 멈춘다 — 기준을 휘어 분기에 욱여넣는 것이 이 라운드 최대의 실패 모드다.
- **기억으로 채우지 마라.** 검색·페치가 안 되면 그 사실을 기록하고 «미발견»으로 둔다. 사전
  지식은 검색어를 고르는 데까지만 쓴다.
- **결론을 부풀리지 마라.** «없음 확정»이 아니라 «이 검색 범위(기록 병기)에서 발견되지 않음»이다.
  타 도구 서술은 그들 문서가 스스로 말한 것만 인용한다.
- **리서치 기각 2건(«PreToolUse 타임아웃 fail-closed»·«deny 최우선 하드 보장»)을 사실로 인용하지
  마라** — 그것은 planedd1probe.md의 실측 대상이지 이 라운드의 조사 대상이 아니다.
- **~N 표기를 도입하지 마라** — 트레이드오프 표가 ~N 우위로 나와도 이 라운드의 처리는 §7 #1의
  번복 조건 등록까지다(sdd 무접촉이 상위 계약).
