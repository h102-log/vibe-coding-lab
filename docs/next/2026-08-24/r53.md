**판정 기준**: 리서치 3-0 ④의 «문장 ID↔테스트 기계 링크 부분 점유» 판정을 뒤집는 것이 아니라
**경계를 문장으로 확정**한다 — «그들이 하는 것(사후 스크립트 대사)»과 «우리부터인 것(훅 사전

| ③ 미발견·판정 불가 | 저장소 소멸·문서 부족 | 리서치 ④ 판정 유지 — 검색 기록만 |

### OFT revision-in-ID 확인 2건 (§3-2)

① revision은 **사람이 수동으로** 올리는가 ② revision을 안 올리고 내용만 고치면 도구가
감지하는가(내용 해시 검사의 존부) — ②가 원문에 명시돼 있지 않으면 «명시 없음(부재 확인)»으로
적는다. 부재의 확인도 판정이다.

## §2. 판정표 — 조사 결과 3행 (전부 원문 인용, 2026-08-24 페치)

### (a) arXiv 2606.02755 → **분기 ② (프로토콜 제안뿐 — 개념 선례 있음, 강제 기계 미확인)**

- **실존 확인**: https://arxiv.org/abs/2606.02755 — «Acceptance-Test-Driven Evaluation Protocols
  for Business-Centric LLM Systems» (Eric Liang, 2026-06-01). 리서치·감리 2차 조사가 실존을 확인
  못 했던 문헌이 이번 페치로 실존 확정됐다.
- **개념은 근접한다** (초록 원문): *"The extension translates stakeholder goals into executable
  behavioral contracts, release gates, monitoring signals, and evidence artifacts **before** prompt,
  model, retrieval, or agent changes **are accepted**. It adapts the red-green-refactor discipline
  of test-driven development to a red-train-green lifecycle: first define failing acceptance tests
  for desired behavior…"* — 구현·변경 수용 전 평가 확정 + 선실패 확인(Red-Check 대응물)이 개념으로
  전부 있다.
- **강제 기계는 산출물로 확인되지 않았다**: 초록의 기여 서술은 *"a governance-oriented **metric
  stack, reference architecture, and empirical protocol**"* — 도구·코드 산출물 언급 0. 코드 리포
  검색(WebSearch `"Acceptance-Test-Driven Evaluation Protocols" Liang LLM github implementation`)
  에서도 구현 저장소 발견 0.
- **조사 한계(기록)**: 본문 정독 실패 — https://arxiv.org/html/2606.02755 은 **404**, PDF
  (arxiv.org/pdf/2606.02755)는 텍스트 추출이 대부분 불가(가독 부분에서 도구·리포 링크 발견 0).
  따라서 «본문 어딘가의 리포 링크»는 배제 못 한다 — «이 검색 범위에서 발견되지 않음»까지다.
- **처리(사전 등록 ② 그대로)**: 결합 문장 유지 + «개념 선례 있음, 강제 기계 없음(인용)» 병기 —

- **게이트 실체** (README + scripts/bash/run-v-model-gate.sh 원문): 8단계 순차 셸 스크립트 —

- **시점·강제 형태**: 커맨드 워크플로(plan → tasks → implement)의 단계에서 스크립트로 실행되는

  mode that **bypasses the V-Model gates**, the `Implements`-directive hallucination guard, and
  the trace post-hook."* 37★ (2026-08-24 기준).
- **정독 대상 3가지 채움**: ① Status: Approved 게이팅 — *"Artifacts under

  `validate-artifact-status.sh`)"* — 스크립트 exit, 워크플로 단계 시점. ② 환각 가드 —
  *"the deterministic `Implements`-directive hallucination guard"* — 결정론, 구현 단계.
  ③ REQ→테스트 커버리지 — 입력 `<feature-dir>`(v-model 하위 구조), 출력 GATE: PASS/FAIL 한 줄,
  검증기 하나라도 비0이면 `overall=1` → `exit 1`.
- **어긋남 기록**(r50 §2 선례): 감리 예상·planedd2 v0 초안은 «사후 스크립트»로 불렀으나 실물은

  경계의 본질(훅 수준 실시간 아님 · opt-in · 우회 자인)은 그대로다. §4 초안은 실물 표현으로 적었다.
- **처리(사전 등록 ① 그대로)**: 차별점 문단에 «부분 선례: spec-kit-v-model» 병기 — 경계 문장 확정.

## §3. OFT revision-in-ID 트레이드오프 표 (확정 — OFT 열 전 셀 인용 근거)

원문: doc/user_guide/user_guide.md (raw.githubusercontent.com, 2026-08-24 페치).

| 축 | OFT revision-in-ID (`req~foo~1`) | 우리 문장 해시 (E5 — planedd4verify.md) |
|---|---|---|
| 개정 감지 주체 | **사람** — *"you made a semantic change and should raise the revision number"*. revision은 ID의 일부: *"All parts are integral to the ID"* | 기계 — 승인 시점 해시와 현재 문장 대조 |
| 표현만 고친 수정 | 개정 아님으로 둘 수 있다 — *"If … you only added a missing period at the end of a sentence, the requirement content did not really change and there is no need to invalidate existing coverage."* — 마찰 0 | Outdated 위반 — `## 개정` 행 강제(마찰 있음) |
| 의도 없는 수정(실수) | 못 잡는다 — 내용 해시 검사 **명시 없음(부재 확인)**: revision 미증가 시 감지 기제가 원문에 없다 | 잡는다 — 사후 손질 차단(REPORT4 §6-1)이 목적이므로 이쪽이 본질 |
| sdd 자산 접촉 | SPEC ID 포맷 변경(S3~2) — sdd 문안·검사기 파급 | 무접촉 — 해시는 EVAL.md 쪽에만 산다 |
| 어느 개정인지 추적 | ID에 이력이 남는다 — *"Incrementing the revision voids all existing links to this item so that authors linking to the item know they have to check for changes and adapt the covering items."* | 해시만으로는 못 안다 — `## 개정` 절 행으로 보완 |

**기본값(문장 해시) 유지를 선언한다.** OFT의 revision은 «사람의 의도 반영»이 강점이지만, 우리
E5의 목적은 «의도 없는/사후 손질 감지»(REPORT4 §6-1 번복 5건 재발 방지)라 축이 다르다. ~N 도입은
하지 않으며(sdd 무접촉 상위 계약), 번복 조건은 §5 표에 등록했다.

## §4. README «다른 점» 확정본 초안 + 차별점 확정 문장

판정 3건 반영: (a)② 개념 선례 병기 추가 · (b)② v0 유지(인용 검증 완료) · (c)① v0 유지하되
«사후 스크립트» → «opt-in 커맨드 게이트»로 실물 표현 교정. 반영(README 실파일 수정)은 planedd8 몫.

```markdown
**다른 점은 둘이다.** ① **문안이 제안이 아니라 훅으로 차단된다** — spec-kit 계열은 템플릿과
슬래시 커맨드를 주지만 지키지 않아도 아무 일이 일어나지 않는다(fail-open — 헌법 Article III도
테스트 선실패 확인을 «명령»할 뿐 강제 기계가 없다). 여기서는 `SPEC.md` 없이 `src/*.ts`를 쓰려
하면 Write가 **거부**되고, 구현 위치를 지목하지 못한 문장이 남아 있으면 **완료 선언이 막힌다**.
② **차단 판정에 LLM이 없다** — 같은 PreToolUse 지점에서 차단하는 tdd-guard(2.3k★, 2026-08-24
기준)는 차단 판정을 모델에 맡기고 자체 릴리스 노트가 간헐적 오차단을 인정한다(v1.6.9
«intermittent false blocks» — 공식 후속 Probity도 간판 룰 enforceTdd는 «Uses an AI validator»).
여기 게이트는 전부 정적 검사라 같은 입력에 항상 같은 답이 나오고, 판단이 필요한 것은 차단하지
않는다(Advisory). 여기에 edd 축이 더하는 것 — 구현 전에 평가를 동결·Red-Check하고(락 + 스냅샷),
SPEC 문장의 출처(S/I/U)가 게이트 강도를 정한다(`선택 대기` 지목 = 단언 금지) — 의 결합은
**훅 수준 실시간으로는** 확인된 선례가 없다(부분 선례: spec-kit-v-model의 opt-in 결정론 커맨드
게이트(훅 아님·hybrid mode 우회 자인) · 개념 선례: arXiv 2606.02755의 평가 동결·release gates
프로토콜(강제 기계는 산출물로 미확인) — 2026-08-24 조사, 판정표 docs/next/2026-08-24/r53.md).
```

**차별점 확정 문장** (planeddmain §1-3의 «잠정» 꼬리표 종결 — planeddmain §5 #5 충족):

> «**훅 수준 실시간** 결정론-전용 차단 + 구현 전 평가 동결·Red-Check + 출처별 게이트 강도의
