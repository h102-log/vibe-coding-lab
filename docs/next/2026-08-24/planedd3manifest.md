# planedd3manifest — EVAL.md 포맷 정의 + eval-template.md 작성 지시서

## §0. 목적과 산출물

**목적 한 줄**: edd 축의 산출물 문서(EVAL.md)의 구조·열 값·해시 규약을 확정해, 뒤따르는 검사기
(planedd4verify.md)·러너(planedd5runner.md)·게이트(planedd6gate.md)가 같은 문법을 읽게 한다.

**이 지시서의 산출물 한 줄**: `framework/eval-template.md` 1파일 신설. 포맷 정의의 SSOT는 이
지시서 §3이다 — 별도 포맷 문서를 만들지 않는다(사용자 대면 문서는 planedd8smoke.md의 README 몫).

## §1. 배경과 근거

- EVAL.md는 SPEC.md(sdd)와 자체 테스트(tdd) 사이의 셋째 산출물이다 — 문장(S/I)을 러너가 판정
  가능한 평가 항목으로 승격하고 승인 시점에 동결한다(planeddmain.md §3-1 항 1·2). E1~E7 검사·스냅샷·훅이
  전부 이 문서의 절·열·해시 값을 파싱하므로 포맷이 먼저다(템플릿 확정 → 검사기가 그것을 검사하는 r50 §1의 순서와 같다).
- 근거 해시가 핵심 장치다: EV 항목이 «승인 시점 문장 내용 해시»를 지니면 SPEC 문장이 바뀔 때 그
  항목만 기계적으로 Outdated가 된다(OFT revision-in-ID의 무접촉 변형 — planeddmain.md §3-1 항 7).
  SPEC ID 포맷(~N)을 건드리지 않고 같은 효과를 얻는 것이 목적이다(sdd 자산 무접촉).
- U 지목 금지(E4)의 근거는 실측이다: i1-cart-r1 판정 IV에서 `선택 대기` 10행 중 4행의 기본값이
  테스트 단언으로 굳는 오염이 관측됐다(r35 §2-4). 이 포맷 규칙이 그 «별도 라운드»로 미뤄둔 예비 개입이다.

## §2. 선행 조건

- 선행 지시서 없음 — 팩 내 최초 착수 가능. 단 **planedd4verify.md와 한 라운드 병합이 기본**이다(planeddmain.md §3-5 R2) — 템플릿 1장만으론 «돌아가는 코드» 요건(개발 규칙 1)을 못 채우고, 그 몫은 eval-verify.mjs가 진다.
- 실행 전 확인 목록:
  - [ ] `framework/eval-template.md`가 아직 없다.
  - [ ] `framework/spec-template.md`·`delta-template.md`·`skills/sdd/SKILL.md` 통독 — 주석 규약(«사본이다», «채우고 나면 이 주석 블록은 지운다»)과 문장 형식을 따른다.
  - [ ] `docs/next/2026-08-21/r50.md` §2-1(한글 헤딩 `\b` 불성립)·§2-4(템플릿 자기 경고)를 읽었다.

## §3. 작업

### 3-1. EVAL.md 전체 구조

머리 + 절 3개. 절 이름은 리터럴이다.

| 요소 | 규약 |
|---|---|
| 제목 | `# EVAL — <대상 이름>` 1줄 |
| 머리 | 불릿 2줄 — `- SPEC: ./SPEC.md`(상대 경로) · `- 러너: vitest`(스냅샷 `runner` 필드와 동일 리터럴) |
| `## 1. 평가 항목` | 6열 고정 표 1개. 절 안의 **첫 표**가 본표다(코드펜스 안 제외 — stripFences 선례) |
| `## 기각` | 2열 표 `\| EV# \| 사유 \|` — 완료 전 재실행에서 green이 아닌 항목의 기각 기록(E6의 대조 재료) |
| `## 개정` | 4열 표 `\| EV# \| 새 해시 \| 사유 \| 날짜 \|` — 동결 후 정당 수정 기록(E5·E7의 통과 재료) |

**헤딩 탐지 인수인계(planedd4verify.md에)**: 번호 접두 허용·`^##\s+(?:\d+[.)]\s*)?기각(?![가-힣])`
형 — 한글 뒤 `\b`는 절대 성립하지 않는다(r50 §2-1 실측). `평가 항목`·`개정`도 같다. **판정
대상은 본표 셀로 한정한다** — 주석·산문 속 ID 리터럴은 세지 않는다(E4의 U 계수 포함).

### 3-2. `## 1. 평가 항목` 열 값 규약

| 열 | 값 규약 | 예시 값 |
|---|---|---|
| ID | `EV`+연번. 유일(E1). 새 ID는 문서 전체 최대 번호+1 — 기각·삭제된 번호를 재사용하지 않는다(spec-template ID 규약 준용) | `EV3` |
| 근거 | SPEC 문장 ID **정확히 1개**(S 또는 I 접두어). 두 문장을 재면 두 항목으로 쪼갠다 — E5 해시 대조가 1:1이어야 기계적이다. I 지목이면 그 접두어 자체가 위임 표시다(planeddmain.md §3-1 항 3) — 별도 열을 만들지 않는다. **SPEC.md가 없는 프로젝트(edd 단독 조합)에서는 요청 원문을 짧게 인용한 자유 텍스트가 근거다** — 그 경우 해시 열은 비워 두고 E3은 경고로 강등된다(planedd4verify.md 'E3.noSpec') | `S1` |
| 근거 해시 | §3-3의 h8 값 8hex 소문자. **승인 시 락을 만드는 도구가 채운다 — 사람이 손으로 적지 않는다.** 승인 전 초안은 빈 셀이며, 빈 셀은 «불일치»가 아니라 **미승인**이다(E5 대조 제외 — 미승인의 차단은 락 부재로 pre 게이트가 맡는다, planedd6gate.md) | `e297df68` |
| 무엇을 어떻게 재나 | 러너가 참/거짓을 낼 수 있는 한 줄 — `<조건> → <러너가 판정하는 관측>`. jsdom에는 레이아웃이 없으므로 «보인다» 금지, «렌더된다/언렌더된다»만(exp/FROZEN.md §4 선례 — axe 전체 스캔 탈락·개별 규칙만 승격) | `0건 응답 스텁 → «결과 없음» 텍스트가 렌더된다` |
| 테스트 | 프로젝트 루트 기준 `tests/eval/` 경로. 한 파일이 여러 EV를 덮을 수 있다. E2는 이 열이 채워졌는가만 보고, 실제 커버 여부는 러너 리포터의 EV 매핑(스냅샷 `missing`)이 잡는다 — 정적 검사와 실행 판정의 분리 | `tests/eval/lookup.test.tsx` |
| 승인 | `<주체>, YYYY-MM-DD` — 주체 리터럴은 `사용자`(직접/선택) 또는 `위임`(물었으나 답 없음 — 물은 기록 필수). 이 열은 사람 몫의 감사 기록이고 **기계 판정은 락이 한다** — 열이 채워졌는데 락이 없으면 락이 이긴다 | `사용자, 2026-08-24` |

테스트↔EV 매핑은 it/describe 이름의 접두다(9장 공통 인터페이스) — `it("EV3: 3건 응답이 목록 행
3개로 렌더된다", …)` 처럼 쓰고, 리포터의 테스트 이름에서 `/\bEV\d+\b/` 전부가 그 테스트의 커버
항목이 된다(구현은 planedd5runner.md).

### 3-3. 해시 규약 h8 — 문장·파일 공통

```
h8(text) = sha256( text의 CRLF→LF 정규화 후 trim ) 의 hex 앞 8자리 소문자
```

- 선례: `exp/judge.mjs:30`의 `frozen`이 개행 정규화 후 sha256을 쓴다 — 같은 계열이고 문장 절취에 필요한 trim만 더한다. 보안이 아니라 **변경 감지** 장치다(8hex 충돌은 문서 한 장 규모에서 실용 무시).
- **문장 해시의 대상**: SPEC.md 정의 줄의 리스트 마커(`- `) 뒤부터 줄 끝까지 **원문 전체** —
  ID·근거 꼬리·`` `[추론]` `` 백틱 포함. 근거 표기만 고쳐도 바뀐다 — 출처(S/I)가 게이트 강도를 정하므로 의도된 민감도다(대안은 §7 #4).
- **파일 해시**(락 `.specgate-eval.lock`의 `evalMd`·`tests` 값)도 같은 h8이다 — 규약 하나, 함수 하나.
- **해시는 도구가 계산한다.** 승인 시 락 생성 도구가 근거 해시 열을 채우고, `## 개정`의 새 해시는
  eval-verify가 E5 불일치 보고와 함께 찍는 현재 값을 옮긴다(그 출력 요구는 planedd4verify.md 몫).

### 3-4. U 지목 금지 (E4의 포맷 근거)

근거 열에는 S/I만 온다. §2.3 미확정표의 U 접두어 행을 지목한 항목은 구현 전 검사 위반이다(E4) —
**아직 정해지지 않은 것은 단언의 재료가 아니다**(r35 §2-4 오염의 재발 방지). 올바른 경로는 그 행을 먼저 확정해 §1로 올린 뒤(S 승격) 지목하는 것 — spec-template.md §2.3 주석과 같은 결이다.

### 3-5. 항목 수·단위 권고 (강제 아님)

- **과제당 3~10개 권고, 상한 강제 없음**(§7 #2) — 3 미만은 평가가 구현을 못 재는 신호, 10 초과는 승인 1회가 «안 읽고 넘김»이 될 신호일 뿐이다.
- **한 항목 = 한 판정** — 러너의 red/green 하나. 서로 다른 문장·관심사를 «그리고»로 묶으면 쪼갠다
  (잘못된 예: «버튼이 렌더되고 클릭하면 호출된다» — EV1+EV2를 한 항목으로). 단 **한 문장이 규정한
  한 시나리오의 사후 상태**를 함께 단언하는 것은 한 판정이다 — §3-7의 EV5가 그 경계의 적법한 예다.

### 3-7. 완전한 예시 1장 — «조회 버튼» 과제

동반 SPEC.md 발췌(해시의 원문 — 이 줄들이 바이트 단위로 §5의 기대 해시와 묶인다):

```markdown
- S1. 접근 가능한 이름이 «조회»인 버튼이 렌더되고, 클릭하면 조회 요청이 정확히 1회 발생하며, 응답의 각 행이 목록의 행으로 렌더된다. (근거: 요청 문장)
- I2. 조회 결과가 0건이면 목록 대신 «결과 없음» 텍스트가 렌더된다. `[추론]`
- I3. 조회 요청이 실패하면 에러 텍스트가 렌더되고 직전 목록 행들은 유지된다. `[추론]`
```

EV1~EV3이 S1 하나를 나눠 잰다 — sdd 문장은 복합일 수 있고 edd가 판정 단위로 쪼갠다. 다섯 항목
전부 «렌더된다/호출된다»형이다(«보인다» 0건 — jsdom 자격). 사용례 3건은 본표를 고치지 않고 읽는다:

- **개정**: 델타로 I3 문안이 «에러 텍스트»→«오류 메시지»로 바뀌면 현재 문장의 h8은 `cd4d11c5`.
  본표의 `14c4c44c`는 두고 `## 개정`에 `| EV5 | cd4d11c5 | I3 문안 변경 — 판정 대상 불변 | 2026-08-25 |`
  1행을 더한다 — E5는 «본표 해시 ≠ 현재 해시»에서 개정 마지막 행 = 현재 해시로 통과한다.
- **기각**: 완료 전 재실행에서 EV5가 red로 남고 정당하면 `## 기각`에 `| EV5 | 실패 응답 재현이 러너 스텁 경계 밖(전송 계층) — 다음 델타에서 재도전 |`.
- **위반 예**: 근거 열에 §2.3 미확정표의 행 ID를 적는 것 — E4 위반(§3-4). 먼저 확정해 §1로 올린다.

## §5. 검증 (판정 가능한 완료 조건)

**해시 재현** — 아래 명령(원문을 인자로 교체하며 4회)의 출력이 표와 정확히 일치해야 한다. 다르면 §3-7 원문이 바이트 단위로 어긋난 것이다 — 기대값이 아니라 원문을 맞춘다:

```bash
node -e 'const{createHash}=require("node:crypto");console.log(createHash("sha256").update(process.argv[1].replace(/\r\n/g,"\n").trim()).digest("hex").slice(0,8))' \
  'S1. 접근 가능한 이름이 «조회»인 버튼이 렌더되고, 클릭하면 조회 요청이 정확히 1회 발생하며, 응답의 각 행이 목록의 행으로 렌더된다. (근거: 요청 문장)'
```

| 원문(리스트 마커 뒤 전체) | 기대 h8 |
|---|---|
| S1 정의 줄 | `e297df68` |
| I2 정의 줄 | `d4f21f56` |
| I3 정의 줄 | `14c4c44c` |
| I3 개정 후 줄(오류 메시지) | `cd4d11c5` |

**예시 EVAL.md ↔ E1~E5 손 대조표** (planedd4의 검사별로 §3-7 예시의 어느 행이 통과 근거인가):

| 검사 | 통과 근거 행 | 값 |
|---|---|---|
| E1 파싱·ID 유일 | 본표 5행 | EV1~EV5 — 6열 정합, 중복 0 |
| E2 테스트 경로·판정 한 줄 | 본표 5행 전건 | 테스트 열 5/5 `tests/eval/` 경로 · 판정 열 5/5 비어 있지 않음 |
| E3 근거 실존 | 본표 근거 열 | S1·I2·I3 — 동반 SPEC 발췌에 정의 줄 실존(SPEC 없으면 경고 강등은 planedd4 몫) |
| E4 U 지목 | 본표 근거 열 | U 접두어 0건 |
| E5 해시 대조 | 본표 해시 열 | 3종 전부 동반 SPEC 원문의 h8과 일치 · 빈 셀 0. 개정 사용례 적용 시엔 «불일치 + 개정 마지막 행 일치»로 통과 |

## §6. 하지 말 것·경계

- **SPEC ID 포맷을 바꾸지 마라** — ~N 개정번호 도입 금지(§7 #1에만 남긴다). sdd 무접촉이 목적이다.
- **`framework/spec-template.md`·`delta-template.md`·`skills/sdd/`를 한 글자도 고치지 마라** — 기존 selftest EXPECTED 무변경이 정합 증거다(r50 선례).
- 포맷 정의 문서를 `framework/`에 별도로 만들지 마라 — SSOT는 이 지시서, 사용자 대면은 planedd8 몫.
- 템플릿에 판정 로직·임계값을 서술하지 마라 — 포맷은 데이터고 판정은 planedd4~6이다. 특히
  «전 문장이 평가로 덮여야 한다»류 문안 금지(C4 복제 금지 — 커버리지는 SG1050 경고 집계까지만).
- 예시·템플릿의 테스트 위치로 `tests/eval/` 밖을 보여주지 마라 — tdd 무접촉(verify-tdd 계수 상호작용은 planeddmain.md §3-7의 «기록만» 대상이다).
- 해시를 손 계산 값으로 적는 절차를 어디에도 만들지 마라 — 도구 계산 경로(§3-3)뿐이다.
