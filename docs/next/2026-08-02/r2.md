2. **Playwright 포기.** 이 머신은 Smart App Control **Enforced**라 chromium 실행이 `spawn UNKNOWN`으로 죽는다(샌드박스 해제해도 동일). 조사 §5.3의 "Playwright/vitest로 Gate 가능" 중 Playwright 갈래가 이 환경에선 닫혔다는 **실측 반증**.
3. **실행 중 차단 0.** 훅·권한·icacls 전부 안 쓴다. 채점 시 `tests/ac/`를 원본으로 통째 복원하면 조작이 점수에 닿을 경로가 없고, 시도는 그대로 관측된다(조사 §6 미해결 #2용 데이터).
4. **코어 층(`src/core/todos.ts` 시그니처 동결) 폐기.** 스택을 React로 고정한 이상 코어 층이 추가로 주는 건 "함수형 코어를 분리하라"는 아키텍처 지시뿐 = 순손실.

### 결정 ②: R4(변경 요구 라운드)를 넣을 것인가

과잉규정 렌즈의 blocker 지적 — **지표가 전부 천장에 붙을 위험**이 크다. 양쪽이 완전한 요구사항 + 실행 가능한 오라클 + 실패 출력 자동 투입을 받으므로 사실상 hill-climbing 과제고, 베이스라인도 4라운드 안에 8/8로 수렴할 공산이 높다. 그러면:

- ① AC 충족률 → **동률 8/8** (1순위 지표가 무정보)
- ② 커버리지 → 처치 준수 여부의 **동어반복**
- ③ 비용 → §8에서 **이미 패배로 사전 등록**
- ④ 피드백 투입 횟수 → 여기도 천장

리포트가 "8/8 대 8/8, 처치군 토큰 3배"로 끝나면 프레임워크가 진 것처럼 읽힌다.

이미 반영한 대응(비용 0): 1순위 지표를 **R0 시점 점수**로 옮김 + 동률 수렴을 §8에 사전 등록.
**추가 제안(비용 1라운드)**: 양쪽이 8/8에 도달한 뒤 동일 문구로 변경 요구 1회.
```

testid는 clear-completed. 다른 요구사항은 그대로다.
```
이 기능은 **범위 밖 목록에 있어서** R0 때 아무도 미리 안 만든다. 새 AC 파일 0개 — 기존 9개를 회귀 스위트로 재사용한다. "기능을 얹었을 때 기존 게 깨지는가"는 **천장이 없는 유일한 신호**다. **권장: 넣는다.**

## 4. 열어둔 리스크

**① 순서 충돌.** FROZEN.md §0은 "두 그룹 실행 사이에 AC·계약을 고쳤으면 양쪽 재실행"을 요구한다. 그런데 계획은 베이스라인 결과를 보고 프레임워크를 만든다 — 그 과정에서 계약을 고치고 싶어지면 베이스라인을 다시 돌려야 한다(비용: 라운드 4세트).
→ **AC/CONTRACT는 이미 적대적 검증을 거쳤으니 고치지 않는다는 각오로 4번에 들어간다.** 그래도 고쳐야 한다면 그건 검증이 놓친 진짜 결함이므로 재실행이 맞다.

**② 설계 편향은 감수하기로 한 것.** 프레임워크가 베이스라인의 관찰된 실패를 보고 설계되므로 당연히 이긴다. 앱을 두 개 만들어 회피하면 일이 두 배. r1 §2.4에서 n=1을 명시하기로 한 것과 같은 태도로, **리포트에 "설계 편향 있음"을 한 줄 적는 것으로 대신한다.**

**③ 처치의 실질 잔여분이 얇다.** FROZEN.md §9-2 — 공통 층이 이미 흡수한 것: 범위 밖 목록(스코프 억제), `test:ac` 안내(테스트 어포던스), **우리가 쓴 AC(판정 주체 분리)**. 남는 처치는 **RED 원문 제출 의무 + 페이즈 분할 + SDD 산출물 강제** 셋뿐이다. 이걸 알고 6번을 설계해야 한다 — 프레임워크가 그 셋 말고 다른 걸 하면 이 실험은 그걸 측정하지 못한다.

**④ 아직 안 정한 것.** 프레임워크의 배포 형태(플러그인 vs `~/.claude` 자산 vs 프로젝트 `.claude`). 조사 §4.2에 따르면 플러그인은 CLAUDE.md·rules를 배포 못 하고 subagent `permissionMode`도 무시한다. 6번에서 정하면 된다 — 지금 정할 필요 없다.
