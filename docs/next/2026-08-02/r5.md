## 2. 🔴 그런데 이긴 이유가 프레임워크가 아니다

동결 AC의 `it()` 제목이 **요구사항 원문 그 자체**다:

```
AC-07 persistence: items and done state survive a remount, via localStorage
AC-08 accessible names: input, toggle and delete each expose a non-empty name
```

**스텁에 오라클을 돌리면 이 여덟 줄이 그대로 출력된다.** 그리고 (b)의 세 런은 정확히 그 선에서 갈렸다:

| 런 | 도구 순서 (세션 로그 원문) | firstImplOracle |
|---|---|---|
| (b) #1 | **ORACLE(스텁)** → `SPEC.md` → `src/` ×5 → 오라클 | **8/8** |
| (b) #2 | **ORACLE(스텁)** → `SPEC.md` → `src/` → 오라클 | **8/8** |
| (b) #3 | `SPEC.md` → `src/` → ORACLE | **7/8** (AC-07 누락) |

**구현 전에 오라클을 돌린 두 런만 8/8이고, 스펙을 먼저 쓴 한 런은 베이스라인과 같은 7/8이다.**
#1·#2의 `SPEC.md`는 항목에 `[AC-07]`·`[AC-08]` 태그를 **직접 달고 있다** — 추론한 게 아니라 읽은 것이다.

### #3이 가장 정직한 데이터다

오라클을 안 보고 스펙을 쓴 유일한 런은 영속성을 **명시적으로 부정**했다:

> `~~U30. 앱은 상태를 브라우저 저장소에 저장하지 않는다.~~ **반증됨.**`
> — 최초 잠정 확정 근거: 계약의 «범위 밖»은 "서버 API·DB"만 적었고 localStorage는 침묵한다.

**절차는 작동했다 — 침묵 지점을 정확히 찾아 문장으로 만들었다. 그런데 답을 반대로 골랐다.**
"범위 밖에 서버 저장이 적혀 있으니 로컬 저장도 안 하는 게 맞다"는 추론은 합리적이고, 계약만 보면 반박할 근거가 없다. r3 §7.4가 "추론 안 되는 것 = 명시되지 않은 비기능 요구"라고 적은 것이 여기서 재확인된다 — **끌어내는 것과 옳게 정하는 것은 다른 문제다.**

### 부정행위는 아니다

`CONTRACT-thin.md`가 양쪽에 똑같이 "동작의 세부는 인수 테스트가 정한다 — `npm run test:ac`의 출력을 근거로 좁혀가라"고 말한다. 열람 금지는 `tests/ac/**` **파일**에 걸린 것이지 **실행 출력**에 걸린 게 아니다. (a)도 할 수 있었고 안 했을 뿐이다.

### 그러나 측정 대상이 바뀐다

재려던 것은 **"명시되지 않은 비기능 요구를 스스로 끌어내는가"**인데, 실제로 갈린 축은 **"구현 전에 정답지를 읽었는가"**다.

그 행동은 `SKILL.md`가 시킨 적이 없다 — RED-first는 r4 §4에서 **의도적으로 뺐다**(표적을 안 겨눈다고 판단해서). 처치가 유발한 부수 행동일 수는 있지만, 어느 쪽이든 **`firstImplOracle`은 이 행동 앞에서 무력하다.** 답을 보고 쓰면 항상 만점이다.

**1순위 지표가 두 번째로 무너졌다.** r4에서 고친 것은 "구현 전 RED 실행을 구현 점수로 오독하는 것"이었는데, 같은 RED 실행이 이번엔 **점수를 올리는 경로**로 돌아왔다.

## 3. 결정해야 할 것 — 조건을 어떻게 균등화하나

세 갈래이고 **전부 (a)(b) 양쪽 재실행**을 요구한다. 재실행 비용은 (a) $1.5 + (b) $5.3 ≈ **$7 수준**으로 낮다.

### ★ (가) AC 제목에서 요구사항 서술을 걷어낸다 — 권장

`it("AC-07 persistence: … via localStorage")` → `it("AC-07")`. 실패 시 출력되는 것은 ID와 단언 실패 원문(`expected [] to deeply equal [ 'A', 'B' ]`)뿐이 된다.

- **왜 이게 맞나**: 오라클을 "요구사항 문서"가 아니라 **판정기**로 되돌린다. 실행 출력으로 좁혀가는 것은 계약이 허용한 그대로 두되, **읽자마자 답이 나오는 경로만 닫는다.**
- **감수할 것**: `exp/ac/todo.ac.test.tsx` 수정 = §0 동결 파일 변경. Red-Check(§5) 재실행 필요. 다만 **단언 로직은 한 글자도 안 건드리고 제목 문자열만 줄이므로** 재검증 범위가 좁다.
- **주의**: 단언 실패 원문에도 정보가 샌다(`AC-08`의 `name /\S/`, `AC-07`의 배열 비교). 완전 차단은 불가능하고, **구현 전에 통째로 읽히는 것만 막는 것**이 목표다.

### (나) 스텁 RED 실행을 양쪽에 강제한다

`prompt-a2.md`·`prompt-b2.md` 공통 층에 "먼저 `npm run test:ac`를 1회 돌려라"를 넣는다.

- 조건이 균등해지고 (가)보다 싸다(AC 무수정).
- **대신 1순위 지표가 죽는다.** 양쪽이 답지를 보고 시작하므로 얇은 스펙 조건이 사실상 완전 스펙으로 돌아간다 — r3에서 깬 천장이 되돌아온다.

### (다) `SPEC.md` 첫 저장본을 지표로 삼는다

오라클 열람 여부와 무관하게, **첫 `SPEC.md` §2에 영속성·접근성에 해당하는 문장이 있는가**를 센다.

- 재실행 없이 기존 데이터로도 계산 가능하고 (a)에는 `SPEC.md`가 없으니 **비교 자체가 성립하지 않는다.** (a)에도 스펙 작성을 시키면 그건 처치를 양쪽에 주는 것이다.
- → **단독으로는 못 쓴다.** (가)의 보조 지표로만.

**권장: (가) → (다)를 보조 지표로 병기.** (나)는 천장을 되돌리므로 배제.

## 7. 열어둔 리스크

- **(가)를 해도 단언 실패 원문으로 정보가 샌다.** 완전 차단은 불가능하고, 목표는 "구현 전에 통째로 읽히는 것"만 막는 것이다. 이 한계는 리포트에 그대로 싣는다.
- **AC 파일을 고치면 §0 동결이 한 번 풀린다.** 제목 문자열만 바꾸고 단언 로직 diff가 0줄임을 기계로 보여야 한다. 그렇지 않으면 "결과를 보고 AC를 손질했다"와 구분되지 않는다.
- **n=3이 세 번째 조건이다.** 완전 스펙 → 얇은 스펙 → 얇은 스펙+제목 축약. 조건을 갈아탈 때마다 이전 데이터는 별도 조건 결과로만 남는다. **여기서 한 번 더 갈아타면 "조건을 계속 바꿔 원하는 신호를 찾는 것"과 구분이 어려워진다** — (가)로 끝내고, 결과가 무엇이든 그것으로 리포트를 쓴다.
- 프레임워크가 이 베이스라인의 실패를 보고 설계됐다는 편향(FROZEN §9-10)은 그대로.
