## 2. 결정적 문제: 4개 지표가 전부 죽었다

| 지표 | (a) 실측 | 처치군 (b)가 이길 수 있는가 |
|---|---|---|
| ① **R0 Gate 통과 수** (1순위) | **8/8** | **불가능** — 동률이 최선이다 |
| ② 커버리지 | 없음 (테스트 0개) | 이기지만 **동어반복** — "테스트를 쓰라"고 지시했으니 쓴 것 |

r2 §2 결정②는 "지표가 전부 천장에 붙을 위험"을 **4라운드 뒤에 올 일**로 봤고, 그 대응으로 1순위를 R0 시점 점수로 옮겼다. 실측 결과 **R0 자체가 천장이었다.** 대비책과 대비 대상이 같이 무너졌다.

r2 §2가 "천장이 없는 유일한 신호"로 지목한 R4마저 37초·6턴에 회귀 0으로 통과했다.

### 왜 이렇게 됐나

FROZEN §9-2가 이미 정확히 적어둔 것이 실측으로 확인됐다. 공통 층이 프레임워크 효과를 흡수했고 — 범위 밖 목록, `test:ac` 안내, 우리가 쓴 AC — 남은 처치는 **RED 원문 제출 의무 + 페이즈 분할 + SDD 산출물 강제** 셋뿐이다. 그런데 그 셋이 겨누는 실패가 **베이스라인에서 하나도 발생하지 않았다.**

여기에 실측이 하나 더 얹혔다: **완전한 요구사항 + DOM 계약 + 실행 가능한 오라클을 받은 Opus에게 Todo 앱은 92초짜리 일이다.** 심지어 **무효 R0는 오라클을 한 번도 실행하지 못한 채로 8/8을 냈다.** 프로세스 강제가 값을 하려면 프로세스 없이는 못 푸는 구간이 있어야 하는데, 이 과제에는 그 구간이 없다.

### 코드를 직접 읽어봐도 표적이 없다

`src/App.tsx` 128줄 + `src/todos.ts` 71줄. 방어적 JSON 파싱, 타입 가드, 순수 함수 분리, `isComposing` 체크(한글 조합 중 Enter), 폼 암묵 제출 차단. AC가 못 잡는 결함을 굳이 꼽으면:

- **자체 테스트 0개** — 가장 큰 결함이지만, 이건 §9-2가 말한 **동어반복 지표 그 자체**다.
- `createTodo`의 `let seq` 모듈 전역 — 리로드 시 리셋. `Date.now()`와 조합해 실질 충돌 확률은 낮다.
- `addTodo`가 `setDraft("")`를 유효성 검사 **앞**에서 호출 — 공백만 입력하고 Enter를 치면 입력창이 비워진다. 계약 위반은 아니고 UX 선택의 문제.

**"프레임워크가 고칠 실패"라고 부를 만한 게 없다.** r2 §3의 5번(베이스라인이 뭘 틀렸는지 수집)이 **빈 결과**이고, r2 §3이 못 박은 순서대로면 **6번을 시작할 수 없다** — "5번이 채워지기 전엔 6번이 뭘 만들지 알 수 없다. 순서를 바꾸면 프레임워크가 추측이 된다."

### 여기서 나온 더 강한 발견

이게 지표 ②가 동어반복인 진짜 이유다. 커버리지 차이는 "처치군이 지시를 따랐다"는 사실만 재고, **그 테스트가 무엇을 막았는지는 영원히 0**이다.

## 4. 부수적으로 알아낸 것 (전부 실측)

### ① 환경 동결은 `--safe-mode` 한 플래그로 끝난다

r2 §3 체크리스트의 `.bak` 이동 5종을 전부 대체했다. 같은 프롬프트 대조에서 safe-mode는 `NONE`, 대조군은 글로벌 CLAUDE.md 본문 + `PONYTAIL MODE ACTIVE` 훅 출력 + 플러그인 스킬 8종을 그대로 뱉었다.

원안보다 **넓고**(output style·workflows·프로젝트 스킬까지) **안전하다** — 파일을 옮기지 않으므로 **복원 실패로 (b)가 자기 프레임워크 없이 도는 사고**가 구조적으로 불가능하다. `--bare`는 더 강하지만 OAuth를 안 읽어 이 머신에서 인증이 성립하지 않는다.

**→ (b)의 프레임워크는 `~\.claude`에 설치하지 않고 `--plugin-dir` / `--settings` / `--agents` 등 세션 한정 플래그로 주입한다.** 그래야 처치가 프롬프트 1줄 + 동결된 자산뿐임이 커맨드라인만 봐도 검증된다. r2 §4-④(배포 형태 미정)의 답도 여기서 절반은 정해진다.

### ② `acceptEdits`만으로는 셸이 통째로 막힌다 — 라운드 하나를 태웠다

첫 R0에서 에이전트가 `npm run test:ac`·`npm run build`·`npx tsc`를 **8번 시도해 8번 거부**당했고, 오라클을 한 번도 실행하지 못한 채 "승인해 달라"며 끝났다.

사전 검증이 이걸 놓친 이유가 더 중요하다. R0 전 확인은 `node --version`으로 했는데 **그건 읽기 전용으로 자동 분류돼 통과하는 커맨드**였고 `npm run …`은 아니었다. **환경 검증은 과제가 실제로 쓸 커맨드로 해야 한다.** 대역으로 하면 라운드를 태운다.

`--allowedTools Bash PowerShell`을 더하면 denials 0. FROZEN §7.2/§7.3에 **`permission_denials` ≠ 0 = 라운드 무효**를 `acRunOk: false`와 같은 급으로 박았다. 양쪽에 똑같이 걸려도 중립이 아니다 — 커맨드를 더 자주 돌리는 처치군이 더 손해다.

### ③ 무효 R0가 남긴 데이터가 오히려 가장 강하다

`exp/runs/void-a-r0-src/`에 산출물을 보존했다. **테스트를 단 한 번도 실행하지 못한 구현이 `8/8` / regression pass.** 오라클 접근이 결과에 아무 영향이 없었다는 뜻이고, §8의 천장 위험에 대한 가장 직접적인 증거다.

### ④ 채점기가 앱 리포의 `git status`를 더럽힌다

`judge.mjs`의 `cpSync`가 `tests/ac/` 두 파일의 mtime을 갱신해 `core.autocrlf=true`와 맞물려 `M`으로 표시된다. `git diff`는 비어 있고 `tampered`도 비어 있으니 내용 변화는 없다. 다만 R1 이후 라운드에서 에이전트가 이걸 보면 **"내가 금지된 파일을 건드렸나"로 읽을 수 있다.** (a)는 R0에서 종료돼 실제 영향은 없었다.

## 5. 모델을 낮춰도 안 깨진다 — 실패는 모델 능력의 함수가 아니다

**선택지 (C)를 실측으로 먼저 죽였다.** 같은 `sent-a-r0.txt`를 시드 사본에 그대로 투입:

| 모델 | gateAC | regression | cost | turns | 벽시계 | 자체 테스트 |
|---|---|---|---|---|---|---|
| Opus 5 | **8/8** | pass | $0.397 | 11 | 92s | 0개 |
| Sonnet 5 | **8/8** | pass | $0.282 | 11 | 60s | 0개 |
| **Haiku 4.5** | **8/8** | pass | **$0.067** | 10 | **54s** | 0개 |

**Haiku 4.5가 6센트·54초에 만점을 낸다.** 모델을 세 단계 낮춰도 실패 지점이 안 생긴다 — 즉 이 과제의 난이도는 **측정 가능한 하한 아래**에 있고, 프레임워크가 겨눌 표적은 모델을 바꿔서는 만들어지지 않는다.

### 그래서 진짜 원인은 이거다 — 설계가 삼각 모순에 갇혀 있다

```
결정론적 Gate를 실행 전에 동결하려면  →  DOM 계약(셀렉터·순서·개수 표기)을 명시해야 하고
DOM 계약 + 동작 요구사항 10개를 주면  →  스펙이 완전해지고
스펙이 완전하면                       →  남는 일은 "읽고 구현하기"뿐이고
                                          그건 Haiku 4.5에게도 54초짜리 일이다
                                     →  프로세스 강제가 개선할 잔여분 = 0
```

r1 §2가 발견한 **"스택 자유와 AC 동결은 논리적으로 양립하지 않는다"와 같은 구조이고, 한 단계 더 근본적이다.** FROZEN §9-1은 이 실험이 "스택이 이미 고정된 조건에서의 프로세스 강제 효과"를 잰다고 적었는데, 실측이 말하는 건 **그 잔여분 자체가 0**이라는 것이다.

**프레임워크의 가치 가설을 잘못 놓았을 가능성이 크다.** 프레임워크가 값을 하는 지점은 "구현 과정을 강제하는 것"이 아니라 **"불완전한 스펙을 완성시키는 것"**인데, 이 실험은 완전한 스펙을 양쪽에 통제변수로 주고 시작해 **재려던 것을 스스로 소거했다.**

## 6. 결정해야 할 것 — 설계를 어디로 트나

### (A) 이대로 결론을 낸다 — 비용 최소

**"완전한 스펙 + 실행 가능한 오라클 + jsdom 난이도에서, 프로세스 강제의 잔여 효과는 0이다 — Haiku 4.5까지 포함해서."** n=1이지만 실측이고, 조사 §7-7 C구역(근거 없는 취향으로 프레임워크를 채우는 것)에 대한 강한 반례다. 비교 수치를 내려면 (b)는 돌려야 하므로 프레임워크 자체는 만들어야 한다.
**단점**: 원래 목표가 "프레임워크를 만든다"에서 "이 조건에선 불필요함을 보였다"로 바뀐다.

### (B) 과제를 갈아엎는다 — 비용 최대

베이스라인이 실패할 만큼 어려운 앱으로 바꾼다. **어제 하루치(AC 설계 + 적대적 검증) 전체 반복**이고, 얼마나 올려야 하는지 모른다 — 다시 천장에 붙거나 양쪽 0점이 될 수 있다. jsdom에서 결정론적으로 잴 수 있는 난이도 상한은 이미 §9-4에서 좁혀져 있다.

### ~~(C) 모델을 낮춘다~~ — **실측으로 사망 (§5)**

### (D) 변경 누적을 더 쌓는다 — 비용 낮음, 기대 낮음

R8, R9로 계속 쌓는다. 4번 해서 4번 다 안 깨졌고 **정지 조건이 없다** — 안 깨지는 걸 확인하는 데 계속 돈을 태우게 된다.

### ★ (E) 스펙을 얇게 한다 — 비용 중간, **어제 작업을 버리지 않는다**

과제도 AC도 그대로 두고 **CONTRACT.md에서 동작 요구사항 산문 10개를 뺀다.** DOM 계약 표(testid 목록)만 남기고, `tests/ac/`를 **열람 금지**로 바꾼다(실행은 허용).

그러면 에이전트는 testid만 알고 나머지를 스스로 추론해야 한다 — 공백 거부, 표시 순서 고정, 영속성 범위, 필터 부분집합의 정의, `todo-count` 텍스트에 숫자 정확히 하나. **AC 9개는 한 글자도 안 고치고 그대로 재사용한다.** 오라클은 여전히 실행 가능하므로 실패 메시지로 좁혀가는 **진짜 TDD 루프**가 되고, 그때 비로소 지표 ①과 ④가 살아난다.

- **왜 이게 맞는 방향인가**: §5의 삼각 모순을 푸는 유일한 지점이 "스펙 완전성"이다. 그리고 프레임워크의 SDD 산출물 강제가 정확히 여기를 겨눈다 — 재려던 걸 되살린다.
- **함정이 아닌 이유**: FROZEN §4가 배제한 "AC를 처치군에만 주는 설계"와 다르다. **양쪽에서 똑같이** 빼므로 스펙 유무 효과가 아니라 처치 효과가 남는다.
- **감수할 것**: 재는 대상이 "프로세스 강제"에서 **"요구사항 추론 + 오라클 수렴"**으로 이동한다. 그리고 열람 금지는 §6대로 강제하지 않고 M3처럼 **관측만** 한다.
- **비용**: CONTRACT.md 축약 + Red-Check 재실행 + (a) 재실행. **(B)의 몇 분의 일이다.**

**권장: (E) → 결과가 무엇이든 (A)의 문장을 같이 싣는다.** (E)가 실패해도(= 얇은 스펙에서도 8/8) 그건 (A)를 더 강하게 만드는 데이터다. 어느 쪽이든 버리는 작업이 없다.

## 7. (E) 실행 결과 — **천장이 깨졌다**

### 7.1 먼저 계측을 고쳐야 했다

`judge.mjs`는 **라운드 끝의 스냅샷**만 본다. 그래서 두 가지를 놓치고 있었다.

1. **(a)는 자체 테스트를 썼다.** R6·R7에서 `scratch/edit.test.tsx`·`scratch/search.test.tsx`를 만들어 5/5로 돌리고 **스스로 지웠다.** M1의 "0개"는 최종 상태만 본 값이라 이 행동을 통째로 놓쳤고, `strayCfg`도 `scratch/vitest.config.ts`를 못 잡았다(루트 파일명만 보므로).
2. **"첫 오라클 실행 시점의 점수"를 잴 수 없었다.** 라운드 안에서 몇 번을 고쳐 8/8이 됐는지가 안 보인다.

→ `exp/logprobe.mjs`를 만들어 세션 로그(`~/.claude/projects/<slug>/<uuid>.jsonl`)에서 뽑는다. **`firstOracle`(오라클을 처음 돌린 순간의 점수), `oracleTrace`, 자체 테스트 작성·삭제 수.** 전부 "무엇이 남았는가"가 아니라 **"무엇을 했는가"**다.

> 이 발견은 결론을 한 번 더 약화시킨다. **"TDD를 강제하면 이득"이라는 가설의 베이스라인이 이미 필요할 때 검증 테스트를 쓴다.** 다만 **회귀 자산으로 남기지 않고 지운다**는 차이는 실재하고, 그건 프레임워크가 겨눌 수 있는 지점이다.

### 7.2 완전 스펙에서는 새 지표도 천장이었다

| 조건 | firstOracle | 오라클 실행 | 자체 테스트 |
|---|---|---|---|
| 완전 스펙 · Opus (R0~R7) | **8/8** | 5회, 전부 8/8 | 2개 작성 → 2개 삭제 |
| 완전 스펙 · Sonnet 5 | **8/8** | 1회 | 0 |
| 완전 스펙 · Haiku 4.5 | **8/8** | 1회 | 0 |

**처음 돌린 그 순간 이미 만점이다.** 지표를 바꾸는 것만으로는 천장이 안 깨진다는 뜻이고, 스펙을 얇게 하는 것과 **같이** 가야 한다.

### 7.3 얇은 스펙 + `firstOracle` → 신호가 나온다

`CONTRACT-thin.md`(testid 표 9줄 + "동작의 세부는 인수 테스트가 정한다", `tests/ac` **열람 금지**·실행 허용) + `prompt-a2.md`. 프롬프트 4,234 → **2,649바이트.**

| | firstOracle | oracleTrace | 최종 gateAC |
|---|---|---|---|
| 완전 스펙 | 8/8 | 8/8 | 8/8 |
| **얇은 스펙** | **6/8** | **6/8 → 8/8** | 8/8 |

**틀린 두 개가 정확히 무엇인지가 이 실험의 핵심 산출물이다:**

- **AC-07 영속성** — `localStorage`를 **아예 만들지 않았다.** `expected [] to deeply equal [ 'A', 'B' ]`
- **AC-08 accessible name** — `placeholder="할 일을 입력하세요"`만 두고 accessible name이 없다. `Unable to find an accessible element with the role "textbox" and name /\S/`

**AC-01~06은 testid 이름만으로 전부 맞췄다** — 추가·공백 거부·토글 왕복·삭제 후 순서 유지·미완료 개수(숫자 유일성 포함)·필터 3종의 언렌더 의미론까지.

### 7.4 그래서 프레임워크가 겨눌 표적이 정해진다

```
추론되는 것    = 기능 동작 (testid 이름에서 복원 가능)
추론 안 되는 것 = 명시되지 않은 비기능 요구 (영속성, 접근성)
```

r2 §3의 5번(**베이스라인이 실제로 뭘 틀렸는지 수집**)이 드디어 채워졌다. 답은 **"스펙에 안 적힌 비기능 요구"**이고, 이건 SDD가 정확히 겨누는 지점이다 — 구현 전에 요구사항을 명시적으로 끌어내는 것. "페이즈 분할"이나 "RED 원문 제출"이 아니라 **여기가** 표적이다.

### 7.5 재현성 — 8/8이 한 번도 안 나온다

> 🔴 **이 절은 정정됐다 → [r4.md](r4.md) §1~2.** 아래 표의 `firstOracle`은 **구현 전 RED 실행을 구현 점수로 오독한다.** 얇은·Haiku의 `0/8`은 스텁 상태에서 돌린 실행이고 그 런의 첫 구현 제출 점수는 `8/8`이다. 1순위 지표는 `firstImplOracle`(= `src/` 쓰기 이후 첫 오라클)로 교체됐고, "얇은 스펙에서 8/8이 한 번도 나오지 않았다"는 **철회**된다(Opus 3/3이 8/8 미만인 것은 유지). 표는 당시 기록이므로 고치지 않는다.

같은 `sent-a2-r0.txt`를 시드 사본에 5회 투입(Opus ×3, Sonnet, Haiku):

| 조건 | 모델 | firstOracle | 확인된 실패 항목 | oracleTrace |
|---|---|---|---|---|
| 완전 | Opus | 8/8 | — | 8/8 ×5 |
| 완전 | Sonnet 5 | 8/8 | — | 8/8 |
| 완전 | Haiku 4.5 | 8/8 | — | 8/8 |
| **얇은** | Opus | **6/8** | **AC-07, AC-08** | 6/8 → 8/8 |
| **얇은** | Opus | **6/8** | **AC-08**(+1, 출력 잘림) | 6/8 → 실행실패 → 8/8 |
| **얇은** | Opus | **7/8** | **AC-07** | 7/8 → 8/8 |
| **얇은** | Sonnet 5 | **6/8** | (출력 잘림) | 6/8 → 6/8 → 8/8 |
| **얇은** | Haiku 4.5 | **0/8** | 전항목 | 0/8 → 0/8 → 8/8 |

**얇은 스펙에서 8/8이 한 번도 나오지 않았고, 완전 스펙에서는 한 번도 8/8 미만이 나오지 않았다.** 지표가 조건을 안정적으로 가른다. 반복 실패 항목은 **AC-07(영속성)과 AC-08(accessible name)**으로 일관된다 — 매번 다른 항목이 튀는 노이즈가 아니다.

전부 최종적으로는 8/8에 도달했다(운영자 피드백 0회, 라운드 내부 자기수정). **그래서 최종 점수는 여전히 무정보이고, 살아난 것은 `firstOracle` 하나다.**

### 7.6 계측의 알려진 한계

실패가 많으면 vitest 출력이 길어져 **tool_result가 잘린다.** 맨 아래 `Tests …` 요약이 통째로 사라지므로 `logprobe.mjs`는 위쪽 파일 요약 줄(`(8 tests | 2 failed)`)을 우선 본다. 그래도 앞부분이 잘리는 경우가 있어 **실패 *항목*은 일부 실행에서 복원되지 않는다**(점수는 복원된다). 위 표의 "출력 잘림"이 그 경우다.

### 7.7 그런데 프레임워크가 이 표적을 겨눌 때 오염 함정이 있다

표적은 "명시되지 않은 비기능 요구를 구현 전에 끌어내라"다. 그런데 **§0은 프레임워크 자산이 도메인 무관할 것을 요구한다.** 스킬·프롬프트에 "영속성과 접근성을 확인하라"고 적는 순간, 그건 **AC를 이미 읽고 쓴 사람의 정답 유출**이고 (b)는 구조적으로 이긴다 — §0이 "Todo·계약 냄새가 한 줄만 섞여도"라고 경고한 바로 그 오염이다.

**따라서 (b)의 프레임워크는 "비기능 요구를 일반적으로 열거하게 만드는 절차"까지만 쓸 수 있고, 무엇을 열거할지는 못 적는다.** 이 제약을 지킨 상태에서 `firstOracle`이 올라가면 그게 진짜 프레임워크 효과다.
