# r46 — KF4 R1+R2: SG 번호 룰셋 + `specgate.mjs` 단일 CLI

계획서 `docs/next/2026-08-19/plankf4ruleset.md` §5 WBS의 **R1·R2**. KF1·KF2·KF3가 2026-08-21로
전부 종료돼 §8의 착수 조건(«룰 목록 안정 뒤» — planmain §10-1 기본값)이 충족됐다.
**R3(delta·drift 서브커맨드 + A 블록)은 안 열었고, R4(volume·interview)는 KF5 부재로 못 연다.**

## 0. 왜 R1만으로 끊지 않았나

R1(=`specgate.mjs` 신설)만 하면 사람이 치는 CLI만 바뀌고 **훅 stderr는 옛 산문 그대로**다.
KF4의 원 요청은 «게이트 실패가 에이전트에게 이해 가능한 형태가 아니면 자기수정 루프가 안 돈다»이므로,
에이전트가 실제로 보는 면이 안 바뀌면 이 라운드는 아무것도 안 한 것이 된다. R2까지가 «돌아가는
한 조각»의 최소 단위다(사용자 확정).

  ↳ 그 `선택 대기` 항목을 재확인 목록에 올린다

`spec-anchor` 15건 · `spec-gate` 23건). 실물 2장(`sd1` exit 1 · `i1` exit 0)은 exit가 `spec-verify`와 같다.

## 2. 계획서와 달라진 4건 (실측이 전제를 바꿨다)

1. **`RULES`에서 심각도를 뺐다.** 계획서 §4-2는 `{id, sev, hint}`였는데, 심각도는 finding이
   `violations`에 있었나 `warnings`에 있었나로 **항상** 정해진다. 표에 또 적으면 어느 쪽이 참인지
   갈리는 자리만 생긴다. 계획서 비목표(«심각도는 각 검사기의 현행 위반/경고 구분을 그대로 옮긴다»)와
   같은 뜻이다.
2. **매핑 키를 `kind ?? check`로 했다.** `spec-delta`의 D1~D5, `spec-anchor`의 A1~A4는 `check`
   하나가 룰 하나에 1:1이라 kind가 필요 없다. C 블록만 한 check에 여러 kind가 붙는다(C2→3 · C4→3 ·
   C5→3). 덕분에 **`spec-delta.mjs`·`spec-anchor.mjs`·`specprobe.mjs`를 한 글자도 안 고쳤다.**
3. **D 블록(SG1011~1015)을 R3에서 R2로 당겼다.** 훅이 델타 위반을 stderr로 낸다(pre D1·D2 /
   stop D1~D5). 등재하지 않으면 개정된 훅이 델타 차단에서 `SG----`를 뱉는다 — 소비자가 이 라운드에
   있으니 표 5행도 이 라운드다.
4. **동적 import·«도구 미도입 안내»·T11을 만들지 않았다.** 계획서 §4-1은 KF4가 KF1·KF3보다 먼저
   착수될 경우를 대비했는데 둘 다 실재하고, 플러그인 루트가 `framework/` 전체라(README 선택 대기 #3)
   셋이 항상 같이 배포된다. 「일어날 수 없는 상황에 대한 에러 처리」다. R3에서 정적 import로 간다.

## 3. 기대값을 고친 2건 (판정 축은 불변)

계획서 §6은 «기대값을 고쳐야 통과하면 멈추고 원인을 가른다»고 했다. 둘 다 판정(exit)은 한 건도
바뀌지 않았고, 바뀐 것은 이 라운드가 **의도해서 바꾼 stderr 계약**이다.

1. **`spec-gate --selftest`의 `said('D1')` → `said('SG1011')`** (4곳: D1·D2·D4·D5).
   델타 케이스 4건이 stderr 문구를 단언하는데, 개정 후 stderr에는 `[D1]`이 없고 `SG1011`이 있다.
   exit는 23건 전부 그대로였다(실패 사유가 전부 «stderr가 D…을 말하지 않았다»였다).
   바꾼 결과 이 단언은 **룰 매핑까지 함께 검사**하게 됐다 — 이전보다 강해졌다.
2. **계획서 T6의 `SG1004` → `SG1005`.** F3의 Error는 SG1004가 아니라 SG1005 8건이다(실측).
   재는 것은 그대로 «Error mute 시도가 무시되는가»다.

## 4. 계획서에 없던 것 2건

1. **SG1027 자리를 열었다(R3에서 등재).** 계획서 §4-2 배정표는 `spec-anchor`의 A1~A3(SG1021~1023)과
   drift 3범주(SG1024~1026)만 실었는데, 실물에는 **A4 경고가 3종 있다**(델타 읽기 실패 · 앵커에만
   있는 문장 · SPEC에만 있는 지목). 그대로 두면 R3에서 T3(«`SG----` 0건»)가 깨진다. 사용자가
   SG1000과 함께 신설로 확정했다.
2. **T3b — 매핑 전수성을 정적으로 잡는다.** 픽스처 6장이 밟는 kind는 4종뿐이라(C5.miss ·
   C4.vague · C4.noId · C5.numericId) 런타임 대조로는 전수가 안 나온다. 소스에서 kind 리터럴을
   직접 뽑아 `RULES`와 대조하는 케이스를 더했고, 인라인 SPEC 2장(T14 혼합 ID · T15 빈 SPEC)이
   4종을 더 밟는다. 남은 5종(C2.missingCat · C2.badLiteral · C3.badCols · C3.pendingLost ·
   C4.miss)은 T3b만 커버한다.

## 5. 한계 (병기 의무 — 계획서 §9 8항이 전부 유효하다)

1. **검출력은 1도 늘지 않았다.** C4·C5가 재는 것은 «ID를 다시 적었는가»뿐이고(빈 셀·«구현 안 함»
   통과 — README·r36 §9-2), SG1004·SG1005로 이름이 바뀌어도 그대로다. 그 한계를 깎는 것은 KF3의 몫이다.
2. **자기수정 루프가 도는지는 여전히 미실측이다**(조사 Q1). 확인된 것은 «차단이 작동한다»($0.36
   프로브)까지고, 그때의 되묻기도 stderr가 아니라 **훅 소스를 읽어 C1~C5를 재구성**한 데서 왔다
   (r37 §3). 이 라운드가 만든 것은 **형태**이고, 효과는 실사용 2회차 관측 항목이다
   (`.specgate-log.jsonl`의 같은 룰 반복 차단 — 이제 `rules` 필드로 판독 가능하다).
3. **«한 줄 포맷이 산문보다 잘 소비된다»도 실측된 적 없는 가정이다.** 훅 stderr는 finding당 힌트
   1줄만큼 길어졌다(룰당 정적 1줄 상한).
4. **정적 힌트는 상황을 모른다.** «이 프로젝트의 이 문장을 어떻게 고칠지»는 담지 못한다. 상황별
   안내에는 LLM이 필요하고 차단 경로에 넣지 않는다(개발 규칙 5).
5. **mute는 Warning 전용이라 오차단의 탈출구가 아니다.** 조치는 FIELD-GUIDE §2대로 `SRC`·`PRE`
   조정이다. Error mute 불가가 내는 마찰은 관측 대상이다(계획서 §10-3 번복 조건).
6. C2.none·C3.none은 메시지(«없다»)와 힌트(«만들어라»)가 거의 같은 말이다 — 힌트가 값을 하는 것은
   C4·C5·C2.badLiteral처럼 «무엇을 어디에» 쓸지가 메시지에 없는 룰이다.
