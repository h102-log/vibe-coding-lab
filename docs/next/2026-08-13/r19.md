## 1. 만드는 것

`framework/skills/sdd/SKILL.md` — 신규 파일 1개.

- **시드**: `exp/fw/skills/spec/SKILL.md`(39줄)의 §1(명시된 것)·§2(명시되지 않은 것)·§3(완료 전
  대조). §4는 이미 tdd 스킬로 분리됐다. exp/는 동결 — **읽고 옮겨 적기만, 원본 무변경**.
- **frontmatter**: `name: sdd` + description 신규 작성(발동 조건 포함 — tdd 선례). 설치형
  트리거의 실효 확인은 4단계 유지(r16 §3-4).
- **금지**: 문안에 tdd·edd·테스트·평가 파일 언급 금지 — 축 연결은 산출물 파일(`SPEC.md`) 존재로만
  한다(r16 §1). sdd는 SPEC.md를 **만드는** 쪽이라 다른 축 산출물을 참조할 일 자체가 없어야 한다.

## 2. 작업 — §2 개정 3건 (r16 §3-2, 재료는 REPORT4 §6)

1. **겨냥 확장 — 요청 모호성.** §2의 탐색 세 방향(문장의 추가 전제·흐름의 갈림길·범위 밖이라
   명시되지 않은 것)에 네 번째 방향을 더한다: **사용자 요청 문장 자체의 해석이 갈리는 지점.**
   근거: 실사용 사건 Q 2건의 발원지는 «구현 결정의 침묵»이 아니라 «요청 문장의 해석»이었다
   (REPORT4 §6-3).
2. **재고 선구현 차단.** §2의 기각·보류 항목에 번복 조건을 문장으로 박는다 — **«사용 중 계기가
   생기기 전에는 구현하지 않는다»**. 근거: 실사용 번복 5건 전부 계기가 «생각나서»/에이전트 제안
   승인이었고(REPORT4 §6-1), U97은 계기만 사용이었다면 R 적중이었다(§6-2 — §2가 결정 지점을
   미리 적는 능력 자체는 이 한 건이 보여줬다).
3. **우선순위 — 열거가 아니라 선별.** «어느 침묵이 비싼가»를 고르게 만드는 문안. 근거: 116문장
   중 사건 적중 1건, 공회전 99%(REPORT4 §1·§3) — 침묵 지점을 찾으라는 지시만으로는 선별이 안
   된다. **구체 문장은 그 세션에서 짓는다**(r16 방침 그대로) — 방향 후보만 적어 두면: «각 항목에
   틀렸을 때의 비용(재작업 범위)을 달고, 비싼 것부터 확정한다» 류. 실효는 실사용 2회차가 잰다 —
   스모크는 형식 도달만 본다(§4).

**알고 유지하는 한계 2건** (r16 §3-2 그대로, 문안으로 풀지 않는다): §3 대조는 구현 존재만 확인
하고 테스트 커버리지·자기 커밋의 번복(REPORT4 §6-5)은 못 잡는다 — tdd·edd의 몫. SPEC 선커밋
규칙은 넣지 않는다 — 실사용 9번 중 1번 준수(REPORT4 §6-4), 훅 없는 v0.1엔 강제 수단이 없다.

## 3. 검증 — 스모크 1런 (r16 §4 원칙: 실험 아님, n=1, 효과 주장 금지)

### 과제 설계

- **디렉터리**: `framework/smoke/s4-sdd/` — `exp/seed/` 사본, s2b-dom과 동일 조정(r18 §3-1:
  `node_modules`·`tests/` 제외, `test:ac` 제거, App.tsx 문구 중립화, name 변경). DOM 조건(주
  용도)으로 간다 — 1단계 재점검이 DOM 과제를 검증 조건으로 확립했다.
- **프롬프트** `sent-s4.txt`: 소규모 UI 과제에 **일부러 불완전한 요구**를 준다. 설계 규칙:
  1. **모호 문장 1개 이상을 의도적으로 심는다** — 해석이 갈리는 요청 문장(개정 1의 표적).
  2. **침묵 지점(정해 주지 않은 구현 결정)을 2곳 이상 남긴다** — §2 원래 표적.
  3. **심은 지점의 목록을 런 전에 그 세션 rN에 적는다** — 판정이 사후 합리화가 되지 않게
     (사전 등록의 축소 유사물, 동결은 아님).
  4. sdd **단독 주입** — tdd 스킬 없이(단독 모드 검증, 1단계 선례). «테스트하라»류 동사 금지는
     여기도 적용(과제문이 처치 역할을 뺏으면 안 된다).

### 판정 기준 (r16 §3-2의 ①②를 구체화)

- **①** 구현 시작 전에 `SPEC.md`가 생성되고 §1(근거 위치)·§2(`[추론]`/`[MISSING]`) 구조를 갖춘다
  — 생성 시점은 세션 로그로 확인.
- **②** §2에 `[추론]` 또는 `[MISSING]` 항목이 1개 이상 있고, 심어둔 침묵 지점 중 최소 1곳을
  가리킨다.
- **③** 심어둔 **모호 문장**이 §2(또는 개정 1이 만든 자리)에 잡힌다 — 개정 1의 도달 확인.
- 개정 2(번복 조건)·개정 3(선별)은 단일 런으로 실효 판정 불가 — **형식 도달만 관찰**(문안이
  지시한 표기가 SPEC에 나타나는가). 실효는 실사용 2회차 몫임을 판정문에 명시.

### 무효·실패 구분 (r18 §3-3의 교훈을 sdd에 맞게)

tdd와 달리 sdd는 **무조건 지시**다(«코드를 쓰기 전에 SPEC.md를 쓴다» — 조건부 «만들어 돌렸다면»이
아니다). 따라서 **SPEC.md 미생성은 무효 스모크가 아니라 기준 ① 실패**(문안 불이행 — D급 재료)다.
무효는 계측 실패뿐: `is_error`·`permission_denials` 비어있지 않음. 무효 재실행은 새 디렉터리
(`s4b-sdd/`), 런은 전경 단독 실행(r18 §3 교훈 그대로).

### 실행 역학 (1단계와 동일)

```bash
# cwd = framework/smoke/s4-sdd (절대경로로 cd), UUID는 node crypto.randomUUID
cat ../runs/sent-s4.txt | claude -p \
  --safe-mode --model opus --effort xhigh \
  --permission-mode acceptEdits --allowedTools Bash PowerShell \
  --append-system-prompt "$(cat ../../skills/sdd/SKILL.md)" \
  --session-id <새 UUID> --output-format json > ../runs/s4-sdd.json 2> ../runs/s4-sdd.stderr.txt
```

logprobe는 sdd 판정엔 테스트 지표뿐이라 부분 유효 — SPEC 생성 시점·심은 지점 포착은 세션
jsonl을 직접 읽는다(슬러그 `C--Users-bhy99-proj-proj3-framework-smoke-s4-sdd`).

**비용 어림**: s2b 실측 $0.71 + SPEC 작성 분량 → 1런 $1~2. 무효 재실행 포함 상한 $4.
