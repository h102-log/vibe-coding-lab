# 프레임워크 v0.1 계획 — 단계 구축: tdd → sdd → edd → 통합 — r16

**상태**: 계획 확정 단계. 다섯 트랙 종료(r15) → 관측은 여기까지, 프레임워크 제작으로 전환.
**이전**: [r15.md](../2026-08-12/r15.md) — §2의 «프레임워크 v0.1 설계 착수» 스케치를 이 문서가 대체한다.
**이 판(v2)**: 같은 세션에서 재작성. v1은 3축을 한 번에 설계하는 그림이었으나, **한 축씩 만들어
검증하고 마지막에 합치는 단계 구축**으로 바꾼다 — 순서는 tdd → sdd → edd → 통합.
EDD(Eval-Driven Development, 평가 주도 개발) 축 추가는 v1과 같다. v1 대비 정정 1건: 흡수 관측의
1차 출처를 REPORT2가 아니라 `exp/FROZEN.md` §8로 바로잡았다 (§5-1).

---

## 1. 모드 체계

축은 3개(sdd·tdd·edd)이고 각 축은 켜고 끄기만 한다. 공집합을 빼면 조합은 **2³−1 = 7개**
— 단독 3 + 2축 조합 3 + `full` 1. 모드 이름은 별도 개념이 아니라 켠 축 집합의 표기다.

구현도 그렇게 간다: **축 = 스킬 1개, 조합 = 켠 스킬의 집합.** 모드 설정값·플래그를 만들지
않으면 7조합이 공짜로 나온다. 스킬끼리는 서로를 참조하지 않고, **상대 축의 산출물 파일이
존재하는가**(`SPEC.md`·평가 파일)로만 연결한다 — sdd가 꺼져 있으면 tdd·edd 문안의 해당
조건문이 자연히 죽는 구조 (§3의 각 단계에서 구체화).

## 2. 구축 순서와 근거 — 왜 tdd부터인가

| 순서 | 축 | 순서 근거 |
|---|---|---|
| 1 | tdd | 문안이 가장 작고(원문 4줄) 효과·자산 생명주기의 실측 근거가 가장 직접적(mutation 3/4 ×3 · 회수 3/3). 산출물(테스트 파일)이 그 자체로 확인 가능해 다른 축 없이 스모크 검증이 된다. |
| 2 | sdd | 문안은 있으나(38줄 중 §1~§3) **§2 개정이 필요** — 개정 재료 2건이 REPORT4 §6에 준비돼 있다. tdd보다 작업량이 많다. |
| 3 | edd | 문안이 **없다**(신규 작성). 원형은 처치가 아니라 실험 장치(동결 AC + judge)라 이식 설계가 필요하다. 가장 무거워서 마지막. |
| 4 | 통합 | 산출물 파일 기반 연결 확인 + full 스모크 + 설치형 트리거 확인. |

**정직한 한계 하나**: tdd «단독» 효과는 실측된 적이 없다. REPORT2 §5.1-2가 사전 등록했듯
«§4만 있고 SDD 없는» 실험 조건은 성립하지 않아(계약에 안 적힌 요구는 테스트로 못 쓴다),
3/4는 전부 SDD 위에서 잰 값이다. tdd를 먼저 만드는 이유는 단독 효과가 증명돼서가 아니라
**문안·검증이 가장 가볍기 때문**이고, 단독 모드의 실효는 실사용에서만 관측된다.

## 3. 단계별 계획

각 단계는 «산출물 → 결정 사항 → 검증»으로 닫는다. 검증의 공통 형식은 §4(스모크 원칙).

### 1단계 — tdd 스킬 (`framework/skills/tdd/SKILL.md`)

**시드**: exp2 원문 §4 4줄(42~43행 지시 2문장)만. **실험 4의 강화 2줄(«하나도 빠짐없이
옮긴다…»)은 제외한다** — 중앙값 3/4 그대로에 비용 ×1.21로, 사전 등록 문장대로 «문안 개정의
상한 관측»이었다(REPORT5 §1·§3). 반론도 기록해 둔다: (e)는 케이스 수가 뚜렷이 늘었고(20·28·20
→ 44·36·58) 탈출구 문장 3/3 이행이라 문서화 가치는 있었다 — 그래도 잰 지표가 안 움직였으므로
v0.1은 뺀다.

**작업(문안 수정 3건)** — 시드는 사본이므로 동결과 무관:
1. **참조 내부화**: 원문 «1·2번의 문장»(exp2판 43행)은 SPEC의 §1·§2 목록을 가리켜 sdd가
   꺼지면 지시 대상이 공중에 뜬다. 대체 문안 방향:
   «그 테스트가 지키는 요구를 테스트 파일 안에 적는다. `SPEC.md`가 있으면 그 문장을 지목한다»
   — 한 문장으로 단독·조합 모드를 다 처리하고, 통합 단계에서 따로 할 일이 없어진다.
2. **자기 설명적 파일명 지시 1줄**: 회수 실측에서 발견 경로가 «디렉터리 훑기 + 자기 설명적
   파일명»이었고 package.json 스크립트는 필요조건이 아니었다(REPORT3 §1.1). tdd 단독 모드는
   SPEC.md 인덱스가 없으므로 파일명이 유일한 회수 경로다.
3. **이식성 1줄 (신규·미실측)**: mtime·시계·네트워크 등 환경에 의존하는 단언 금지 — S-14가
   보여준 «자산으로 남으면 회수 시점에 오탐 내는 테스트» 유형 차단(REPORT5 §5-3·§6).

**검증**: 스모크 1런 — 스크래치 앱에 tdd 스킬만 주입, ① 테스트 파일이 남고 ② 파일 안에 지키는
요구가 적혔고 ③ 환경 의존 단언이 없는지 육안 확인. SPEC.md 없는 조건이 곧 단독 모드 검증이다.
문안 검토(1단계 실행 중) 반영 결정 1건: 처치의 조건부(«만들어 돌렸다면»)는 실측 원문이므로
테스트 생성을 강제하는 문장을 **넣지 않는다**. 대신 과제를 자체 테스트를 자연 유도하는 것으로
고르고, **테스트 0개 런은 기준 ①을 검증하지 못한 무효 스모크로 기록하고 재실행한다.**

**결과 (2026-08-13, 이 세션): 통과.** 스모크 1런($0.40 · 10턴 · 90초 · denials 0, 과제:
textkit 3함수): ① 테스트 3파일 18케이스가 남았고 전부 통과(빌드 0) ② 파일마다 헤더 주석에
지키는 요구를 인용 — 에이전트가 «이 저장소에는 SPEC.md가 없어 과제 명세문을 그대로 인용한다»고
스스로 적어 **참조 내부화의 조건 분기가 단독 모드에서 의도대로 작동** ③ 환경 의존 단언
0건(Date.now·mtime·random·fetch류 grep). 파일명 3개 전부 자기 설명적. 원문
`framework/smoke/runs/s1-tdd.json`.

### 2단계 — sdd 스킬 (`framework/skills/sdd/SKILL.md`)

**시드**: exp 원문 §1(명시된 것)·§2(침묵 지점)·§3(완료 전 대조). §4는 이제 tdd 스킬로 분리됐다.

**작업(§2 개정 3건)** — 표적은 «어느 침묵이 비싼지 고르게 만드는 문안»(REPORT4 §1 사전 등록·§7),
그 문안이 겨눌 두 지점은 §6-1(재고 선구현)·§6-3(요청 모호성)이다:
1. **겨냥 확장 — 요청 모호성**: 실사용 사건 Q 2건의 발원지는 §2가 겨눈 «구현 결정의 침묵»이
   아니라 «사용자 요청 문장의 해석이 갈리는 지점»이었다(REPORT4 §6-3). §2에 이 방향을 추가한다.
2. **재고 선구현 차단**: §2 재고는 사건이 되기 전에 «생각나서» 선구현으로 소진됐다 — 번복
   5건 전부 사용 계기 없음(REPORT4 §6-1). 기각·보류 항목의 번복 조건(사용 중 계기)을 문안에
   명시한다.
3. **우선순위 — 어느 침묵이 비싼가**: 116문장 중 사건 적중 1건(specHit 1/4), «침묵 지점을
   찾으라는 지시만으로는 어느 침묵이 비싼지 고르지 못한다»(REPORT4 §1 사전 등록 문장). 열거가
   아니라 선별을 시키는 문안이 필요하다 — 구체 문안은 이 단계에서 짓고, 실효는 실사용 2회차가 잰다.

**알고 유지하는 한계 2건**(문안으로 안 풀리는 것): §3 대조는 구현 존재만 확인하고 테스트
커버리지(REPORT2 §1.1 todo-dc)·자기 커밋의 번복(REPORT4 §6-5)은 못 잡는다 — 보완은 tdd·edd의
몫이다. SPEC 선커밋 규칙은 실사용에서 9번 중 1번만 지켜졌다(REPORT4 §6-4) — 훅 없는 v0.1은
강제 수단이 없으므로 규칙으로 넣지 않는다.

**검증**: 스모크 1런 — **일부러 불완전한 요구**를 주고 ① SPEC.md §2에 `[추론]`·`[MISSING]`
항목이 생기고 ② 요청 문장의 모호성 항목이 잡히는지 확인.

### 3단계 — edd 스킬 (`framework/skills/edd/SKILL.md`)

**시드 없음 — 신규 작성.** 원형은 실험 장치다: 동결 AC + `judge.mjs`는 다섯 트랙 내내 가장
강한 장치였다(gateAC 네 조건 연속 8/8 · 변경 요구 4회 회귀 0). 단 실험에는 실험자가 있었고
프레임워크에는 없다 — **[가정] 에이전트가 스펙에서 평가를 도출·동결하고 사용자가 승인**하는
형태로 잡는다 (v1과 동일, 사용자 확인 대기 — §7-2).

**문안 최소형(4요소)**:
1. 구현 전에 판정 가능한 평가 항목을 파일로 확정한다 — 스펙이 있으면 §1·§2 문장에서 도출.
2. **Red-Check 이식**: 구현 전에 평가를 실행해 실패를 확인한다 — 평가가 구현을 재고 있다는
   검증(FROZEN2 §2 «AC가 구현을 재고 있다»의 이중 장치 중 이식 가능한 쪽).
3. 완료 선언 전에 평가를 실행한다. 전 항목 통과 또는 항목별 기각 사유 — 둘 전에는 완료가 아니다.
4. **자기 손질 차단**: 평가 파일은 구현 시작 전에 커밋하고, 구현과 같은 커밋에서 수정하지
   않는다 — 동결의 목적은 «잡을 만한 것만 남기는 사후 손질» 차단이다(FROZEN2 §0.4의 정신).
   실험의 해시+채점 시점 복원 수준까지 갈지는 미결(§7-3).

**judge에서 이식하는 판정 규율**: 평가 실행 자체가 깨진 것(계측 실패 — acRunOk 상당)과 평가
실패(산출물 결함)를 구분한다. 전자는 무효, 후자만 «고치거나 기각»의 대상.

**실행 형태의 하드 제약**(재검토 금지, CLAUDE.md): vitest + jsdom + `tsc -b` + `vite build`만.
E2E·네이티브 린터 불가. jsdom엔 레이아웃이 없어 가시성 판정 불가. 그리고 **사전 명세 가능한
항목만 평가 자격이 있다** — axe 전체 스캔이 빠지고 개별 규칙(accessible name)만 AC-08로 올라간
전례가 자격 조건을 보여준다(exp/FROZEN.md §4).

**검증**: 스모크 1런 — ① 평가 파일이 구현 전에 생기고(커밋 순서로 확인) ② Red-Check가 실행됐고
③ 완료 전 실행이 통과했는지 확인.

### 4단계 — 통합

1. **조합 연결 확인**: 스킬 간 직접 참조가 없는지, 산출물 파일 존재 조건문이 각 조합에서
   올바르게 죽고 사는지 문안 검토. (1단계 참조 내부화가 제대로 됐으면 여기서 할 일이 거의 없다.)
2. **full 스모크 1런**: 3축 주입, 산출물 4종(SPEC.md·테스트·평가 파일·구현)이 순서대로 나오는지.
3. **설치형 트리거 확인**: 실험·스모크는 전부 `--append-system-prompt` 주입이었다. 실제 배포
   형태(`.claude/skills` 설치)에서 description으로 발동하는지는 **리포 밖 스크래치 프로젝트**에서
   확인한다 — 이 리포에 설치하면 실험자 세션 오염(CLAUDE.md 하네스 절). 확인 항목(1단계 문안
   검토 지적): ① 테스트를 만든 직후(작업 중간)에 발동하는가 — 완료 시점에야 발동하면 중간
   삭제를 못 막는다 ② «TDD로 해줘» 류 요청의 과발동이 무해한가.
4. `framework/README.md` — 조합 안내(어떤 상황에 어떤 축을 끄는가, §5의 근거 요약).

## 4. 스모크 원칙 — 스모크는 실험이 아니다

동결·채점·n·사전 등록이 없다. 묻는 것은 «문안이 도달해 지시된 산출물이 나오는가»뿐이고,
품질·효과 주장은 하지 않는다 — **실효 검증은 실사용 2회차가 전담한다** (§2를 통제 실험으로
못 재는 삼각 모순은 그대로다: 채점하려면 계약을 줘야 하고, 계약을 주면 §2가 할 일이 사라진다
— r8 §1·r13 §1). 실행 역학은 실측 검증된 런 방식 그대로: Git Bash · stdin 프롬프트 ·
`--append-system-prompt` 주입. 스크래치 앱은 `framework/smoke/`(신규 디렉터리, exp* 불변).
라운드당 비용은 실험 실측 기준 $2~3대 — 4단계 합쳐 $10 안팎.

## 5. 알려진 상호작용 — 조합은 가산적이지 않다 (v1 유지·출처 정정)

1. **edd가 tdd를 흡수한다.** 1차 관측은 실험 1의 «AC가 회귀 안전망까지 흡수한다» 절:
   «(a)는 5라운드 내내 자체 테스트 0개로 갔는데 아무 손해도 보지 않았다 … 처치군이 테스트를
   더 써도 **이 설계 안에서는** 잴 수 있는 이득이 남지 않는다»(`exp/FROZEN.md` §8 — v1이
   REPORT2로 잘못 인용했던 것). 한정어에 주의 — 실험 설계 안의 관측이지 일반 명제가 아니다.
   REPORT2는 이 전제를
   mutationScore에서 AC를 제외하는 설계로 구현했다(FROZEN2 §4.2). `full`에서 tdd가 죽은
   무게일 가설과, 산출물 수준 평가가 못 잡는 세밀한 회귀를 tdd 자산이 잡는다는 상보 가설이
   공존한다 — v0.1은 판정하지 않고 끄고 켤 수 있게만 둔다.
2. **sdd 없이 edd는 상한이 낮다.** 사전 동결 게이트를 만들려면 침묵 지점이 먼저 문장이 돼야
   한다(삼각 모순의 역방향). §2의 산출이 곧 edd 평가 항목의 재료 — `sdd+edd`가 가치 가설
   («불완전한 스펙 완성 → 게이트로 고정»)의 핵심 조합인 이유.
3. **스펙이 완전하면 sdd는 무의미하다.** 완전 스펙 조건에서 잔여 효과 0(베이스라인이 R0 8/8,
   Haiku 4.5까지 8/8 — REPORT §3.1·r3 §5). 완전한 계약을 들고 오는 사용자는 sdd를 끄는 게 맞다.
4. **tdd는 자산 생명주기가 닫힌 유일한 축이다**(생성 3/4 → 회수·확장 3/3 · 삭제 0, 한계 비용
   7~16%). 단 «사고를 막았다»는 데이터는 여전히 0(REPORT3 §3.1 — 잡을 회귀가 안 났다).
