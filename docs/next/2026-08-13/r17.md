## 1. 왜 재점검인가 — 스모크 1런(s1)이 못 본 것

s1은 r16의 판정 기준 3건을 통과했지만(테스트 3파일 18케이스 잔존·요구 인용·환경 의존 0건,
`framework/smoke/runs/s1-tdd.json`), 다음 네 가지를 보지 못했다.

1. **대조군 부재.** 과제(textkit 3함수)가 엣지 케이스를 명시한 순수 함수라 **스킬 없이도
   테스트가 남았을 수 있다.** 실측 참고치: 처치 없이 테스트를 만든 런은 exp2에서 1/6이었고,
   exp3 (b)는 3/3이 만들었다가 **지웠다**. s1의 «남았다»가 스킬 효과인지 과제 성격인지
   분리되지 않았다 — 스모크 판정 기준 ①의 정보량 점검이 필요하다.
2. **과제 편향.** 주 용도(웹사이트 제작 — 메모리 «구상 5요소»)와 달리 DOM이 없는 과제였다.
   실측된 처치 효과는 전부 React+jsdom 조건에서 나왔다.
3. **회수 미확인.** «남는다»까지만 봤다. SPEC.md 없는 단독 조건에서 **새 세션이 자산을
   회수하는지**는 REPORT3도 못 쟀다(3/3 전부 SPEC.md 있는 산출물, 파일명 기반 발견은 간접
   단서 — REPORT3 §1.1·§1.2). s1 산출물은 SPEC 없는 최초의 tdd 산출물이라 이걸 볼 수 있는
   첫 기회다.
4. **검토 유예 2건 재확인.** 1단계 문안 검토에서 4단계로 유예한 것 — ① 설치형 발동 시점
   (테스트 생성 직후인가) ② `name: tdd` 과발동(«TDD로 해줘» 류). 재점검 결과에 따라 유예
   유지가 타당한지만 판단한다(설치형 실측 자체는 4단계 유지).

## 2. 점검 절차 (권장 순서, 전부 스모크 = 실험 아님)

r16 §4의 스모크 원칙이 그대로 적용된다: n=1 신호일 뿐 효과 주장은 하지 않고, 동결·채점 없이
«문안이 도달해 지시된 산출물이 나오는가»만 본다. 실행 역학 동일(Git Bash·stdin·주입).

### A. 대조 런 (s1-ctrl) — 판정 기준의 정보량 점검

같은 과제·같은 조건에서 **스킬 주입 없이** 1런:

```bash
# 준비: s1-ctrl/ 신설 — s1-tdd에서 package.json·package-lock.json·tsconfig.json만 복사 후
# npm install. (s1의 세션 로그 검증 결과 에이전트는 이 설정 파일들을 안 건드렸다 — 시드로 유효)
cd framework/smoke/s1-ctrl && cat ../runs/sent-s1.txt | claude -p \
  --safe-mode --model opus --effort xhigh \
  --permission-mode acceptEdits --allowedTools Bash PowerShell \
  --session-id <새 UUID> \
  --output-format json > ../runs/s1-ctrl.json 2> ../runs/s1-ctrl.stderr.txt
```

- 해석: 대조 런에도 테스트가 남으면 **이 과제는 기준 ①을 판별하지 못한다** → 과제를 덜
  유도적인 것으로 바꿔 s1을 재실행할지 판단. 대조 런이 안 남기거나 만들고 지우면 s1의
  잔존은 **과제 성격만으로는 설명되지 않는다(기준 ①은 정보를 담는다)** — 거기까지만 말한다.
- 주의: 효과 주장 금지(r16 §4 그대로) — n=1끼리의 비교가 말할 수 있는 것은 판정 기준의
  정보량뿐이다.
- «안 만듦»과 «만들고 지움»(exp3 (b) 패턴)은 종료 상태 파일로 구분이 안 된다 — 세션 로그로
  판별한다. `--session-id`를 준 이유이고, logprobe를 쓰면 cwd 슬러그를 반드시 맞춘다:
  `node exp3/logprobe.mjs <UUID> C--Users-bhy99-proj-proj3-framework-smoke-s1-ctrl`

### B. DOM 과제 런 (s2) — 주 용도 조건

React+vitest+jsdom 스캐폴드에서 소규모 UI 과제 1런, 기준 ①②③ 재판정.

- 스캐폴드는 실측 검증된 스택 그대로(`exp/seed/` **사본** — exp*는 불변). 과제는
  todo 계약이 아닌 새 소품(예: 태그 입력 컴포넌트)으로 — 동결 계약 재사용은 해석만 흐린다.
- 추가 관찰(판정 기준 아님): Testing Library 쿼리 종류 — 실측에서 접근성 쿼리가 사실상
  0건이었던 지점(exp2 3런 0건, exp4 3런 0/0·0/0·0/1 — REPORT5 §4-1)이라, 여기서도 그런지
  기록만 해 둔다(문안 개정 근거 아님, §2 축의 재료).

### C. 회수 런 (s3) — 새 세션 투입

**실행 전에 s1 산출물을 먼저 커밋(최소한 사본 백업)한다** — C는 `s1-tdd/`를 제자리에서
변경하므로, 미커밋 상태로 실행하면 «SPEC 없는 최초의 tdd 산출물» 원본이 소실되고 복구
경로가 없다(절대 규칙 6의 취지).

s1 산출물에 변경 요구 1건을 **새 세션**으로 투입(REPORT3 R1 방식 축소판, `--resume` 금지,
새 `--session-id`). 예: «truncate에 말줄임표 문자열을 인자로 받는 오버로드 추가». 실행
역학은 A와 동일하되 **tdd 스킬을 주입한다**(`--append-system-prompt "$(cat
../../skills/tdd/SKILL.md)"`).

- 보는 것: 기존 테스트 3파일을 찾아 돌리는가 / 같은 파일을 확장하는가 / 지우는가.
- SPEC.md 없는 회수의 최초 관찰 지점이다(§1-3).

### D. 문안 재독

A~C에서 SKILL.md를 고칠 필요가 나왔는지 판단. 수정하면 해당 스모크를 재실행하고 r16
1단계에 사유를 기록한다. 아무것도 안 나오면 그대로 두고 2단계로 — **고칠 게 없다는 결론도
유효한 재점검 결과다.**

**비용 어림**: s1 실측 $0.40 기준 A·C는 각 $0.5 안팎, B는 스캐폴드 크기에 따라 $1~3.
합계 $2~4 예상.

## 3. 기록 규칙

- 각 런의 원문은 `framework/smoke/runs/`에, 판정은 그 세션의 rN 문서에 적는다.
- s1 산출물(`framework/smoke/s1-tdd/`)은 C의 시드이므로 **A를 위해 덮어쓰지 말 것** —
  대조 런은 별도 디렉터리(`s1-ctrl/`)에서 한다.
- 문안 수정이 생기면: SKILL.md 수정 → r16 1단계에 사유 → 관련 스모크 재실행. 실측 원문
  2문장(«지우지 마라»·«요구를 파일 안에 적는다»)의 의미는 보존 — 바꾸려면 근거를 함께 적는다.
