## 작업 A — 플러그인 로드 검증 (사용자 개입 필수, 먼저)

`/plugin marketplace add` · `/plugin install`은 **대화형이라 에이전트가 못 친다.** 사용자가
직접 실행한다(프롬프트에 `!` 접두어로도 된다).

```
/plugin marketplace add C:\Users\bhy99\proj\proj3
/plugin install specgate@proj3
```

**확인할 것 3가지:**

| # | 확인 | 실패하면 |
|---|---|---|
| A-1 | `/plugin` 목록에 `specgate`가 뜨는가 | `plugin.json` 스키마 문제 — 필드명 확인 |
| A-2 | `/spec` 커맨드가 자동완성에 뜨는가 | `commands` 경로 문제 |
| A-3 | 설치 세션에서 SPEC 없이 `.ts` Write가 **막히는가** | `${CLAUDE_PLUGIN_ROOT}` 치환 실패 가능 — 훅 명령을 절대경로로 임시 대체해 원인 가름 |

A-3이 이 라운드의 관문이다. **여기서 깨지면 «남이 갖다 쓸 물건»이 아니다.** 깨지는 경우
r37의 대안(설치 안내를 `.claude/settings.json` 직접 등록으로 문서화)이 남아 있으므로 되돌릴 수는 있지만,
그때는 «플러그인»이라 부르지 않는다.

⚠️ 이 리포 자신에 설치하면 실험자 세션이 오염된다(CLAUDE.md 하네스 절). **설치 시험은
리포 밖 스크래치 프로젝트에서 한다.** 검증 후 `/plugin uninstall`을 확인한다.

## 작업 B — 실제 프로젝트에 한 번 투입

A가 통과하면, **진짜 요구가 있는 작은 작업 하나**를 specgate 아래서 한다.
후보는 `C:\Users\bhy99\proj\ai-prompt-vault`(실사용 트랙의 그 프로젝트, 별도 리포의 살아 있는 코드).

- 과제는 **작아야 한다** — 게이트의 마찰이 어디서 아픈지 보는 게 목적이지 성과가 아니다.
- 관측할 것은 «점수»가 아니라 **«아쉬운 지점»**이다(조사 §221 — 네이티브 먼저, 써보고
  아쉬운 지점부터 채운다). 통제 실험이 아니므로 대조군·사전등록을 하지 않는다.
- 기록은 «무엇이 막혔고, 그게 정당했는가» 한 줄씩. 특히:
  - 정당한 차단 / **오차단**(SPEC이 필요 없는 작업인데 막힌 것)
  - 우회 유혹 — 빈 파일 + Edit, Bash 우회를 실제로 하고 싶어졌는가
  - `선택 대기` 행이 실제로 사용자에게 되돌아왔는가

**사용자 게이트 G3(실사용 2회차 실수요)에 걸린다** — 진짜 필요한 작업이 없으면 작업 B를
하지 말고 A만 하고 멈춘다. 억지 과제를 만들면 그건 또 «재기»다.
