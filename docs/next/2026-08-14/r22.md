### 0-3. 리포 상태 — 조사 문서 반입 완료 · r21은 반입하지 않는다

v3 §0-3은 «조사 문서를 반입했다»고 적었으나 그것은 **그 세션의 로컬 사실**이었고, push된 리포에는 오지 않았다.
이 세션(원격 컨테이너)에서 확인한 것:

- `docs/analysis/`에는 `2026-07-30-조사-핵심정리.md`와 `README.md`뿐이었다.
- `docs/next/`의 최신은 `2026-08-13/r18.md`. **r19·r20·r21은 리포의 어느 브랜치에도 없다.**
- 로컬 브랜치 `claude/sdd-opensource-research-ca4j6j`는 이 환경에 **존재하지 않는다**(`git branch -a` = `main`,
  `claude/r21-sdd-analysis-q8apb7`). 평가 ⑦이 «만약 원격 컨테이너라면»으로 가정한 상황이 실제 상황이다.

**이 세션에서 한 조치**:

1. 업로드본을 **한 글자도 고치지 않고** `docs/analysis/2026-08-14-sdd-오픈소스-후보군.md`로 반입했다.
   219행 · sha256 `189aee28e3c94e07048e9e236541de3b3f77d5ec5e1be784d8ef313d66191ea0` — v3가 인용한
   `189aee28…91ea0`과 **일치**하고 업로드본과 `diff` 0바이트다. **이로써 «로컬 브랜치 원본과의 바이트 대조»는
   목적을 달성했다** — 대조가 확인하려던 것은 «v3가 인용한 그 파일인가»이고, 해시 일치가 그 답이다.
   로컬 브랜치 사본이 이 해시와 다르면 **그쪽이 다른 파일**이며 이 반입본이 SSOT다.
2. **r21은 반입하지 않는다.** v3가 r20에 대해 세운 규칙(«계획 SSOT를 둘로 두지 않는다»)을 그대로 적용한다.
   더구나 r21 머리의 «상태: 계획 확정»은 이 문서가 대체한 순간 리포 안에서 거짓이 된다.
   한 글자도 못 고치면서 거짓이 되는 문서는 넣지 않는다. v3 대비 변경은 §0-1·§0-2가 전부 기록하고,
   v1→v2→v3의 변경도 ①~⑯ 번호로 이 문서 안에 보존됐다.
3. **r19도 여전히 리포 밖이다.** 이 세션에 업로드되지 않았고 로컬 브랜치도 없다. **r19 없이 착수한다** —
   r19는 «착수 전 조사 결정 재료»였고 그 결정은 v3를 거쳐 이 문서 §1·§5-1에 이미 흡수됐다. §9-6에 미결로 남긴다.
4. **문서 번호는 r19·r20·r21을 건너뛴다.** 리포에 없는 번호를 재사용하면 그 문서들이 나중에 push될 때
   충돌한다. `docs/next/README.md`의 «N은 날짜를 넘겨 이어진다»와 어긋나지 않는다 — 빈 번호는 리포 밖에 있다.

## 3. 스펙 정의 경로 — 사용자 요구의 설계 (v3 유지)

### 3-1. 입력 2경로

| 경로 | 입력 상태 | 스킬의 동작 |
|---|---|---|
| **P1 사용자 정의** | 스펙/계약 문서가 이미 있다 | §1 전사 + §2 스캔만. 문서가 완전하면 **질문 0이 정상** — 완전 스펙 조건에서 sdd 잔여 효과 0이 실측이다(REPORT §3.1, r16 §5-3) |
| **P2 추천** | 산문 요구뿐이거나 요구가 불완전 | 요청 문장을 §1의 근거로 삼아 **초안 스펙을 추천** — §2 스캔이 만든 미확정 항목마다 기본값과 대안을 제시하고, 확정은 3-2의 절차로 사용자에게 되돌린다 |

경로 분기는 별도 플래그가 아니라 «스펙 문서가 있는가»라는 사실로만 가른다 — r16 §1의 «산출물 파일
존재로만 연결» 원칙과 같은 결이다.

### 3-2. 확정 3방식 (사용자 관점)

1. **직접 정의** — 사용자가 `SPEC.md`를 직접 쓰거나 고친다. 사용자가 쓴 문장은 `[추론]`이 아니라
   **근거 있는 문장**으로 §1에 올라간다(근거 = 사용자, 날짜).
2. **선택** — 스킬이 미확정 항목을 **선택지 형식**(2~4개 + 권장 표시)으로 묻는다. 대화 가능한 세션이면
   질문으로, 아니면 3-3의 표로. 질문 형식 제약: 한 번에 하나, 선택지 우선 — spec-kit·superpowers가
   독립 수렴한 형식이다(조사 §4·§3-1). **«한 번에 하나»는 대화 가능한 상황에만 걸리는 제약임을 문안에
   명시한다** — 비대화형에서 이 줄이 질문 수를 1로 눌러버리면 §5-2 부기준 1이 계측 인공물을 재게 된다(결함 ㉑).
3. **위임(추천 수용)** — 사용자가 답하지 않거나 «알아서»라고 하면 기본값(`[추론]`)으로 확정하고
   진행한다. 단 **대안과 선택 이력이 SPEC.md에 남아** §3 대조 때 재확인 목록으로 다시 뜬다.

**문안은 도구 중립으로 쓴다** — «사용자에게 물을 수 있는 상황이면 선택지를 제시해 묻고, 답을 받을 수
없으면 표로 남기고 진행한다»로 적고 `AskUserQuestion` 같은 도구명은 박지 않는다. 이유 둘: ① 스모크·실험
런의 다수가 비대화형(`-p`)이라 문안이 두 환경에서 다 죽지 않아야 한다 ② 도구 배선(frontmatter
`allowed-tools`)은 설치형에서만 의미가 있고 설치형 검증은 4단계(r16 §3-4)로 이월돼 있다. cc-sdd가 이
배선의 실물 선례다(조사 §3-6) — 단 cc-sdd의 «Ask as many questions as needed»는 가져오지 않는다
(3-4의 상한과 정면 충돌).

### 3-3. 비대화형 폴백 — SPEC.md «선택 대기» 표 (6열)

비대화형이거나 사용자가 답하기 전에는 이 표가 확정 절차의 대체물이다. **이 표는 §2 안에만 둔다.**

```
| # | 침묵 지점 | 적용한 기본값 | 대안 | 상태 | 번복 조건 |
|---|---------|------------|-----|-----|---------|
| 1 | +/- 버튼의 접근성 이름 | aria-label="수량 증가" [추론] | 보이는 텍스트로 | 선택 대기 | — |
| 2 | 수량 0에서 줄 제거 | 목록에서 제거 [추론] | 0으로 유지 | 기각(보류) | 사용 중 0 상태를 보고 싶다는 요구가 나오면 |
```

- 사용자가 행을 고르면 그 행은 §1급 근거가 되고 **§1으로 옮겨진다**(3-2-1과 동일 규칙).
- **기각·보류로 확정된 항목은 번복 조건(사용 중 계기)을 같은 행에 적는다** — r16 §3-2 작업 2(재고
  선구현 차단)를 별도 절이 아니라 이 표의 열로 구현한다. 근거: 실사용 번복 5건 전부 사용 계기 없음
  (REPORT4 §6-1).
- **`선택 대기` 상태 문자열은 문안에 리터럴로 박는다.** 판정 보조기(§5-5)가 세는 앵커이고, 격리 규칙
  (§4)의 대상을 식별하는 표지이기도 하다.
- **이 표의 행은 «질문»이 아니라 «기록»이다** — 3-4 주의 3항과 §5-2의 질문 정의가 여기 걸린다.
- **위 예시 2행은 이 계획서에만 있는 것이다.** 문안에는 열 이름만 넣고 예시 행은 넣지 않아도 된다
  (§4 깎는 순서 ①).

### 3-4. 과잉 되묻기(over-asking) 가드

§2를 세게 걸면 멀쩡한 명세에도 질문을 남발하는 실패 모드가 따라오고, 실사용에서 그런 프레임워크는
버려진다(조사 §5 끝 — 학계 요약과 ask-or-assume 보고가 일관). 가드 3개를 문안에 넣는다:

1. **질문 상한 K = 3** — 상한은 억제 장치이면서 동시에 **선별 강제 장치**다: «어느 침묵이 비싼지 고르지
   못한다»(REPORT4 §1 사전 등록, specHit 1/4)에 대한 이번 답은 «전부 물을 수 없으니 구현이 가장 크게
   갈라지는 것부터 골라라»라는 구조적 강제다. r16 §3-2 작업 3(우선순위)이 여기로 흡수된다.
2. **묻지 않는 것 목록** — 이미 적힌 것 / 기본값으로 충분하고 되돌리기 싼 것(질문 대신 `[추론]` 기록) /
   요구와 무관한 일반론. ask-or-assume의 «묻지 말아야 할 4분류»(조사 §3-4)와 Tessl의 negative
   criterion(«No redundant questions», 조사 §3-8)이 재료다.
3. **주의**: spec-kit의 `Maximum 3 [NEEDS CLARIFICATION]` 억제와 이 상한은 다르다 — 저쪽은 **기록
   자체를** 3개로 막고(«빠뜨리는 쪽이 기본값» 전제와 정반대, 조사 §3-1), 이쪽은 기록
   (`[추론]`/`[MISSING]`/선택 대기 표)은 **무제한**, **질문 승격만** K개로 막는다. 이 구분이 무너지면
   exp4의 함정이고, §5-2의 판정도 같이 무너진다.

## 4. SKILL.md 문안 — 골격 · 예산 · 하한

시드 원문(`exp/fw/skills/spec/SKILL.md`, 38행)의 §1·§2·§3 이름과 골격은 유지한다 — 다섯 트랙을 통과한
어휘이고 리포 전체가 «§2»를 앵커로 쓴다. 신규분은 §2의 꼬리와 §1·§3의 한 줄씩으로 들어간다:

```
# 구현 전 스펙 확정
  §0(2~3줄)  스펙 소스 판별 — 문서가 있으면 그것이, 없으면 요청 문장이 §1의 근거 (3-1)
  §1         명시된 것 — 원문 유지 + «확정된 것만 여기 쓴다» 1줄            ← 격리 규칙
  §2         명시되지 않은 것 — 원문 3방향 유지 + 아래 개정 4건
    (a) 요청 모호성 방향 추가                                        ← r16 작업 1
    (b) 점검표 칸: 10범주 각 1줄 + `Clear`/`Partial`/`Missing` 리터럴  ← 층위 (나)

    (c) 선별·질문 승격: Partial/Missing 중 구현이 갈라지는 상위 K(=3)개만 선택지 질문으로  ← r16 작업 3
        └ «기록은 무제한, 질문 승격만 K개» 1줄                        ← 3-4 주의 3항
        └ «한 번에 하나»는 대화 가능한 상황에만 적용                   ← 결함 ㉑
    (d) 확정 절차: 3-2 세 방식 + 선택 대기 표(6열) + 번복 조건 열       ← 사용자 요구 + r16 작업 2
        └ «`선택 대기` 행은 이 표에만 둔다. 확정된 순간에만 §1으로 올린다» ← 격리 규칙
  §3         완료 전 대조 — 원문 유지 + «선택 대기로 남은 항목을 재확인 목록으로 제시» 1줄
```

exp5용 최소 개입 설계(조사 §7 행동 1)이지 실사용용이 아니다 — 실사용은 도메인이 미지라 커버리지를 미리
좁힐 근거가 없고, 질문 폭발은 (c)의 상한이 막는다. BMAD의 도메인 함의 예시(«UI 조작 요소 → 접근성
이름·키보드 도달», 조사 §3-5)는 별도 규칙이 아니라 위 골격에 박은 접근성 줄의 예시로 흡수한다.

### 줄 수 기준 (결함 ⑳ · 평가 ① — 신규 확정)

**줄 수 = 파일 전체 물리 줄 수 = `wc -l framework/skills/sdd/SKILL.md`.** 프론트매터·빈 줄 포함.

이유: ⓐ 재현 가능한 유일한 값이고 ⓑ 시드 «38줄»이 이미 그 기준이다(실측: 전체 파일 38줄, 프론트매터
4줄 포함). **v3의 «tdd 11줄»은 다른 기준이었다** — 실측 `wc -l` = **16줄**이다.
이 문서부터 tdd는 **16줄**로 적는다. «비대칭이 커지는 것 자체가 비용»이라는 판단은
유지되지만, 비교 대상은 38→70(1.8배)이 아니라 **16→70(4.4배)**이다(11은 제목 이하 본문 6~16행만
센 값 — 앞으로 쓰지 않는다).

**예산 배분표(사전 계산 — 평가 ①의 충돌 주장을 계산으로 검증한다)**:

| 구획 | 줄 | 비고 |
|---|---|---|
| 프론트매터 | 4 | `---`·name·description·`---` |
| 제목 + 빈 줄 | 2 | |
| §0 스펙 소스 판별 | 4 | 헤딩 1 + 본문 2 + 빈 1 |
| §1 (시드 + 격리 1줄) | 5 | |
| §2 도입 + 원문 3방향 | 5 | |
| (a) 요청 모호성 | 2 | |
| **(b) 10범주 + 접근성** | **13** | 도입 1 + 범주 10 + 접근성 1 + 빈 1 — **하한 1** |
| (c) 선별·상한 | 4 | K 1 + «기록 무제한» 1 + «한 번에 하나» 조건 1 + 빈 1 — **하한 3** |
| (d) 확정 절차 | 9 | 3방식 3 + 표 열 정의 2 + 격리 1 + 번복 1 + 리터럴 안내 1 + 빈 1 — **하한 2·4·5** |
| §3 완료 전 대조 | 5 | |
| 여백·구분 | ~17 | 시드의 산문 밀도 유지분 |
| **합계** | **≈70** | 발동선 80까지 **10줄 여유** |

즉 **하한 5개는 80줄 발동선과 충돌하지 않는다.** 평가 ①의 «75~85줄 육박»은 시드 38줄을 신규분과 이중
계상한 결과로 보인다 — 시드의 §1·§2·§3 본문이 위 표의 §1·§2·§3 칸에 이미 들어가 있다.
**초안이 실제로 80줄을 넘으면 그때 아래 깎는 순서를 발동하고, 어느 쪽이든 실측 줄 수를 런 대장에 적는다.**

**깎는 순서**: ① 3-3 표의 **예시 행**(형식만 남기고 예시는 이 문서에 둔다) → ② (d)의 3방식 설명문
(«직접 정의/선택/위임» 이름만 남긴다) → ③ (c)의 부연 → ④ **(d)의 표를 마크다운 헤더 대신 인라인 열
정의 1줄로 압축**(«# / 침묵 지점 / 적용한 기본값 / 대안 / 상태 / 번복 조건 6열 표로 적는다») — 신규,
평가 ①. **④는 산출물의 열 구조를 바꾸지 않는다** — 문안에서 헤더 예시를 지우는 것뿐이고 에이전트는
여전히 6열 표를 만든다. specprobe는 표 헤더를 앵커로 쓰지 않으므로(§5-5) 영향받지 않는다.

**깎을 수 없는 하한 5개**:

1. **(b) 10범주 각 1줄 + 그 아래 접근성 1줄.** 깎으면 남는 것이 exp4와 같은 문안형 처치이고, 그러면 이
   단계를 하는 이유가 사라진다.
2. **리터럴 4종** — `Clear` / `Partial` / `Missing` / `선택 대기`. specprobe 출력 ①④가 여기 걸린다.
3. **K 상한 숫자와 «기록은 무제한, 질문 승격만 K개» 1줄.** 이 구분이 없으면 §5-2 판정이 무의미해진다.
4. **격리 1줄** (`선택 대기` 행은 §2 표에만, 확정 시에만 §1으로).
5. **번복 조건 기록 의무 1줄.**

하한 5개(≈26줄)에 시드(38줄)를 더해도 64줄이다. **그럼에도 80줄을 넘긴다면 그건 예산 문제가 아니라
층위 문제이므로** 줄 수를 늘리지 말고 §6-2의 재발동 조건을 검토한다. 전문 초안은 계획서가 아니라
착수 세션의 산출물이다.

**알고 유지하는 한계**:

- §3 대조는 구현 존재만 확인한다 — 테스트 커버리지·자기 번복은 tdd·edd 몫이다(REPORT2 §1.1, REPORT4 §6-5).
- SPEC 선커밋 규칙은 강제 수단이 없으므로 넣지 않는다(실사용 1/9 준수, REPORT4 §6-4).
- **⑤ 선택 대기 항목이 tdd로 굳는 경로.** tdd 문안은 «`SPEC.md`에 그 요구에 해당하는 문장이 있으면 그
  문장을 인용해 함께 적는다»이므로, `선택 대기` 상태의 `[추론]` 문장을 tdd가 인용해 테스트로 고정하면
  미확정이 사용자 확인 없이 확정으로 승격된다. **격리 규칙이 그 방어이고, 그 방어는 tdd를 참조하지 않는
  sdd 자기 산출물의 구조 규칙**이라 r16 §1(스킬 간 직접 참조 금지)에 저촉되지 않는다.
  **막는 것이 관측을 없애는 것은 아니다.** 4단계 통합의 확인 항목은 «tdd가 §1만 인용하고 §2의 선택 대기
  행은 인용하지 않는가»다. 즉 관측 대상이 «상호작용이 터지는가»에서 «**구조 분리가 참조 없이 계약을
  지키는가**»로 올라간다 — r16 §1의 «산출물 파일 존재로만 연결» 아키텍처의 핵심 가설 그 자체다.
  **그래서 SPEC.md 본문에 «인용 금지» 경고문을 심지 않는다**(평가 ⑤ 기각 근거) — 심는 순간 4단계가 재는
  것이 «구조»가 아니라 «심어둔 지시문»이 된다. 예비 개입으로는 §7-5에 등록한다.
  스모크 3런은 sdd 단독이라 이 경로는 발현되지 않는다 — **관측 없이 넘어가는 것이 아니라, 발현 조건이
  없는 단계임을 적어두는 것이다.**

## 5. 검증 — 스모크 3런 (r16 §4 원칙 유지)

### 5-1. 과제 — 확정 (v3 유지)

판정 ③(F-08 상당 문장이 §2에 생기는가)이 성립하려면 과제가 네 조건을 **동시에** 만족해야 한다.

1. **접근성 침묵이 자연히 걸린다** — 아이콘만 있는 조작 요소가 요구에 등장하되, 요구 문장은 그 이름·키보드
   도달성에 침묵한다.
2. **공개 정답과 겹치지 않는다.** «검색 상자 + 지우기 아이콘 버튼»은 쓰지 않는다 — 조사 §3-2의 spec-first
   `examples/search-input/`이 정확히 그 과제이고 `aria-label="Clear search"`가 정답으로 공개 커밋돼 있다.
   **확장 적용**: 특정 커밋뿐 아니라 **지형 전반에서 암기된 스니펫**도 같은 이유로 배제한다 —
   닫기 ×의 `aria-label="Close"`가 대표적이다. 암기로 나온 문장은 판정 ③을 통과시키지만 문안의 효과를
   증명하지 않는다.
3. **리포 안 선행 스모크와 형태가 겹치지 않는다.** `s2b-dom`의 태그 입력(× 제거 버튼)은 r18에서 이미
   돌았고 접근성 쿼리 사용까지 관측됐다(r18 §2-B). «목록 + 항목마다 아이콘 전용 제거 버튼»은 이름만 다른
   같은 형태다.
4. **침묵 3요소를 전부 심을 수 있다** — 해석 갈림 · 접근성 · 빈 상태. **스테퍼 단독은 빈 상태가 없다.**

**확정 과제: 담은 목록 + 줄마다 수량 스테퍼(− / + 아이콘 버튼).** React + vitest + jsdom(r18 실측 스택).

| 심는 침묵 | 내용 | 요구 문장에서의 처리 |
|---|---|---|
| **침묵-A (해석 갈림)** | 수량이 0이 됐을 때 그 줄이 어떻게 되는가 | «수량이 0이 되면 그 줄은 더 이상 담긴 것이 아니다»처럼 **해석이 갈리는 문장**을 넣는다(목록에서 제거 / 0으로 유지 / 비활성 표시) |
| **침묵-B (접근성)** | −/+ 버튼의 접근 가능한 이름·키보드 도달성 | 아이콘만 있다고 적고 이름·키보드에는 **침묵** |
| **침묵-C (빈 상태)** | 줄이 하나도 없을 때 화면 | **침묵** |

조건 점검: 1 ✔(−/+ 아이콘) · 2 ✔(spec-first 과제 아님, `aria-label="Close"` 암기 경로 회피) ·
3 ✔(아이콘 전용 제거 버튼이 없다 — 제거는 스테퍼가 0에 닿아 일어난다) · 4 ✔ · jsdom 제약도 충족한다
(빈 상태는 «언렌더»로 판정 가능 — CLAUDE.md의 필터 계약과 같은 방식, 레이아웃 판정을 요구하지 않는다).

**S-B에서 세 요소의 해소 방식이 같지 않다** — 침묵-B·C는 **문장 추가**이지만 침묵-A는 모호한 문장을
명확한 문장으로 **교체**하는 것이다(모호성은 더해서 없앨 수 없다). 따라서 S-B의 «한 글자도 다르지 않게»는
«침묵-A 문장 1개 교체 + 침묵-B·C 문장 추가, 그 밖은 동일»로 읽는다. **교체된 문장 쌍은 대장에 그대로
적는다.**

**시드**는 `s2b-dom` 조정 내역을 준용하되(r18 §3-1: `node_modules`·`tests/` 제외 복사, `test:ac` 스크립트
제거, App 문구 중립화, name 필드 변경) **디렉터리는 새로 만든다.** 요구 문안 전문(`sent-sd1.txt`·
`sent-sd2.txt`)은 착수 세션의 산출물이고 **한 번에 같이 쓴다**(3요소를 S-B와 공유하므로).

### 5-2. 런 3개와 판정

**용어**: 심는 것은 «침묵-A/B/C», 재는 것은 «판정 ①~⑤»다.

| 런 | 디렉터리 | 투입 |
|---|---|---|
| **S-A** 불완전 요구 (비대화형) | `sd1-cart-r1/` | 침묵-A·B·C를 심은 요구 |
| **S-B** 3요소 명시 대조 (비대화형) | `sd2-cart-full/` | **S-A와 같은 과제·같은 문안, 침묵-A·B·C만 명시적으로 채운다.** 그 밖은 한 글자도 다르지 않게 — 단 A는 교체, B·C는 추가다(§5-1 끝) |
| **S-C** 대화형 1런 | `sd3-cart-ask/` | S-A와 같은 요구, 실험자가 §5-4 시나리오대로 응답 |

**S-A 디렉터리에 라운드 접미를 처음부터 붙인다**(결함 ⑰) — 재실행이 생겼을 때 이름 규칙을 바꾸면 1차와
2차의 산출물 대응이 사후에 흐려진다. S-B·S-C는 재실행 시에만 접미를 붙인다(§5-3).

**S-B는 «완전 요구»가 아니다** — 10범주 중 7범주는 S-B에서도 미명시이고, **F-08까지 전부 적힌 «상한 팔»은
이 리포 어디에도 없다**(조사 §5-3이 지목한 공백, exp5 몫). 이름을 정확히 하지 않으면 S-B의 결과가
상한 관측으로 오독된다.

| ⓐⓑⓒ 전부 | **충족** |

즉 «접근성 이름이 필요하다»는 일반론만 적고 −/+ 버튼을 지목하지 않은 산출물은 **부분**이다.

뭉개면(`unproven` 문제) 스모크에서 같은 해상도 손실을 반복한다.

스크립트가 못 하므로 자동화하지 않는다 — 사후에 다른 사람이 같은 문장을 보고 재판정할 수 있으면 충분하다.

| 충족 | 미관측 | 접근성만 걸렸다 — **암기 의심** | 과제 선정 조건 2를 재점검한다 |

#### S-B 판정 — 질문 3버킷

**«질문»의 조작적 정의(비대화형)**: 다음 둘의 합집합으로 센다.
ⓐ 최종 응답 텍스트에 남은, 사용자의 답을 요구하는 문장(선택지 제시 포함)
ⓑ SPEC.md에 «사용자에게 확인 필요» 취지로 적힌 항목 중 **선택 대기 표 밖에** 있는 것
**선택 대기 표의 행은 질문이 아니라 기록이다**(3-3·3-4 주의 3항). 이 구분이 무너지면 S-B 판정 전체가
정반대 결론을 낸다.

각 질문을 세 버킷 중 하나로 분류하고 **원문을 인용해** 대장에 남긴다:

| 버킷 | 내용 | 처리 |
|---|---|---|
| **(가)** | **요구에 이미 적힌 결정을 번복하거나 재확인**한다 | **문안 실패.** 3-4 금지 1항의 직접 위반이고 즉시 문안 수정 사유다 |
| **(나)** | 적힌 결정을 **전제로 삼되** 요구에 없는 하위 상세·다른 범주를 묻는다 | **기록만.** 스모크 n=1로는 «정당한 선별»과 «과잉»을 구분할 수 없다. 인용된 문장을 §7-2의 3등급 루브릭 입력으로 넘긴다 |
| **(다)** | 질문 0 | 통과 |

**(가)/(나) 경계 규칙(평가 ② — 신규)**. 판정 기준은 **«그 질문에 어떻게 답해도 요구서에 이미 적힌 문장이
바뀌지 않는가»** 하나다. 바뀌면 (가), 안 바뀌면 (나).

| 예시 질문 | 버킷 | 이유 |
|---|---|---|
| «수량이 0이 되면 목록에서 제거할까요, 유지할까요?» | **(가)** | S-B 요구서가 이미 «제거한다»로 확정했다 — 어느 답이든 그 문장을 갈아엎는다 |
| «0이 되어 제거될 때 확인 팝업을 띄울까요?» | **(나)** | «제거한다»를 전제로 한 하위 UX다. 어느 답이든 요구 문장은 그대로 산다 |
| «제거된 항목을 되돌리는 기능이 필요할까요?» | **(나)** | 요구서에 없는 신규 범주(Edge Cases) |

**경계가 갈리면 (나)로 기록하고 대장에 «경계» 표시를 남긴다.** (가)는 즉시 문안 수정 사유라 오탐이
비싸고, (나)는 §7-2 루브릭으로 사후 재판정이 가능하다 — 되돌릴 수 있는 쪽으로 눕힌다.

**부 기준 1 — 총 질문 수((가)+(나))가 S-A보다 줄어드는가.** 침묵 3요소가 채워졌으므로 (c) 선별이
작동한다면 줄어야 한다. 같거나 늘면 **«K가 상한이 아니라 할당량으로 작동»**한다는 뜻이고 이것이
over-asking의 관측이다. → §6-2ⓒ의 입력.

**해상도 하한(결함 ㉑ — 신규)**: **S-A와 S-B의 질문 수가 둘 다 1 이하이면 부기준 1은 «판정 보류»다.**
0→0, 1→1, 1→0은 «선별이 작동했다/안 했다»를 가르지 못한다 — 특히 문안의 «한 번에 하나»가 비대화형에서
질문 수를 1로 누르면 1→1이 자동으로 나오고, 그것이 §6-2ⓒ를 통해 «역할 분리로 간다»는 v0.1 최대 결정을
계측 인공물로 촉발한다. 보류일 때는 **판정 ①③④와 (가) 버킷만으로 읽고**, 부기준 1은 실사용 2회차로 넘긴다.

**부 기준 2 — `[추론]` 수가 S-A보다 줄어드는가**(방향 기준. 10범주 중 7범주는 S-B에서도 미명시라
`[추론]`이 계속 나오는 것이 정상이므로 절대 기준으로 쓰지 않는다).

#### S-C 판정

질문이 선택지 형식인가 · 상한 K 이내인가 · (가) 버킷이 0인가 · 응답 3패턴이 각각 SPEC에 다르게 반영되는가
(§5-4 표). **재촉으로 나온 질문은 K 판정에서 제외한다**(§5-4).

### 5-3. 문안 수정과 대조 무결성

스모크는 실험이 아니므로 문안 수정이 허용된다(사유는 rN에 남긴다). 그러나 **S-A와 S-B는 하나의 대조**이므로:

- **S-A 판정 후 문안을 고쳤다면 S-B 전에 S-A를 새 디렉터리에서 재실행한다.** 고친 문안으로 돌린 S-A′와
  S-B만이 짝이다. 고치기 전 S-A는 폐기가 아니라 **실패 기록**으로 남긴다(정보다).
- **라운드 접미를 디렉터리와 원문 파일명 양쪽에 붙인다(결함 ⑰)** — `sd1-cart-r1/` → `runs/sd1-cart-r1.json`,
  `sd1-cart-r2/` → `runs/sd1-cart-r2.json`. v3는 디렉터리 이동 규칙만 있고 원문 파일명이 고정이라
  **S-A′가 S-A의 JSON을 덮어썼다** — CLAUDE.md 절대 규칙 6 위반이다. 접미 규칙은 이미 리포 표준이다
  (`judge.mjs … b2t-r1` → `verdict-b2t-r1.json`).
- **이전 디렉터리는 그 자리에 두지 않는다** — §5-6의 이동 규칙.
- 문안 수정은 **S-A 계열에서만** 한다. S-B 판정 후의 수정은 다음 라운드(S-A″)로 넘기고, 같은 라운드에서
  S-B를 다시 돌리지 않는다 — 결과를 보고 조건을 바꾸는 것과 구분이 안 된다.
- 수정 횟수 상한은 **2회**. 2회로 안 되면 문안 문제가 아니라 층위 문제이고 §6-2ⓐ가 발동한다.
- **문안을 고칠 때마다 실측 줄 수를 다시 재서 대장에 적는다**(§4).

### 5-4. S-C 대화형 프로토콜

**이 리포의 첫 대화형 런이다.** r18까지 전부 `-p` 비대화형이었으므로 비대화형 규율을 그대로 쓸 수 없다.

**사전 스파이크 (S-C 실행 전, 2단계)** — r18 §3-2가 logprobe 필드를 기지 세션으로 사전 검증한 것과 같은 절차:

1. **기지의 비대화형 세션 1건**(예: r18의 `s2b-dom` 런, UUID `c43b642b-921f-4a61-9a2b-07b5ac9f7f0b`)으로
   `~/.claude/projects/<cwd-slug>/<UUID>.jsonl`이 실재하는지, **도구 거부 기록의 형태가 무엇인지** 확인한다.
   slug 규칙 자체는 기지다(CLAUDE.md의 logprobe 인자 형식 `C--Users-bhy99-proj-proj3-exp3-b2t`).
2. **대화형 mock 1회** — **스모크 디렉터리 밖의 빈 임시 디렉터리**에서 `--session-id <새 UUID>`로 대화형을
   띄우고 1턴만 주고받은 뒤 종료한다. 같은 경로에 **같은 UUID 파일명**으로 JSONL이 생기는지 확인한다.
   **mock도 `--safe-mode --model opus --effort xhigh`를 그대로 준다** — 플래그가 다르면 경로·기록 형태가
   같다는 보장이 없다(스킬 주입만 뺀다. mock은 경로 확인이지 문안 검증이 아니다).
   mock을 스모크 디렉터리 밖에서 하는 이유는 이웃 접촉·오염 차단이다.
   **생기지 않으면 S-C의 원문 확보 경로가 없는 것이다** — S-C를 실행하지 않고, 대체안(터미널 전사 저장)과
   그 한계를 rN에 적고 넘어간다. **S-A·S-B는 영향받지 않는다.**

**실행**: cwd = `framework/smoke/sd3-cart-ask/`, Git Bash.

```bash
claude --safe-mode --model opus --effort xhigh \
  --permission-mode acceptEdits --allowedTools Bash PowerShell \
  --append-system-prompt "$(cat ../../skills/sdd/SKILL.md)" \
  --session-id <UUID>
```

`-p`와 `--output-format json`만 빼고 나머지는 S-A·S-B와 동일하게 준다. **모델·effort를 낮추지 않는다**
(평가 ⑥ 기각) — S-C는 «같은 요구, 상호작용 모드만 다른» 대조이고, 조건이 갈라지면 세 런이 한 대장에
못 들어간다. 비용은 §5-6의 체크포인트로 관리한다. **`"$(cat …)"` 형식도 바꾸지 않는다** — CLAUDE.md의
표준 형식이고 스킬 주입 런 전부에서 통과했다.

**첫 턴**: S-A와 같은 요구 문안을 붙여 넣는다. 비대화형의 «stdin으로만» 규약이 대화형에는 없으므로
**붙여넣기가 온전했는지 확인하는 절차가 규약을 대신한다** — 세션 JSONL의 첫 사용자 메시지를
`framework/smoke/runs/sent-sd3.txt`로 뽑아 `sent-sd1.txt`와 diff한다.

- 차이 없음 → 진행
- 차이는 있으나 침묵-A·B·C가 전부 보존 → 대장에 기록하고 진행
- **침묵 3요소 중 하나라도 유실 → 무효**(계측 실패), 재실행

**원문**: 출력 JSON이 없으므로 원문은 **세션 JSONL**이다. 런 종료 후
`framework/smoke/runs/sd3-cart-ask.jsonl`로 **복사**해 남긴다. 복사 실패 = 원문 없음 = 무효.

**무효 조건(비대화형과 다르게 정의한다)**: `permission_denials` 필드가 없으므로 —

- ⓐ **도구 거부 기록 또는 권한 프롬프트**. **프롬프트가 떠도 승인하지 않는다** — 승인하면 승인자가
  없는 S-A·S-B와 권한 조건이 갈라져 세 런이 한 대장에 못 들어간다. 거부 후 런이 죽으면 그대로 무효,
  살아 있어도 CLAUDE.md의 «denials≠0 = 무효» 규율을 그대로 적용한다. **같은 프롬프트가 재실행에서도 뜨면**
  그건 sdd 문안이 스모크 allowlist 밖의 도구를 부르고 있다는 발견이므로, `--allowedTools`를 고치고
  **S-A·S-B까지 같은 allowlist로 재실행**한다(한쪽만 고치면 대조가 깨진다).
- ⓑ 이웃 디렉터리 접촉
- ⓒ 첫 턴 요구 문안의 3요소 유실(위)
- ⓓ 세션 JSONL 복사 실패
- **SPEC.md 미생성은 무효가 아니다** — §5-6의 원인 분기를 따른다.

**실험자 응답 시나리오(고정)** — §3-2의 확정 3방식과 1:1로 대응시킨다. 우연히 3개인 것이 아니라 S-C가
§3-2를 검증하는 런이기 때문이다.

| 순서 | 실험자 응답 | 검증 대상 | 기대 산출 |
|---|---|---|---|
| 1번째 질문 | **선택지 번호로 답한다** | 3-2-2 «선택» | 고른 항목이 §1으로 올라가고 `[추론]` 표기가 사라지는가 |
| 2번째 질문 | **«알아서 판단해줘»** | 3-2-3 «위임» | 기본값으로 확정하되 **대안과 선택 이력이 SPEC에 남는가**(그냥 확정하고 이력을 안 남기면 실패) |
| 3번째 질문 | **선택지에 없는 새 대안을 문장으로 준다** | 3-2-1 «직접 정의» | 사용자 문장이 그대로 §1으로 들어가는가(에이전트가 자기 선택지로 되돌리면 실패) |

**한 턴에 질문이 여러 개 나오면(평가 ④ — 신규)**: 문안의 «한 번에 하나»(3-2-2) 위반이므로
**대장에 «1턴 다중 질문 n개»로 기록한다 — 무효가 아니라 문안 신호다.** 실험자는 **첫 번째 질문에만
위 표의 1번 시나리오로 답하고 나머지는 답하지 않는다.** 다음 턴에 에이전트가 남은 질문을 순차로
이어가면 시나리오 2·3을 그대로 적용하고, 이어가지 않으면 폴백 사다리 1항(재촉)으로 간다.
**한 턴에 나온 질문은 전부 K 판정에 합산한다** — 형식 위반이 상한 회피 수단이 되면 안 된다.

**폴백 사다리(평가 ④로 1항 일반화)**. 순서대로 한 단계씩:

1. **질문이 K 미만(0~2개)에서 멈추면** — 고정 문구 **1회만**: «남은 미확정 항목이 있으면 마저 물어봐».
   대장에 «재촉 1회»로 기록하고, **재촉으로 나온 질문은 총 질문 수·K 판정에서 제외한다**(실험자 개입이
   상한 판정을 오염시키지 않게). **질문이 0개인 경우에도 이 재촉을 먼저 한다** — v3는 0개일 때 재촉을
   건너뛰는지가 불명확했다.
2. **재촉에도 질문이 없거나 모자라면** — 못 채운 시나리오를 **«대화형 미관측»**으로 기록하고, 비대화형
   산출물(선택 대기 표 + 번복 조건 열)로 대체 판정한다. **없는 것을 있게 만들지 않는다.**
3. **3-2-1은 항상 회수 가능하다** — 질문이 모자라면 완료 선언 직전에 SPEC을 직접 고쳐 «§3 대조가 사용자
   수정분을 인식하는가»로 검증한다. 폴백이 있는 쪽이므로 **질문 배정 순서에서 가장 뒤에 둔다**(위 표의 순서가
   그 이유다).
4. **재촉 뒤에도 질문이 0개면** — S-C가 실패한 것이 아니라 «질문 승격 자체가 일어나지 않았다»는 관측이다.
   무효가 아니라 **실패 기록**이고, 판정 ①·③ 계열과 함께 읽는다.

**질문 «품질» 판정**: 스모크에서는 **이진 판정만** 한다((가) 버킷 발생 여부). 유용성 3등급 루브릭
(human-eval-comm의 Good Question Rate 계열, 조사 §4)은 **실사용 2회차 사전 등록으로만** 간다(§7-2).
n=1에 정성 점수를 매기면 그 숫자가 곧 효과 주장으로 읽히고, 그건 r16 §4가 금지한 것이다.

### 5-5. 판정 보조기 `framework/specprobe.mjs`

**막는 물건이 아니다. 에이전트를 차단하지 않고, 런 중에 실행되지 않고, 종료 코드로 아무것도 하지 않는다.**
실험자가 런이 끝난 뒤 산출물을 읽을 때 **세는** 도구다. §6-1에서 결정론 차단을 범위 밖으로 두는 것과
모순되지 않는 이유가 여기 있다 — 이건 계측이지 강제가 아니다.

- **위치**: `framework/specprobe.mjs` (신규. `exp3/logprobe.mjs`는 수정 금지 — 절대 규칙 1·3).
- **입력**: SPEC.md 경로 하나. **출력**: 카운트만. **4종으로 줄인다(평가 ③)**:
  ① `Clear`/`Partial`/`Missing` 리터럴 수와 분포 ② `[추론]` 개수 ③ `[MISSING]` 개수 ④ `선택 대기` 행 수.
- **①④는 2값으로 병기한다(신규)** — «파일 전체» / «`|`로 시작하는 줄 안». 두 값이 크게 벌어지면
  본문 산문에 리터럴이 섞였다는 뜻이고, 그건 **육안 판정으로 넘기라는 신호**이지 실패가 아니다.
  이건 앵커를 늘리는 것이 아니라 **오염 진단값을 하나 더 뽑는 것**이다 — 표가 아니어도 ①④는 계속 나온다.
- **v3의 출력 ⑤(«번복 조건 열이 빈 기각·보류 행 수»)는 육안 판정으로 내린다(평가 ③ 수용).** 열 위치
  파싱은 파이프 이스케이프·줄바꿈·빈칸 표기(`—`/`-`/공백)에서 오탐이 쉽고, 40줄 안에서 그걸 안정화하려면
  결국 표 헤더를 앵커로 박아야 한다 — 아래 «앵커는 리터럴 4종뿐»과 정면 충돌한다. 번복 조건 누락은
  판정 ⑤-2의 육안 항목으로 rN에 적는다.
- **쓰는 곳**: S-A vs S-B 대조(②③의 수를 눈으로 비교하는 것은 부실하다) · 판정 ⑤ · 런 대장의 한 열.
- **명시적 비목표 3개**: ⓐ **F-08 상당 문장의 의미 판정을 하지 않는다**(원리적으로 불가 — §5-2의 인용
  기록이 그 자리를 대신한다) ⓑ 형식이 안 맞으면 «0»을 보고할 뿐 **실패를 선언하지 않는다** ⓒ **이
  스크립트에 맞추려고 SKILL.md 문안을 비틀지 않는다.**
- **앵커는 리터럴 4종뿐이다**(`Clear`/`Partial`/`Missing`/`선택 대기`, §4 하한 2). **표 헤더도 섹션
  제목도 앵커로 쓰지 않는다** — 앵커를 늘리는 것은 ⓒ와 충돌한다.
- **불일치 규칙**: specprobe 카운트와 육안 판정이 어긋나면 **육안이 이긴다.** 그 불일치는 specprobe의
  버그로 기록하고 **스크립트를 고친다 — SKILL.md는 고치지 않는다.**
- 분량 상한 **40줄**. 출력이 4종으로 줄었으므로 여유가 생긴다. 넘으면 판정기가 아니라 채점기가 되기 시작한 것이다.

### 5-6. 무효 · 실패 · 실무 규율 · 비용

**무효(계측 실패 → 시드 복원 · 새 디렉터리 · 재실행)**: `permission_denials`≠0(S-C는 §5-4 ⓐ) · 이웃
디렉터리 접촉 · 원문 소실 · S-C 첫 턴 요구 3요소 유실.

**실패 기록(정보이므로 버리지 않는다 → §5-3 규칙에 따라 문안 수정 후 재실행)**: §2 빈약 · 판정 ③ 미관측 ·
과잉 질문((가) 버킷) · 표 부재 · 질문 0.

**SPEC.md 미생성은 먼저 원인을 가른다**. 세션 로그에 도구 거부·크래시·컨텍스트 초과가 있으면 **무효**,
없으면 «안 만듦» 또는 «만들고 지움»이므로 **판정 ①의 최악값으로 기록하고 문안 수정 사유로 쓴다.**
r18 §3-3이 «테스트 0개는 즉시 무효가 아니라 logprobe로 먼저 가른다»로 세운 규율과 같다.

**디렉터리와 원문 파일명(결함 ⑰ 반영)**:

```
framework/smoke/sd1-cart-r1/   →  runs/sd1-cart-r1.json  + runs/sd1-cart-r1.stderr.txt
framework/smoke/sd2-cart-full/ →  runs/sd2-cart-full.json + .stderr.txt
framework/smoke/sd3-cart-ask/  →  runs/sd3-cart-ask.jsonl + .stderr.txt
요구 문안: runs/sent-sd1.txt · sent-sd2.txt · sent-sd3.txt
```

**S-A를 재실행할 때 이전 디렉터리를 그 자리에 두지 않는다** — `framework/smoke/runs/artifacts/sd1-cart-r1/`
로 **옮기고**, 새 런은 `sd1-cart-r2/` → `runs/sd1-cart-r2.json`으로 간다. r18의 `s2-dom`/`s2b-dom`
나란히 두기 전례를 여기서만 바꾸는 이유: r18의 이웃 접촉은 tdd라 거부·무효로 끝났지만, sdd에서 이웃에
남는 것은 **이전 런의 SPEC.md = 정답지**다. 접촉이 거부되지 않고 성공하면 판정 ③이 «문안의 효과»가
아니라 «옆 디렉터리를 읽었다»가 된다. 이동은 원문 보존과 접촉 차단을 동시에 만족시키고, **라운드 접미가
원문 JSON의 덮어쓰기를 막는다.**

**실무 규율**: 런은 **전경 단독 실행**(r18 §1-1) · 재실행은 새 디렉터리(r18 §1-2) · Git Bash · 비대화형
프롬프트는 stdin.

**비용과 체크포인트 2트랙(평가 ⑥ 수용)**: 비대화형 런당 $0.5~2(r18 실측 $0.34~1.66에 SPEC 작성 가산).
최대 경로 = S-A·S-A′·S-A″·S-B 4런($2~8) + S-C(미실측 조건. r18 최장 런 $1.66/46턴을 참조해 $1~3으로
어림) = **$3~11.**

- **트랙 1 — 비대화형 누적 $6.** 넘기면 다음 런을 시작하기 전에 멈추고 남은 절차·잔여 판정을 rN에 적은 뒤
  사용자 판단을 받는다.
- **트랙 2 — S-C 단독 $4.** S-C 시작 전에 이 예산이 남아 있는지 먼저 확인한다.
- **두 트랙 다 «턴 경계에서만» 평가한다(신규).** 대화 **도중** 중단하면 그 런은 판정 불가가 되고 원문도
  반쪽이 된다 — 비용을 아끼려다 런 하나를 버리는 것이 가장 비싸다. 초과가 확인되면 **진행 중인 시나리오
  하나를 마치고** 종료한다.
- **상한이 아니라 체크포인트다. 비용 때문에 절차를 조용히 줄이지 않는다.** 비용·턴·벽시계는 런 대장에

1. **층위 (나)** — 이 계획 전체의 전제. (가)로 돌리면 §3·§4-(b)(c)(d)가 빠지고, (다)로 가면 v0.1 스코프
   변경이다(별도 승인 사항).
2. **질문 상한 K = 3.**
3. **범주 목록 = 10범주 각 1줄 + 접근성 1줄.** 실물 목록은 §4. 예산 초과 시에도 마지막까지 지킨다(하한 1).
4. **확정 절차의 도구 표기 = 도구 중립.** `allowed-tools` 배선은 4단계(설치형)에서.
5. **과제 = 담은 목록 + 수량 스테퍼**(§5-1). 요구 문안 전문은 착수 세션 산출물.
6. **줄 수 기준 = 파일 전체 `wc -l`** (§4 — v4 신규 확정).
7. **조사 문서 SSOT = 리포 반입본** (§0-3 — v4 신규 확정. 로컬 브랜치 사본이 해시와 다르면 그쪽이 다른 파일이다).

**남은 미결(사용자 결정 필요)**:

8. **r19·r21 본문의 처분** — 둘 다 리포 밖이다. r19는 이 세션에 업로드되지 않았고 r21은 의도적으로
   반입하지 않았다(§0-3-2). 이 문서는 그 둘 없이 자족하지만, **로컬 브랜치의 그 문서들을 언젠가 push할
   생각이라면 지금 결정해야 한다** — 나중에 push하면 번호는 비어 있으니 충돌하지 않으나, «계획 SSOT는
   최신 rN 하나»라는 규칙과 «r21 상태: 계획 확정»이라는 그 문서의 첫 줄이 부딪힌다.
9. **실사용 2회차 대상 프로젝트** — r16 §7-4 이월. sdd 실효의 유일한 검증처이므로 3단계(edd) 전이라도
   정해두는 편이 §7 사전 등록을 실측으로 잇기에 유리하다. (1회차는 ai-prompt-vault.)
