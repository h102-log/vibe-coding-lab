## 0. 왜 하는가 — 지금 근거는 전부 «개발 셋»이다

1. **기지값 4앱은 홀드아웃이 아니다.** r20 §4의 기지값(s1-tdd·s1-ctrl·s2-dom·s2b-dom)은
   스크립트를 **그 기대값에 맞춰 개발**한 데이터다. 재현 = 회귀 없음의 증거이지 정확도의
   증거가 아니다. 같은 앱을 정확도 주장에 재사용하면 순환이다.
2. **음성 픽스처 4종은 인공 변형이다.** 스크립트 상수(MUTATIONS)로 주입한, 스크립트 작성자가
   상상한 위반이다. 에이전트가 실전에서 만드는 **자연 발생 위반·변주**(어중간한 헤더, 패턴
   목록 밖의 환경 의존, 예상 밖 파일 배치)에서의 오탐·미탐은 미검증이다.
3. **투입처가 정해져 있다.** full 스모크(r16 §3-4단계)·실사용 2회차·향후 tdd 재스모크가 이
   계측기를 쓴다(r20 §0-2). 투입 전에 실전 정확도 근거가 있어야 r20 §0-4의 «스킬 16줄 +
   검증 하네스 한 세트» 주장이 성립한다.

## 2. 설계 — 2×2 런 + 선판정-후대조

### 2.1 런 매트릭스와 격리 실행

| 라벨 | 스킬 | 과제 | 이 셀이 주는 재료 |
|---|---|---|---|
| `e1-tdd` | tdd 주입 | s1(textkit) | 테스트+헤더+인용 → B·C·D **오탐** 재료 |
| `e1-ctrl` | 없음 | s1(textkit) | 자산 0(예상) → A `"none"` 일치 확인 |
| `e2-tdd` | tdd 주입 | s2(TagInput) | DOM 쪽 오탐 재료 + 파일 배치 변주 |
| `e2-ctrl` | 없음 | s2(TagInput) | 자산 0 또는 헤더 없는 테스트 → B **미탐** 재료 |

스킬 유/무를 분리하는 이유는 효과 비교가 아니라 **산출물 분포의 양쪽 끝 확보**다:
처치군은 «깨끗하지만 변주 있는» 산출물(오탐이 나올 자리), 대조군은 «지저분하거나 빈»
산출물(미탐·none이 나올 자리). 한쪽만으로는 검사 4종의 양방향을 재지 못한다.

과제·프롬프트는 기존 스모크 것을 재사용한다(`sent-s1.txt`·`sent-s2.txt` 실물 커밋됨).
같은 과제의 **새 세션**이므로 산출물은 기지값과 다른 변주가 된다(s2-dom vs s2b-dom이
이미 파일 배치부터 달랐던 실물 근거).

**격리 실행 — 런은 리포 밖에서 한다.** 근거 2건이 겹친다: ① r18 §1-2의 실측 무효 사유
재생산 방지 — 스모크 디렉터리가 나란히 있는 배치 자체가 이웃 접촉 경로를 만들었다
(에이전트가 cwd 밖 `s1-tdd/`를 Read 시도 → denials 2건 → 무효). ② **답안지 노출 차단** —
기존 스모크 때는 존재하지 않던 `framework/verify-tdd.mjs`(패턴 상수·디나이리스트 = 이
평가의 답안지)와 기지값 JSON 8건이 지금은 리포에 커밋돼 있다. cwd가 리포 안이면 에이전트가
관례 파악차 상위를 훑는 것만으로 읽힌다. 그래서: **각 런은 OS 스크래치의 단독 부모
디렉터리에서 실행하고(형제·리포 비가시), 종료 후 산출물 전체를
`framework/verify-eval/<label>/`로 이동해 커밋한다.** 이동 후 판정·verify는 리포 안에서.

### 2.2 블라인드 절차 — 이 계획의 핵심 규율

정확도 대조가 성립하려면 사람 판정이 스크립트 출력에 오염되지 않아야 한다:

1. **육안 판정을 먼저** 한다 — 라운드마다 `runs/human-<label>.md`에 4검사 질문의 답을
   기록하고 **verify-tdd 실행 전에 커밋**한다. 커밋 시각이 순서의 증거다.
   **순서를 어긴 라운드는 정확도 데이터로 무효**(산출물 재료로만 남긴다).
2. **A(잔존·실행)의 사람 판정 절차**: 앱의 **자체 배선**(에이전트가 구성한 config·`npm test`,
   없으면 vitest 직접 호출)으로 실행해 pass/none/fail을 판정하고, 실행 커맨드와 결과 요약을
   `human-<label>.md`에 기록한다 — verify-tdd의 임시 config 경로와 **독립인 실행**이어야
   대조가 성립한다.
3. **B·C·D 육안 판정 방식**: 테스트 파일 **전문 통독이 기본, grep은 보조.** 특히 C는 스크립트
   패턴 목록으로 긁지 않고 SKILL.md 문안 기준(«코드가 멀쩡해도 다른 머신·다른 시점에서
   실패하는 단언인가»)으로 판정한다 — 같은 패턴으로 찾으면 같은 미탐을 공유해 대조가
   무의미해진다.

### 2.3 그라운드 트루스와 미탐·오탐의 정의 — 검사별로

사람 선판정도 놓칠 수 있다. 확정 위반 집합은 **«사람 선판정 ∪ 스크립트 산출» 전체를 사후
재확인해 확정**한 것으로 정의한다. 스크립트만 잡은 것이 재확인에서 위반으로 확정되면 사람
선판정의 누락으로 기록한다(스크립트 감점 아님 — 오히려 실용성의 증거).

**스크립트 재료** = `testFiles[].path`(열거) · `header`·`headerPresent`·`specRefs`(B) ·
`envFlags`(C) · `nameFlag`(D). 미탐·오탐은 검사별로 이렇게만 정의한다 — **flag 검사(B·C·D)의
«의미 판정»(인용이 요구를 적절히 담았는가·이름이 충분히 자기설명적인가)은 r20 §2 설계상
사람 몫이므로 정확도 지표에서 제외**하고, 발생 건은 실용성 부수 기록으로만 남긴다:

| 검사 | 미탐 (치명) | 오탐 (기록) |
|---|---|---|
| A | — (hard, §3의 일치 지표로 잰다) | — |
| B | 자체 테스트 **열거 누락**, 또는 실재 선두 헤더의 **오추출**(있는 헤더를 null로 / 무관 주석을 헤더로) | 헤더 부재 플래그가 재확인 결과 헤더 실재 |
| C | 확정 환경 의존 단언이 `envFlags`에 부재 | 플래그가 재확인 결과 환경 비의존 |
| D | 열거 누락 (이름 판정 자체는 의미 판정) | 제네릭 플래그가 재확인 결과 자기설명적 |

## 3. 지표 — 사전 등록 (결과 본 뒤 변경 금지)

| 지표 | 정의 | 기대 | 어긋나면 |
|---|---|---|---|
| **A 일치** | 스크립트 A verdict == 사람 판정. 대조값은 **pass/none/fail 3종** — `run-error`의 처분은 §5로 일원화 | 대조 가능 라운드 전부 일치 | 먼저 **원인 격리**: 앱 배선 실행 vs 임시 config 실행을 재현 대조. 실행 전략(고정값) 차이로 확인되면 «기지 한계»로 기록(고정값 변경은 r20 §6-4 절차 + 기지값 4앱 재검 조건). 스크립트 자체 결함으로 확인된 것만 §5 수정 경로 |
| **미탐 (B·C·D)** | §2.3 표 | **노출된 검사에서 0건.** 표본에 해당 위반이 없던 검사는 «0건»이 아니라 **«미검증»**으로 기록한다 (노출 정의: B는 인용 없는 테스트 파일 ≥1, C는 비주석 환경 의존 구문 ≥1, D는 일회용 이름 ≥1 — 그라운드 트루스 확정 집합 기준) | 1건이라도: 해당 검사를 보조 도구로 강등, r20 §6-4 절차로 v2 개정 |
| **오탐률 (B·C·D)** | 플래그 중 비위반 비율 | 기록만 (flag 설계상 허용) | 과반이 오탐인 검사는 실용성 감점으로 기록 |
| **실용성 ①** | JSON+콘솔 요약만으로 1차 판정이 끝난 라운드 수 (원문 열람이 필요했던 건수·사유 기록) | 4/4 | 부족했던 정보를 콘솔 요약 개선 후보로 기록 |
| **실용성 ②** | 판정 소요 단계 수 — r18 §2의 수동 절차(육안+grep) 대비 | 감소 | 정성 기록 |

**사전 등록 문장**: **채택 판정은 각 라운드 최초 verify JSON과 박제된 `human-*.md`의
«첫 대조»에만 근거한다.** A 전 라운드 일치 + 노출된 검사의 미탐 0이면 verify-tdd를 tdd
산출물 판정의 **1차 도구로 채택**한다. 이후 스모크·실사용의 육안 판정 축소(플래그 + 재료
재확인으로)는 **미탐이 실제 검증된 검사에만** 적용한다 — 미검증 검사는 «오탐 방향만 검증됨»
으로 기록하고 육안 전수를 유지하며, 이후 실전에서 자연 발생 위반의 미탐 0이 확인되는 시점에
축소로 전환한다. 미탐이 1건이라도 나오면 해당 검사는 «도구가 재료를 주되 육안 전수가 남는»
보조 지위로 강등하고 개정을 검토한다. **평가 중 스크립트를 수정한 경우, §5의 재실행·재대조는
회귀 확인 기록일 뿐 채택 판정의 입력이 아니다** — 수정판의 정확도 주장은 새 표본(새 런)을
요구한다(§0-1의 순환 금지가 여기에도 적용된다).

## 4. 절차 (1~2세션)

1. **시드 재구성** — 기존 스모크는 시드를 커밋하지 않았다(48c674a·17a363e에 산출물만 — 실물
   확인). 이번에는 `framework/verify-eval/seed/`로 **커밋해 재현성을 남긴다**.
   - **s1**: s1-ctrl 구성에서 `src/textkit.ts`를 스텁으로 교체, package.json·lockfile·tsconfig 유지.
   - **s2**: **vite 템플릿 재스캐폴드 금지** — 원 시드는 템플릿이 아니라 exp* seed 사본
     조정본이다(r18 §3-1). 현 s2 산출물에서 package.json(name만 시드명으로, 에이전트가 추가한
     `test` 스크립트 제거)·lockfile·tsconfig*·vite.config.ts·index.html·public/·src/assets/·
     App.css·index.css·main.tsx를 유지하고, 에이전트 산출물(TagInput.tsx·`*.test.tsx`·
     vitest.config.ts·dist/)을 제거하며, App.tsx는 exp* seed 원본을 r18 §3-1과 동일하게
     중립화해 재구성한다(동결 원본은 복사만 — 절대 규칙 1).
2. **런 4회** — 각 런의 사이클: **① 스크래치 단독 부모에 시드 복사(§2.1 격리) → ② `npm ci`**
   (`npm install` 금지 — r20 §5-6 lockfile 보호. 프롬프트의 «설치됨» 전제를 참으로 만드는
   단계다 — sent-s1·s2 첫 줄이 이를 전제한다) **→ ③ 런(전경 단독 — r18 §3-3) → ④ 산출물을
   `framework/verify-eval/<label>/`로 이동.** 런 규약은 기존 그대로(Git Bash · stdin 프롬프트 ·
   `--safe-mode --model opus --effort xhigh` · `--permission-mode acceptEdits
   --allowedTools Bash PowerShell`). **T군 주입물은 런 시작 전 리포 루트에서 읽어 비어 있지
   않음을 확인한 변수로 전달한다** — cwd 의존 상대경로는 격리 실행과 조합하면 조용히 빈
   처치가 되므로 금지: `SKILL=$(cat framework/skills/tdd/SKILL.md); [ -n "$SKILL" ] || 중단`.
   세션 원문 → `runs/<label>.json` + stderr.
3. **세션 로그 사후 점검** — §5의 무효 조건 2종(노출·denials)을 logprobe 관행으로 점검하고,
   T군 테스트 0개는 «안 만듦»/«만들고 지움»을 가른다(§5).
4. **육안 판정 4건** → `runs/human-<label>.md` (A는 §2.2-2 절차로 실행 포함) → **커밋(박제)**.
5. **계측기 준비** — verify JSON 기록 위치가 `framework/smoke/runs/` 고정이므로 **세 번째
   인자 `[out-dir]`을 추가한다**(기본값 현행 — 기존 사용 무변경. 판정 로직 무변경의 확장이라
   patternListVersion과 무관, 이 문서가 사유 기록). **인자 추가 직후 `--selftest` + 기지값
   4앱을 기존 2-인자 호출로 재실행해 기대값 불변을 확인한 뒤에만 평가 verify에 착수한다**
   (r20 §12의 «수정 후 기지값 재생성·재확인» 관행 계승). 불변이 아니면 원복 후 재시도.
6. **verify 4회** → `framework/verify-eval/runs/verify-<label>.json` (verify 직전 `npm ci`
   재실행 — 에이전트가 트리를 바꿨을 수 있으므로 lockfile 상태 재보장).
7. **대조표 작성(첫 대조)** → §3 사전 등록 문장 판정 → 결과는 다음 rN에 기록, 커밋.

**예상 규모**: 에이전트 런 4회(스모크 실측 $0.34~0.71/런) ~$2, **무효 재실행 1~2회 발생 시
$2~4** · 판정은 로컬 · 1~2세션.

## 5. 무효·재실행 규정 (사전 등록 — 결과 본 뒤 추가·완화 불가)

- **노출 점검**: 라운드 종료 후 세션 로그에서 `framework/verify-tdd.mjs`·`framework/skills/`·
  `framework/smoke/runs/`·`framework/verify-eval/runs/`의 열람(Read·cat·type 류 도구 호출)이
  검출되면 **해당 라운드 무효, 재실행.** §2.1 격리가 1차 방어이고 이 점검은 2차다 — 결과를
  본 뒤에는 이 조건을 추가할 수 없으므로(절대 규칙 5) 지금 등록한다.
- 출력 JSON의 `permission_denials` 비어있지 않음 = 무효 재실행 (기존 런 규약). **재실행은 새
  라벨 디렉터리에서**(`e2b-*` 식), 변이된 디렉터리는 실측 원문으로 보존한다(r18 §1-2·§3-3).
- **T군 테스트 0개는 즉시 무효가 아니다** — logprobe로 가른다(r18 §3-3): «안 만듦» = 문안
  도달 실패로 무효 재실행(r16 §3-1), «만들고 지움» = **유효** — A `"none"` 대조 재료이자
  종료 상태 판정의 정당한 표본. C군 자산 0은 정상 데이터.
- **verify `run-error`(exit 1)의 처분 일원화**: 원인이 계측 측(vitest 미설치·임시 config 오류
  류)이면 해소 후 재실행(점수 아님). 원인이 **산출물 자체**(예: hang 테스트)로 확인되면
  라운드 무효가 아니라 **해당 라운드 A를 «대조 제외»로 기록**하고 B·C·D 재료만 쓴다 —
  §3 A 지표의 분모에서 빠진다.
- **평가 중 스크립트 결함 발견 시**: 발견 시점의 판정 JSON·사람 판정을 먼저 커밋(박제) →
  수정(패턴 변경이면 §6-4 사유 기록 + patternListVersion 증가) → 전 라운드 verify만 재실행
  (사람 선판정은 스크립트와 독립이므로 재사용) → **재대조는 회귀 확인으로만 기록, §3 채택
  판정의 입력이 아니다.** 여기서 «스크립트 결함»은 **판정 산출 이전 단계의 계측 실패**
  (크래시·JSON 파싱 오류·열거 오류 — r20 §12-2류)만이다. **패턴·휴리스틱 미비로 위반을 놓친
  것은 결함이 아니라 미탐(측정값)이며 §3대로 처리한다.**

## 6. 함정·리스크 (미리 등록)

1. **개발 셋 재사용 금지** — 기지값 4앱·음성 픽스처를 정확도 표본에 넣지 않는다(§0-1).
   같은 이유로 평가 중 수정된 스크립트의 정확도 주장에 평가 4런을 재사용하지 않는다(§3).
2. **실험자 단일·비맹검** — 같은 실험자가 선판정과 대조를 다 한다. 방어는 선기록 커밋
   하나뿐이고, 이것은 순서 조작만 막지 인지 편향은 못 막는다. 한계로 정직하게 기록한다.
3. **패턴 공유 오염** — 육안 C 판정을 스크립트 패턴으로 하면 같은 미탐을 공유한다.
   §2.2-3의 «정의 기준 통독»이 방어다.
4. **재료 빈곤** — 확장 조건을 지금 정의한다: 4런 종료 시 T군 테스트 파일 합계가 **6개
   미만**이면 T 1런 추가(`e3-tdd`, 파일이 적었던 과제 쪽). **B·C·D 전 검사의 노출이 0이면
   C군 1런 추가(`e3-ctrl`)를 인정한다** — 단 §3의 «미검증» 기록만으로도 잘못된 채택은
   차단되므로 이 확장은 선택이다.
5. **같은 과제 재사용의 낮은 다양성** — 산출물이 기지값과 유사할 수 있다. 세션 분산이 유일한
   변주원이고, 제3 과제 추가는 미결(§7-1)로 남긴다.
6. **그룹 차이 과해석 금지** — 그룹당 1~2런이다. T/C verdict 차이는 부수 기록까지만 하고
   효과 문장을 쓰지 않는다.
7. **판정 도구 채택의 범위** — 사전 등록 문장이 채택해도 그 범위는 «tdd 산출물 판정»이다.
   sdd·edd 산출물 판정(SPEC.md·평가 파일)은 별도 도구의 몫(r20 §7-1).
