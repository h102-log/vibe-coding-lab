# KF1 라운드 3 계획서 — 게이트 델타 분기 (델타 루프를 자동으로)

## 0. 요약

`plankf1delta.md` §5 WBS의 **마지막 라운드**. `spec-gate.mjs`의 `decide()`에 델타 분기를 넣어
pre에서 D1·D2를, Stop에서 D1~D5를 보고, **통과하면 그 자리에서 병합**한다. `commands/spec.md`에
`delta` 분기를, `README.md`에 1행+한계 1줄을 더한다. 새 파일은 만들지 않는다 — R2가 만든
`inspectDelta`·`mergeDelta`를 import해 시점만 가른다(`spec-verify`의 `inspect`와 같은 방식).

**이걸 해야 하는 이유**: 지금 `merge`는 사람이 친다. 델타 루프의 값은 «커맨드 1회 외에 중단이
없다»는 데 있는데(계획서 §7 ②), 사람이 매번 병합을 기억해야 하면 그 예산이 깨진다.

## 1. R2가 바꾼 것이 R3에 미치는 영향

| `plankf1delta.md`의 문언 | 실물 | R3에서 |
|---|---|---|
| §4-6 stop: «`mergeDelta` → 병합 결과 `inspect()` 위반 0 확인 → 쓰기» | 그 조건은 성립하지 않아 **«check별 위반 수 증가 없음»으로 바뀌었고, `mergeDelta` 안에 이미 들어가 있다** | 게이트는 **따로 검사하지 않는다**. `try/catch`로 예외만 받는다 |
| §6 G17·G18 기대 exit 0 | 그대로 유효 — R2 손검증에서 웜·콜드 둘 다 위반이 늘지 않았다 | 기대값 무변경 |
| §4-5 «ADDED `U*`» | 6열 표 행으로 확정 | G 재료의 U는 표 행으로 쓴다 |

## 2. 목표 / 비목표

**목표**

1. 델타가 있으면 델타가 활성 문서다 — pre에서 본 SPEC의 C1~C3을 **병행 검사하지 않는다**.
   (콜드스타트 누적 SPEC은 점검표가 없어 C2에 영원히 막힌다 — `plankf1delta.md` §10 #3)
2. Stop에서 D1~D5 전건 통과 시 **자동 병합**. 재진입에서도 병합은 수행한다.
3. 병합 실패가 무한 루프가 되지 않는다 — 초회 exit 2, 재진입 exit 0 + 경고.
4. 델타 없는 기존 경로는 **한 글자도 다르게 동작하지 않는다**(기존 selftest 10건 기대값 무변경).

**비목표**

- `hooks.json` 무변경. 델타 분기는 게이트 내부 로직이다.
- Edit을 막지 않는다. SG 번호 부여(KF4)·볼륨(KF5)·드리프트(KF3)는 여기 없다.
- 새 기능/수정 구별을 기계가 하지 않는다.

## 3. 설계

### 3-1. `decide()` 반환 타입을 바꾼다 (필수)

현재 `decide()`는 «차단 메시지 문자열 또는 `null`»을 반환하고, CLI가 `if (block) { 로그; stderr;
exit 2 }`를 한다. 이 구조로는 R3에 필요한 두 가지를 표현할 수 없다:

- **메시지는 내되 exit 0** (병합 실패 재진입 — §3-4)
- **차단이 아닌 로그** (병합 성공 기록 — §3-5)

→ 반환을 항상 객체로 바꾼다. `decide`를 import하는 곳은 없다(확인함 — `spec-gate.mjs` 자신뿐).

```js
// { msg: string|null, exit: 0|2, log: object|null }
const d = decide(mode, ev);
if (d.log) appendLog(ev, d.log);      // 실패해도 게이트를 막지 않는다(현행 그대로)
if (d.msg) console.error(d.msg);
process.exit(d.exit);
```

기존 차단은 `{msg, exit: 2, log: {t, mode, file, first}}` — **로그 형식은 그대로 유지한다**
(`.specgate-log.jsonl`은 실사용 관측 자산이다, FIELD-GUIDE §1).

### 3-2. 결정표 (`plankf1delta.md` §4-6 그대로, 실물 표기로)

| 모드 | 델타 | SPEC | 판정 |
|---|---|---|---|
| pre (SRC) | 있음 | 무관 | `inspectDelta` → **D1·D2 위반 시 exit 2**. D3~D5는 통과(D4·D5는 stop 몫) |
| pre (SRC) | 없음 | 있음 | 기존 그대로 — C1~C3 |
| pre (SRC) | 없음 | 없음 | 기존 차단 + 메시지에 «기존 코드 수정이면 `/spec delta`» 한 줄 추가 |
| pre (비SRC) | 무관 | 무관 | 통과 — SRC 필터가 **델타 검사보다 먼저**다(`.md`는 대상이 아니라 델타 자신을 쓰는 Write는 안 막힌다) |
| stop | 있음 | 무관 | D1~D5 전건. **위반**: 재진입이면 통과, 아니면 exit 2. **통과**: 재진입 여부와 무관하게 병합 |
| stop | 없음 | 있음 | 기존 그대로 — C1~C5 (+재진입 가드) |
| stop | 없음 | 없음 | 통과(기존) |

`PRE = new Set(['C1','C2','C3'])`의 자매로 `PRE_D = new Set(['D1','D2'])`를 둔다.

### 3-3. 재진입 가드를 «차단 전용»으로 옮긴다

지금은 `stop` 첫 줄이 `if (ev.stop_hook_active) return null;`이다. 이대로면
«위반으로 1회 차단 → 대조 채움 → 재정지»라는 **정상 흐름에서 병합이 영영 안 일어난다**.
가드를 «차단 직전»으로 내리고, 병합은 재진입에서도 수행한다. 반복 차단형 무한 루프는 그대로 막힌다.

### 3-4. 병합 실패 2분기

`mergeDelta`가 던지거나(위반 증가) `writeFileSync`가 실패하면(권한·경로 점유):

- **초회** — `{msg: '병합 실패: <이유> — SPEC.delta.md는 남겨뒀다', exit: 2, log: null}`
- **재진입** — 같은 메시지, `exit: 0`. 쓰기 권한 오류·병합 버그처럼 **에이전트 행동으로 해소되지
  않는 결정론적 실패**가 Stop마다 exit 2를 반복하면, 재진입 가드가 막으려던 무한 루프가 병합
  경로로 되살아난다.

복구 경로는 잔존 델타를 사람이 `merge`로 돌리는 것이다(그래서 델타를 지우지 않는다 — 조용한 유실 금지).

### 3-5. 병합 성공 로그

```json
{"t":"...","mode":"merge","added":2,"modified":1,"removed":1,"coldstart":false}
```

기존 `appendLog`를 그대로 쓴다(차단 기록과 같은 파일·같은 실패 정책).

### 3-6. `commands/spec.md` delta 분기

`plankf1delta.md` §4-7 골자대로 3항목. **커맨드 수는 늘리지 않는다**(진입로는 `/spec` 하나).
`allowed-tools`의 `Bash(node:*)`는 그대로면 `spec-delta.mjs`도 돌릴 수 있다 — 확인만 한다.

### 3-7. `README.md`

「무엇이 들어오나」 표에 커맨드 `/spec delta` 1행, 「검사」 절에 D1~D5 표 1개, 한계에
«새 기능을 수정으로 위장하면 델타 1장으로 pre를 통과한다»(`plankf1delta.md` §9 #6) 1줄. **코드가 돈 뒤 말미에** 쓴다.

## 4. R2에서 넘어온 미비 1건 (이 라운드에서 닫는다)

**`## 대조` 절 이름이 다르면 verify는 통과하고 merge가 실패한다.** D1은 3절(ADDED/MODIFIED/
REMOVED)만 요구하고 대조 절 이름은 검사하지 않는다. D4는 «정의 줄 이후 어디서든 ID 재등장»을
보므로 MODIFIED 절 본문의 언급만으로도 통과한다. 반면 `mergeDelta`는 `## 대조` 절에서만 행을
읽으므로 그 경우 `rows = 0`이 되고, 병합 결과가 본 SPEC의 C4 위반을 늘려 **병합이 거부된다**.

**실측(2026-08-20)** — `## 대조`를 `## 검증`으로만 바꾼 델타로 확인했다:
`verify` **exit 0**(위반 0 · D4 1/1) → `merge` **exit 2**(«병합이 위반을 늘렸다: C4 0→1») ·
양쪽 파일 무변경. **안전망은 제대로 걸렸고 SPEC은 망가지지 않았다** — 문제는 메시지가 원인을
짚지 못한다는 것뿐이다.

→ `mergeDelta`에서 `rows.length === 0`이면 경고 1줄(«`## 대조` 절에서 읽은 행이 0이다 — 절 이름을 확인하라»)을
먼저 낸다. 검사기 쪽은 건드리지 않는다(D1에 대조 절을 더하면 기존 V 케이스 기대값이 흔들린다).

**M10** — 대조 절 이름이 다른 델타 → `merge` exit 2 · 원인 경고 · 양쪽 파일 무변경.

## 8. 한계 (반증 지점 병기)

1. **`decide()`가 파일을 쓰게 된다.** 판정 함수에 부수효과가 들어가는 것이고, «판정과 실행 분리»를
   지키려면 병합 지시만 반환하고 CLI가 쓰는 형태가 맞다. 짧은 쪽(§3-1)을 기본값으로 잡되
   **선택 대기**로 남긴다 — 번복 조건은 «decide를 다른 곳에서 부르고 싶어지는 사건 1건».
2. **델타 분기는 본 SPEC 요구를 약화시키는 통로다**(`plankf1delta.md` §9 #6 그대로). 새 기능을 «수정»으로 위장해
   델타 1장으로 pre를 통과할 수 있다. 게이트 철학대로 «작정한 우회»가 아니라 «그냥 시작해버리는
   것»만 막는다. 실사용 관측 항목(FIELD-GUIDE «미차단»).
3. **자동 병합이 SPEC.md를 망가뜨리면 되돌리는 건 git뿐이다.** `mergeDelta`의 «위반 수 증가
   없음»이 유일한 안전망이고, 그건 «검사가 보는 것»만 지킨다 — 문장이 엉뚱한 절에 놓이는 것은
   위반이 아니다(R2의 `ordered` 단언이 selftest에서만 그것을 본다).
4. **G22의 «디렉터리로 점유»가 Windows에서 기대대로 실패하는지는 미확인이다.** 안 되면 읽기전용
   속성으로 바꾼다 — 실패 경로를 못 만들면 G22·G23을 지우지 말고 **재료를 바꾼다**.

## 10. 이 라운드를 안 하고 KF3 R-A3을 먼저 할 수도 있다

R2가 `ids.modified`를 열어 KF3 R-A3(drift의 `modified` 범주)의 블로커가 사라졌다. 둘은 무의존이라
순서를 바꿔도 된다. **R3을 먼저 잡은 이유**는 R2 산출물(`merge`)이 지금 수동이라 값을 못 하고,
KF1 하나를 끝내야 «델타 루프»라는 물건이 처음으로 완성되기 때문이다. R-A3은 drift의 범주가 2→3으로
느는 개선이지 미완성 해소가 아니다.
