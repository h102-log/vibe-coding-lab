## 1. 결론 5줄

1. **§2(요구가 침묵한 지점을 명세 단계에서 포착)를 푼 프로젝트는 없다.** 24건을 실물 확인했고, "빠진 것을 기계적으로 드러내는 장치"를 가진 것은 4계열뿐이며 전부 **사람이 미리 적어둔 목록 안에서만** 작동한다. 요구 텍스트만 보고 "당신이 X를 말하지 않았다"를 도출하는 도구는 이 지형에 존재하지 않는다.
2. **그러나 F-08은 이미 남의 택소노미 칸에 이름이 있다.** spec-kit `clarify.md` 3단계 10범주 중 «Interaction & UX Flow → Accessibility or localization notes», BMAD의 «도메인 침묵 → open_questions[]» 규칙, adversarial-spec의 `accessibility-specialist` 페르소나, jasonkneen/kiro 템플릿의 `Accessibility: [...]` 빈칸 — 네 곳이 F-08이 떨어졌어야 할 자리를 명시한다. **exp4와의 차이가 「문안 강도」가 아니라 「칸의 유무」였을 가능성**이 이번 조사의 최대 수확이다.
3. **exp4의 «문안 개정으로는 못 닫힘»에 독립 통제 증거가 있다.** ask-or-assume은 동일 백본·동일 프롬프트로 «같은 에이전트에게 산문 리마인더»(UA-Single 61.20%)와 «별도 관측자 + 강제 제어»(UA-Multi 69.40%)를 갈라 **p<0.001**로 후자 우위를 보였다. 이 리포의 §2 다음 개입은 SKILL.md 문장이 아니라 **역할 분리**여야 한다는 외부 근거다.
4. **스타 수와 게이트 실재는 이 지형에서 역상관이다.** Superpowers(272k)는 훅이 SessionStart 컨텍스트 주입 1개뿐이고 결정론 차단이 0개, CCPM(8.3k)의 `validate.sh`는 96행 중 `exit`가 `exit 0` 하나, Night Market(328)의 «TDD gates block…»은 전 종료 경로가 `sys.exit(0)`이며 소스 주석이 자백한다. 반면 **진짜 Stop 훅 차단을 가진 것은 스타 4개짜리 bitcraft-apps/spec-first 하나**였고, 이 세션에서 직접 실행해 `{"decision":"block","reason":"Spec missing sections: risks"}`를 확인했다.
5. **차별점은 있다.** ① 택소노미(spec-kit) × exit code 게이트(spec-first 배선)를 결합한 사례가 없고, ② §2를 이진(specHit)보다 높은 해상도로 잰 사례가 SDD 도구 쪽에 없으며, ③ **상한(F-08까지 적힌 완전 명세) 팔을 둔 실험이 이 리포에도 남에게도 없다.** 셋 다 이 리포의 기존 하네스 사거리 안에 있다.

## 3. 각 후보 상세

### 1. github/spec-kit — §2 택소노미의 유일한 완성품, 단 마커가 아니라 clarify가 엔진

훔칠 것은 셋으로 좁혀진다. **(a) `templates/commands/clarify.md` 3단계**: 「Perform a structured ambiguity & coverage scan using this taxonomy. For each category, mark status: Clear / Partial / Missing」 — 범주는 **정확히 10개**(Functional Scope & Behavior / Domain & Data Model / **Interaction & UX Flow** / Non-Functional Quality Attributes / Integration & External Dependencies / Edge Cases & Failure Handling / Constraints & Tradeoffs / Terminology & Consistency / Completion Signals / Misc-Placeholders)이고, 3번 하위에 정확히 `- Accessibility or localization notes`가 있다. **exp4가 «전부 옮겨라»로 실패한 이유가 «무엇이 빠졌는지 열거하라»고 시키지 않았기 때문이라면, 이 택소노미가 바로 그 열거를 강제한다.** Partial/Missing인 범주만 질문으로 승격된다. **(b) `checklist.md`의 프레임**: 「Checklists are **UNIT TESTS FOR REQUIREMENTS WRITING**」 / 「If your spec is code written in English, the checklist is its unit test suite」, 예시 항목 197행이 문자 그대로 `"Are accessibility requirements specified for all interactive elements? [Completeness]"`다. **(c) clarify 9단계의 체크리스트 재평가** — before/after 스냅샷을 비교해 **Newly passing / Regressions(체크→미체크로 되돌아간 항목) / Still unchecked** 세 목록을 만들고 `"12/16 → 15/16 items passing"`으로 보고한다. 명세 레이어에 회귀 개념을 도입한 드문 사례로, exp2·exp3의 코드 자산 회귀 추적을 명세로 확장할 때의 참조다.

**가장 중요한 반전은 마커 쪽이다.** `specify.md` 122~128행이 `[NEEDS CLARIFICATION]`을 억제한다 — 「Make informed guesses based on context and industry standards」 + 3조건 충족 시에만 마킹 + **「LIMIT: Maximum 3 [NEEDS CLARIFICATION] markers total」**. 즉 **spec-template의 마커만 베끼면 exp4와 같은 문안형 한계에 그대로 걸린다.** §2의 엔진은 마커가 아니라 clarify의 택소노미 스캔이고, 이식할 때 둘을 분리해야 한다. 게이트 쪽도 정직하게 봐야 한다: 결정론 exit 1은 `check-prerequisites.sh`의 **파일 존재 검사뿐**이고, `implement.md` 56~87행의 체크리스트 게이트는 「STOP → yes/no 확인 → no면 halt」라는 **사람 확인 프롬프트**다. 이 리포의 `-p --permission-mode acceptEdits` 비대화형 런에서는 LLM이 스스로 yes로 넘어갈 가능성이 높아 게이트로 작동하지 않는다. 이식 경로 자체는 최상급이다 — `ClaudeIntegration`이 `registrar_config = {'dir': '.claude/skills', 'extension': '/SKILL.md', 'args': '$ARGUMENTS'}`로 **슬래시 커맨드가 아니라 네이티브 스킬로 설치**하고, `CANONICAL_TO_NATIVE`에 SessionStart/PreToolUse/PostToolUse/SessionEnd/UserPromptSubmit/Stop 훅 매핑이 이미 있다.

### 2. bitcraft-apps/spec-first — 스타 4개, 그런데 이 스윕에서 유일하게 진짜 게이트를 가졌고 F-08급을 실제로 잡았다

**게이트 배선을 직접 실행해 검증했다.** `hooks/hooks.json`의 Stop 이벤트 → 어댑터가 `REASON=$(bash "$SCRIPT" … 2>&1 >/dev/null) || jq -nc --arg reason "$REASON" '{decision:"block",reason:$reason}'` + 자신은 `exit 0`. Risks 섹션 없는 `.sf/spec.md`를 만들고 stdin을 파이프하니 `{"decision":"block","reason":"Spec missing sections: risks"}`가 나왔고, 추가 후 재실행하니 무출력 통과였다. (`2>&1 >/dev/null`은 stderr만 캡처하는 정상 관용구다 — WebFetch 요약기가 버그로 잘못 보고한 것을 정정한다.) **검사 본문은 무력하다** — `grep -qi "scope\|problem"` 3줄이 전부라 산문 한 줄 «There is no scope here, no acceptance of any risk whatsoever.»가 통과했고, `[ ! -f "$SPEC_FILE" ] && exit 0`이라 **spec.md를 안 쓰면 fail-open으로 조용히 통과**한다. **값어치의 대부분은 검사 본문이 아니라 배선에 있고, 그 자리에 `judge.mjs`·`mutation.sh` 판정을 꽂으면 v0.1의 Gate 층이 하루 만에 선다.**

§2 쪽은 더 흥미롭다. `workflows/spec.js`가 명세 작성을 scope·criteria·**risks** 3개 서브에이전트로 쪼개고, risks에게만 «Identify the blockers… **Challenge assumptions.** Essential edge cases only»를 `model:'haiku', effort:'low'`로 병렬 실행시킨다. **`examples/search-input/`의 입력 요구는 접근성에 완전히 침묵**했는데(«Show a clear button.»가 전부), `risks.md`가 «An icon-only button has no name for a screen reader → `aria-label="Clear search"`»를 스스로 뽑아냈고 → `criteria.md` #6 → `spec.md` Scope/In → `SearchInput.test.tsx:89` `getByRole("button", { name: "Clear search" })`까지 **끝까지 전이됐다**. 2026-08-04 실제 런 산출물이라고 examples/README.md가 명시한다. **다만 n=1이고 손질 여부를 외부 검증할 수 없으므로 «이 장치는 F-08을 잡는다»가 아니라 «잡은 관측이 1건 있다»가 정확한 표현이다.** 두 개의 결정적 흠도 기록해 둔다: 그 a11y 항목이 게이트되는 `## Acceptance Criteria` 8개 안에는 안 들어갔고(포착 경로와 게이트 경로가 분리돼 있다), 같은 워크플로의 scope 에이전트는 정반대로 «If a requirement is unclear, **exclude it**», 합성 단계는 «Add nothing the inputs do not state»라고 민다.

### 3. fecarrico/A11Y.md — 침묵에 이름과 자리를 주고, 그것을 exit code로 지킨다

이번 조사에서 §2 «어휘»의 완성형이다. `templates/REPORT.md`의 마킹 legend 원문: 「`[x]` verified, with the evidence described beside it · `[!]` verified and **failed** · `[~]` partially verified, with what is missing written down · `[ ]` **not verified** — the reason MUST be written beside it. Marking `[x]` without reproducible evidence invalidates the whole report.」 그리고 「Overall status is CONDITIONAL — never PASS — while any `[ ]` or `[!]` remains.」 **`[NEEDS CLARIFICATION]` 단일 마커보다 표현력이 높다 — 「모른다 / 반쯤 안다 / 알았고 실패했다」가 구분된다.** 그 legend를 지키는 것이 `tools/verify-a11y.py`(281행, stdlib 전용)의 `report-status` 체크로, PASS라고 써놓고 미해결 마크를 달고 있으면 error를 세고 `return 1 if errors and not args.warn_only else 0`으로 끝난다. **judge.mjs가 «구현»을 채점한다면 이건 «명세 자체»를 채점하는 오라클이고, 이 리포에 아직 없는 종류의 계측기다.**

**중대 정정: `control-has-associated-label`은 `recommended`·`strict` 양쪽에서 기본 `'off'`다**(플러그인 config 객체를 덤프해 확인). 명시적으로 `'error'`로 켜야 한다. 그리고 **이것을 도입하고 «§2 갭을 닫았다»고 기록하면 실험 기록이 오염된다** — 정적 JSX 패턴으로 판정 가능한 a11y 결함군에만 듣고, 명세가 침묵한 다른 종류(도메인 규칙·상태 전이·비기능 성능)에는 무력하다. **«표적 결함 1개에 대한 우회로»라고 정확히 적어야 한다.** npm 최신 릴리스가 2024-10-26(6.10.2)로 약 22개월 정체이므로 «안정적이지만 성장하지 않는 의존성»으로 취급하고, `package.json` 수정이 불가피하므로 **반드시 새 트랙 디렉터리에서만** 해야 한다(절대규칙 1·2).

## 5. §2(침묵 지점 포착)에 대한 지형 판정

**판정: 아무도 풀지 않았다. 부분해가 4계열 있고, 그 4계열의 조합·계측·상한 측정이 전부 공백이다.**

**(a) 택소노미형** — spec-kit 10범주, adversarial-spec 페르소나 10종, CCPM PRD 9섹션, jasonkneen/kiro 3슬롯, Tessl 5행. **«훑을 칸을 열거해 Missing을 강제 노출»한다.** 이 리포에 가장 직접적이다 — F-08은 spec-kit 3번 칸에 정확히 대응한다. **한계는 원리적이다: 칸을 사람이 미리 적어야 하고, 적을 수 있었으면 명세에도 적었을 것이다.** 이 계열은 §2를 푸는 게 아니라 **한 번만 풀면 되게(프로젝트 생애 1회) 상각한다.** 그게 값어치가 없다는 뜻은 아니다 — exp4는 그 상각조차 시도하지 않았다.

**(b) 어휘형** — A11Y.md 4값 마킹, BMAD `open_questions[]`/`assumptions[]` 영속 필드, kiro `## Open Questions`, agent-spec `unproven`. **탐지하지 않고, 침묵에 이름과 자리를 준다.** specHit 1/4 상황에서는 이쪽이 현실적이다 — **놓친 것을 0으로 만들 수 없다면 놓친 것의 목록이라도 자산으로 남는다.** A11Y.md만이 이 어휘를 exit code로 지킨다.

**(c) 아키텍처형** — ask-or-assume 관측자 분리, spec-first 병렬 risks 서브에이전트, adversarial-spec 다중 페르소나. **열거하지 않고, «의심하는 역할»을 «쓰는 역할»에서 분리한다.** **이 계열만이 exp4의 실패 모드에 대한 통제 증거를 가졌다**(UA-Single 61.20 vs UA-Multi 69.40, p<0.001). spec-first는 그 위에 «실제로 F-08급 침묵을 잡아 테스트까지 전이시킨» 예제를 1건 커밋해 두었다. **이 리포의 다음 개입은 여기여야 한다.**

**(d) 우회형** — jsx-a11y, axe-core. **§2를 풀지 않고 특정 침묵의 영향을 0으로 만든다.** F-08이 정확히 그 사거리에 있음을 이 세션에서 실측했다.

**아무도 하지 않은 것 셋이 곧 차별점 후보다.**
1. **택소노미 × exit code.** spec-kit 택소노미에는 exit code가 없고, A11Y.md의 exit code는 a11y 한 축에만 걸리며, StrictDoc의 exit code는 «이미 만들어진 행의 빈 칸»만 본다. **«10범주를 전부 Clear/Partial/Missing으로 찍지 않으면 exit 1»을 구현한 곳이 없다.** 구현 난도는 낮다.
2. **§2의 계측 해상도.** SDD 도구 쪽에 §2 지표가 없다(spec-kit의 «12/16 → 15/16»이 유일한 근접). 학계에는 있지만(KQC·ATC·Comm Rate·Good Question Rate) 배포된 도구가 없다. **이 리포의 specHit 1/4는 사실상 1비트라 개선 신호가 해상도 아래로 깔려 있다** — REPORT5가 «중앙값 3/4»에서 막힌 것이 지표 해상도 탓일 가능성을 아직 배제하지 못했다.
3. **상한 측정.** 5개 트랙 어디에도 «F-08까지 전부 적힌 완전 CONTRACT» 팔이 없다. **상한이 없으면 3/4가 나쁜 점수인지 판정할 수 없다.** ask-or-assume은 Full(70.80)·Hidden(54.80) 두 극단을 먼저 박고 그 사이에서 처치를 비교했다 — 이 리포가 안 한 유일한 설계 요소이고, 비용이 가장 싸다.

한 가지 회의적 관측도 남긴다. **학계 쪽 보고(요약 경유)는 «도메인 접지 없는 LLM은 재현율만 높고 정밀도가 낮아 과다 플래그를 낸다»고 일관되게 말하고, ask-or-assume은 «모델이 잘 명세된 것과 덜 명세된 것을 구분하지 못한다»고 보고한다.** §2 장치를 세게 걸면 멀쩡한 명세에까지 질문을 남발하는 실패 모드가 따라오고, 실사용에서 그런 프레임워크는 버려진다. **«거짓 되묻기(over-asking)»를 사전 등록 계측 항목으로 넣지 않으면 v0.1은 정확히 그 방향으로 실패한다.**

## 7. 다음 행동 3개

### 행동 1 — exp5 설계: 단일 변수를 «§2를 누가 하는가»로 잡고, 상한 팔을 처음으로 넣는다

exp4가 «문안 강도»를 변수로 잡아 상한에 걸렸다. **다음 변수는 «역할»이어야 한다** — ask-or-assume의 UA-Single(61.20) vs UA-Multi(69.40, p<0.001)가 이 축이 살아 있음을 통제 대조로 보여줬고, spec-first가 CC에서의 구현형(병렬 서브에이전트)을 이미 갖고 있다. 팔 구성 4개:

- **(u) 상한** — F-08 문장까지 적힌 완전 CONTRACT. **5개 트랙 어디에도 없던 팔이고, 없으면 3/4가 나쁜 점수인지 판정할 수 없다.**
- **(d) 대조** — exp4 재현(단일 에이전트 + 문안).
- **(e) 택소노미** — 명세 작성 후 spec-kit `clarify.md` 3단계를 **3범주로 발췌**(Interaction & UX Flow / Non-Functional Quality Attributes / Edge Cases & Failure Handling)해 각 칸에 Clear/Partial/Missing을 강제로 찍게 한다. `- Accessibility or localization notes` 한 줄 포함 여부가 exp4와의 **최소 개입 차이**다.
- **(f) 역할 분리** — spec-first 방식으로 명세 작성을 scope/criteria/**risks** 3분할하고 risks에게만 «Challenge assumptions. Essential edge cases only»를 준다.

주 판정은 **F-08 survived 여부**, 부 판정은 §2 3분해(아래 행동 2). 처치물은 `--safe-mode` 제약상 `--append-system-prompt` 본문 주입이고, 반드시 **새 트랙 디렉터리에 자산을 복사**한다(절대규칙 1). 컨텍스트 예산 통제를 위해 택소노미는 발췌본을 동결 해시하고, spec-kit `specify.md`의 «Maximum 3 markers» 억제 문구는 **가져오지 않는다**(exp4와 같은 함정).

### 행동 2 — 지표 해상도를 올리고, 게이트를 «같은 검사기 두 모드»로 배선한다

**지표**: specHit 이진을 3분해한다 — **(탐지) 명세에 그 문장이 생겼는가 / (전이) 그 문장이 테스트로 갔는가 / (반영) 구현에 들어갔는가.** Ambig-SWE의 3분해와 동형이고, exp4가 «§4가 아니라 §2»라고 결론낸 근거를 런타임 산출물로 확인하게 해준다. 여기에 **agent-spec의 `unproven`을 judge.mjs에 도입**해 「명세에 문장이 없어 판정 불가」를 fail과 분리하면 §2 갭이 사후 집계가 아니라 verdict에 직접 뜬다. 되묻기 루프를 측정할 거라면 ClarEval의 **ATC(낮을수록 우수)**를 짝으로 반드시 같이 재서 «무조건 많이 물어라»로의 퇴화와 **거짓 되묻기(over-asking)**를 사전 등록 실패 항목으로 박는다. (계측기 변경은 `FROZEN3.md` §7.1 화이트리스트 밖이므로 **새 트랙에서만** 하고, 기존 트랙 재측정은 하지 않는다.)

**게이트**: spec-first의 Stop 훅 어댑터 3줄을 그대로 가져오고 — `REASON=$(bash "$SCRIPT" … 2>&1 >/dev/null) || jq -nc --arg reason "$REASON" '{decision:"block",reason:$reason}'` + `exit 0` — 검사 본문 자리에 «§2 택소노미 3칸이 전부 찍혔는가»를 넣는다. **강도 A/B는 A11Y.md의 `--warn-only` / OpenSpec의 `strictMode ? errors===0 && warnings===0 : errors===0` 패턴으로 동일 코드에서 낸다.** 그리고 spec-first에서 배운 두 구멍을 처음부터 막는다: **fail-open 금지**(`[ ! -f "$SPEC" ] && exit 0`을 exit 1로 뒤집기, EvilGenie의 「File missing or unreadable = modified」), **게이트 스크립트마다 단위 테스트 첨부**(Tessl·spec-first가 둘 다 하는 규율). 마지막으로 **포착 경로와 게이트 경로를 반드시 이어붙인다** — spec-first의 실패가 정확히 여기였다(risks가 잡은 a11y 항목이 게이트되는 체크리스트에는 안 들어갔다).

### 행동 3 — F-08 우회로를 **별도 트랙으로 분리 기록**하고, 질문 자체를 바꾼다

`jsx-a11y/control-has-associated-label: 'error'` 3줄이 이미 F-08을 exit 1로 죽인다는 것을 이 세션에서 실측했다(21파일 오탐 1건). **그러나 이것을 §2 트랙에 섞으면 실험 기록이 오염된다** — «§2 갭을 닫았다»가 아니라 «표적 결함 1개에 대한 층위 우회»다. 새 트랙 디렉터리를 만들고(기존 `exp*/`의 `package.json`을 건드리면 동결 위반), 기록할 명제를 이렇게 바꾼다: **«§2 문안을 어떻게 고치나»에서 «이 결함은 어느 층에서 잡는 게 싼가»로.** 세 층을 같은 F-08에 대해 비용 대비로 비교한다 — (a) 명세 층(택소노미/역할 분리, 토큰 비용 큼), (b) 정적 린터 층(설정 3줄, 비용 0, 사거리 좁음), (c) 런타임 층(axe-core, jsdom 동작 미검증).

이때 **비용을 처음으로 1급 지표로 올린다.** 5개 트랙은 전부 점수만 쟀고 토큰·시간을 안 쟀는데, §2 장치는 전부 토큰을 크게 먹는 종류(ask-or-assume은 매 턴 관측자 호출로 **턴 예산 3배**)라, 비용 없이는 «이득 없음»과 «비용만 늘고 이득 없음»이 구분되지 않는다. `logprobe.mjs`에 단계별 input/output/cache 토큰과 stop reason·타임스탬프를 추가하고, 보고 형식은 **(비용, 품질) 쌍**으로 고정한다. 그리고 v0.1 문서에 **적용 경계 절**을 명시한다 — 문헌 리뷰(2605.01160, 1차 실증 아님)의 조절 변수 3종(task abstraction / codebase maturity / developer experience)이 「언제 이 프레임워크를 쓰지 말아야 하는가」의 뼈대가 된다. 실험 리포 출신 프로젝트가 스스로 적용 경계를 선언하는 것은 강점이 될 수 있다.
