## 1. 1순위 지표 — `mutationScore`

**정의**: 동결된 결함 4개 중, **산출물에 남은 자체 테스트가** 실패로 잡아낸 개수.
AC 오라클이 아니라 **에이전트가 남긴 테스트**로 잰다.

| 조건 | 앱 | `F-07` 영속 | `F-08` 접근성 이름 | `F-03` 토글 | `F-06` 필터 | **score** |
|---|---|---|---|---|---|---|
| a | `todo-a2t` · `a2tb` · `a2tc` | none | none | none | none | **0/4** ×3 |
| b | `todo-b2t` · `b2tb` · `b2tc` | none | none | none | none | **0/4** ×3 |

| **d** | `todo-dc` | killed (2) | **survived** | killed (7) | killed (5) | **3/4** |

`FROZEN2.md` §8.2가 이 경우에 대해 미리 등록한 문장:

> 대가는 비용 (a) 대비 4.99배 · (b) 대비 1.16배다. n=3, 유의성 주장 없음.**

### 1.1 지표가 자명하지 않았다 — `F-08`을 3/3 놓쳤다

이 실험의 값은 전적으로 "mutationScore가 자명하지 않다"에 걸려 있었다(r7 §7). **자명하지 않았다.**
(d)는 테스트를 남겼고, 그 테스트는 3개를 잡았고, **하나를 일관되게 놓쳤다.**

놓친 것이 하필 `F-08`(삭제 버튼의 접근성 이름 제거)이라는 점이 이 실험에서 가장 값진 관측이다.
**AC-07(영속)과 AC-08(접근성 이름)은 계약에 안 적힌 두 요구이고, SDD가 겨눈 표적이 정확히 그 둘이었다.**
(d)는 그중 하나만 테스트로 옮겼다.

**세션 로그와 산출물을 대조한 결과, 원인은 "SDD가 못 끌어냈다"가 아니다.**

| 앱 | `SPEC.md`가 접근성 이름을 문장으로 적었나 | 자체 테스트가 그것을 검사했나 |
|---|---|---|
| `todo-d` | **적었다.** U-38 "`todo-input`, 토글, 삭제, 필터 버튼에는 한국어 접근성 이름(placeholder / aria-label)이 있다" | **안 했다** |
| `todo-db` | **안 적었다.** `aria-pressed`(필터 선택 상태)만 있고 삭제 버튼 이름은 없다 | 안 했다 |
| `todo-dc` | **적었다.** U18 "삭제 버튼의 접근 가능한 이름은 '삭제', 체크박스의 접근 가능한 이름은 그 항목의 제목이다" | **안 했다** |

`todo-d`의 U-38에는 이런 단서가 붙어 있다:

> `이름 문자열 자체는 테스트가 판정하지 않는다. [추론]`

**에이전트가 그 문장을 테스트 대상에서 명시적으로 제외했다.** `todo-dc`는 한술 더 떠서 SDD §3(완료 전 대조)을
완주했다 — `SPEC.md` 대조표에 `U18 | TodoItem.tsx:17 aria-label={todo.title}, :22 버튼 텍스트 "삭제" | ✅`로
**코드 위치까지 지목**했다. 문장도 있고 구현도 있고 대조도 했는데 **테스트만 없다.**

결정적 확인: **3런의 자체 테스트에서 `getByRole`/`getAllByRole` 사용은 0건이다.**
접근성 이름을 판정할 수 있는 유일한 경로를 아무도 쓰지 않았다. `aria-pressed`는 셋 다 검사했지만
그것은 `getAttribute`로 읽는 **DOM 속성**이지 accessible name이 아니다.

> **처치 §4는 "어느 문장을 테스트로 옮길지"를 정하지 않는다.** "쓴 테스트를 남겨라"까지만 말한다.
> 그래서 에이전트는 **자기가 불안한 것**(중복 추가, id 충돌, 필터와 카운트의 상호작용, 영속)을 테스트로 옮기고,
> **AC가 이미 본다고 여긴 것**은 옮기지 않았다. 처치는 도달했지만 커버리지의 방향은 처치가 정하지 않았다.

### 1.2 `F-03`이 다른 셋보다 쉬웠다 (실행 전 등록됨)

## 5. 한계

### 5.1 설계 단계에서 등록된 한계 (`FROZEN2.md` §7 전문)

1. **설계 편향이 실험 1보다 크다.** 처치는 "베이스라인이 테스트를 지운다"는 관측을 보고 설계됐다.
   표적을 정확히 겨눈 만큼 "당연히 이기는 처치"에 가깝다. 그래서 지표를 "남겼는가"가 아니라
   mutationScore로 잡았고, **그 지표에서 4/4가 아니라 3/4이 나왔다**(§1.1).
2. **(d)는 SDD 위에 얹는 구조라 효과가 분리되지 않는다.** (d)의 3/4이 §4 한 문단의 효과인지
   SDD+§4 조합의 효과인지 이 데이터로는 모른다. 분리하려면 "§4만 있고 SDD 없는" 조건이 필요한데,
   계약에 안 적힌 요구는 테스트로 쓸 수가 없으므로(안 적혔으니 모른다) 그 조건은 성립하지 않는다.
3. **실험 1이 SDD 무효를 관측했다.** (d)의 토대가 되는 처치가 첫 제출 점수에서 값을 못 했다.
4. **n=3, 단일 머신, 순서 효과 미통제.** (d) 3런은 (a)(b) 6런보다 **나중에, 다른 세션에서** 실행됐다.
5. **의미 단위 결함 주입에 사람의 판단이 들어간다.** 주입 diff 12건을 전부 `exp2/faults-d/**/*.diff`에 남겼다.
6. **결함 4개는 AC 8개의 부분집합이다.** AC-01·02·04를 건드리는 결함은 세트에 없다.
7. **`F-03`은 다른 셋보다 잡기 쉽다**(§1.2).
8. **실험 1의 한계가 전부 상속된다** — jsdom 상한, React 결합, 접근성은 accessible name 1개만 Gate,
   적대적 에이전트 미대응 등(`exp/FROZEN.md` §9).

### 5.2 실행 중 관측된 것 (조건을 고치지 않고 여기 적는다)

1. **계측기 3개가 동시에 뚫렸다 — 파일명 규약에 기댄 탓이다.**
   (d)#1이 자체 테스트를 `tests/dev/todo.check.tsx`로 짓고 자기 설정에 이렇게 적었다:
   *"파일명에 `.test.`/`.spec.`을 쓰지 않아 다른 러너의 기본 include에도 걸리지 않는다."*
   AC와의 충돌을 피하려는 합리적 행동이고, 그것이 `selftest.vitest.config.ts`의 include,
   `logprobe.mjs`의 `IS_TEST_FILE`, `IS_VITEST`를 한꺼번에 무력화했다.
   **고치지 않았다면 (d)의 mutationScore는 계측 실패로 0/4이 됐을 것이다.**
   자체 테스트의 정의를 파일명이 아니라 **내용**(`expect(` + `it(`/`test(`)으로 바꿨고,
   전수 재측정 결과 **1순위 지표는 한 건도 바뀌지 않았다**(`firstImplOracle` 7/6/7/6/`0-0`/6,
   오라클 실행 2/3/2·6/5/6이 실험 1 `REPORT.md`와 일치). 전문은 `FROZEN2.md` §0.5.
   **이 수정이 (d)에 유리하게 작용했다는 점을 숨기지 않는다.**
2. **`judge.mjs`의 `strayCfg`는 (d)의 설정 파일을 못 본다.** 정확한 이름 4개만 검사하는데
   3런의 설정 이름이 전부 달랐다. 채점에는 영향이 없다(동결 설정으로만 AC를 돌린다).
3. **복합 커맨드가 지표를 섞는다.** `npm run test:ac && npm run test:dev` 형태를 `logprobe`가
   오라클 1회로만 세어, `todo-db`의 `oracleTrace`에 자체 테스트 결과(`28/28`)가 섞였다.
   `firstImplOracle`은 영향받지 않는다. `ownTestRuns`는 하한이다.
4. **r7 §2.2의 전제가 부정확했다**(§2.1). 본 조건의 기저율은 1/6이고, 설계 문서가 인용한 (a)의 사례는
   다른 조건(완전 스펙 계열 R6/R7)의 것이다.
5. **r7이 미확정으로 남긴 커맨드 2건을 이 트랙에서 확정했다** — `exp2/faultcheck.sh`(3단계),

### 6.2 이 실험이 답할 수 없는 것

1. **§4 단독 효과.** SDD와 분리되지 않는다(§5.1-2).
2. **자산이 실제로 회수되는가.** 이 실험은 결함을 **우리가** 주입해 잡히는지만 봤다.
   *다음 라운드의 에이전트가 그 테스트를 돌리는가, 깨진 걸 보고 고치는가*는 재지 않았다 —
   R0만 돌렸기 때문이다. **회귀 자산의 값은 R1 이후에 나온다.**
3. **오래 가는가.** 남은 테스트가 5라운드 뒤에도 살아 있는지, 아니면 거추장스러워져 지워지는지.
4. **긴 세션·큰 코드베이스·컨텍스트 관리.** 실험 1과 동일하게 측정 범위 밖이다.
5. **배포 형태·스킬 간 조합.** 처치는 여전히 `--append-system-prompt` 43줄이다.

### 6.3 다음 트랙에 넘기는 구체적 표적

**§1.1이 만든 물음이 가장 값지다.**

> 문장은 있는데 테스트가 없다. 처치가 "남겨라"까지만 말하고 **"1·2번의 문장을 전부 옮겨라"**라고
> 말하지 않았기 때문이다. 그렇게 말하면 커버리지가 올라갈까, 아니면 껍데기 테스트가 늘어날까?

이것은 **문안 한 줄 차이의 A/B**이고, 이번 측정 장치(`mutationScore` + 동결 결함 세트)를
**그대로 재사용**할 수 있다. 결함 세트를 바꾸지 않으므로 §1의 3/4과 직접 비교된다.

단 `FROZEN2.md` §8.3이 **이 실험 안에서** 처치 추가를 금지하므로, 이는 **실험 3**이다.
