# 동결 문서 — 실험 3 (자산 회수 트랙)

**작성일**: 2026-08-02 · **동결 시각**: **2026-08-02, `exp3/b2t` R1 실행 직전** · **환경**: Windows 11, node v24.14.0
**선행**: `docs/REPORT2.md` §6.2-2 (이 실험이 메우는 공백) · `docs/REPORT.md` · `exp2/FROZEN2.md`
**성격**: 설계·동결·종료 조건을 한 문서에 담는다. 새 처치가 없고 커맨드가 전부 확정돼 있어 분리할 이유가 없다.

> **SSOT**: 실험 3에 관해서는 이 문서가 이긴다.
> `exp/`·`exp2/` 전체는 동결 취급이며 이 트랙에서 **한 글자도 고치지 않는다** — 자산은 `exp3/`로 복사만 했다.

## 1. 왜 이 실험인가 — 실험 2가 남긴 논리적 공백

실험 2는 **"자산을 만든다"**를 증명했다 (`mutationScore` 0 → 3/4, 처치 도달 3/3, 삭제 0건).
증명하지 **않은** 것은 **"자산이 값을 한다"**이다.

```
실험 2가 잰 것 :  우리가 결함을 주입하고  우리가 남은 테스트를 돌렸다  → 3/4이 잡혔다
실제로 궁금한 것:  에이전트가 다음 라운드에  그 테스트를 돌리는가        → 데이터 0
```

**돌리지 않으면 남아 있어도 죽은 자산이다.** 그리고 실험 1·2 모두 R0만 돌려 이 장면을 한 번도 못 봤다
(`REPORT2.md` §6.2-2가 "회귀 자산의 값은 R1 이후에 나온다"고 등록했다).

### 1.1 왜 `--resume`이 아니라 새 세션인가 — 이 트랙의 가장 중요한 설계 결정

실험 1의 R4~R7은 `--resume` 같은 세션이었다(`exp/FROZEN.md` §7.2). 그대로 하면 에이전트가
**방금 자기가 쓴 테스트를 기억한 채** 변경 요구를 받는다. 그건 "자산이 회수되는가"가 아니라
"기억하는가"이고, 결과가 자명해진다.

> **새 세션으로 돌린다.** 사용자가 겪은 원래 문제("나중에 다시 필요했고 다시 검증했다")도,
> 회귀 자산의 본래 목적도 **컨텍스트가 사라진 뒤**다. 새 세션이면 (b)와 (d)의 차이가
> 대화 내용이 아니라 **디스크에 남은 파일에만** 있게 된다 — 정확히 재려는 것이다.

대가: 실험 1의 R4~R7과 직접 비교되지 않는다. 다만 그쪽은 **완전 스펙 계열**이라 애초에 조건이 다르다.

## 2. 1순위 지표 — `assetRun`

> **`assetRun` = R1 세션에서, R1 시작 시점에 이미 존재하던 자체 테스트를 1회 이상 실행했는가 (런당 0/1).**

**자발적 실행을 잰다.** R1 프롬프트는 자체 테스트를 돌리라고 **말하지 않는다.** 완료 조건은
`npm run test:ac`와 `npm run build` 둘뿐이므로, 남은 테스트를 무시해도 완료할 수 있다.
시스템 프롬프트의 §4도 "만들어 돌렸다면 지우지 마라"까지만 말하고 "기존 것을 돌려라"고 하지 않는다.

**판정**: `logprobe.mjs`의 `ownTestRuns > 0` + 세션 로그의 커맨드를 눈으로 대조해
그 실행이 **기존 파일**을 대상으로 하는지 확인한다(R1에서 새로 만든 테스트를 돌린 것과 구분).

**(b)는 정의상 0/3이다** — 남은 테스트가 없다. 그래도 돌리는 이유는 §3.1.

### 2.1 2순위 (병기, 결론에 쓰지 않는다)

| 지표 | 무엇 |
|---|---|
| `assetSurvival` | R1 끝에 원래 테스트 파일이 남아 있는가 · 케이스 수가 늘었나 줄었나 |
| `assetGrowth` | **새 요구(`todo-edit`)를 검사하는 케이스를 추가했는가** — 자산이 자라는가 |

| 변경 요구 이행 | `grep -rl todo-edit src/` (Gate 아님, 유무 기록) |

## 3. 조건과 프로토콜

### 3.1 조건 — 6런

| 조건 | 산출물 (R0 상태) | 남은 자산 | 시스템 프롬프트 |
|---|---|---|---|
| (b) | `exp/todo-b2t{,b,c}` 사본 → `exp3/b2t{,b,c}` | **없음** | `fw-b/…/SKILL.md` (38줄) |
| (d) | `exp2/todo-d{,b,c}` 사본 → `exp3/{d,db,dc}` | **있음** | `fw-d/…/SKILL.md` (43줄) |

**(b)를 돌리는 이유**: 1순위에는 기여하지 않지만(자명하게 0), **회귀와 비용은 대조군 없이 해석 불가**다.
(d)가 회귀 0이어도 (b)도 0이면 무정보다.

### 3.2 프롬프트 — 양쪽 바이트 동일

```
exp3/runs/sent-r1.txt = prompt-r1.md + CONTRACT-thin.md + prompt-change-r6.md
```

변경 요구는 `prompt-change-r6.md` **1건**(인라인 제목 편집, `todo-edit`). 4건 중 이것을 고른 이유는
**DOM 구조를 바꾸므로 기존 자체 테스트를 깨뜨릴 가능성이 가장 높기** 때문이다 —
`todo-title`이 입력창으로 바뀌는 경로가 생긴다.

`prompt-r1.md`는 R0의 `prompt-d.md`에서 **2줄만 다르다**:

```
- 아래 **구현 계약**을 만족하는 앱을 이 저장소에 구현하라.
+ 이 저장소에는 **이미 구현된 앱**이 있다. 아래 **변경 요구**를 반영하라.
+ - 아래 «변경 요구»는 계약의 «범위 밖» 목록보다 우선한다. 그 외 계약은 그대로다.
```

> **두 번째 줄이 필요한 이유**: `CONTRACT-thin.md`의 «범위 밖»에 "인라인 제목 편집(더블클릭 수정)"이
> 명시돼 있어 변경 요구와 **직접 모순**이다. 실험 1은 `--resume`이라 새 지시가 컨텍스트를 덮어썼지만,
> 새 세션에서는 둘이 동시에 주어진다. **계약을 고치지 않고**(동결) 우선순위만 명시해 해소했다.
> 양쪽 동일하므로 비교는 공정하다.

오염 검사: `prompt-r1.md`에 축 이름(`localStorage`·`aria`·`영속`·`접근성`·`checkbox`…) **0줄**.

### 3.3 실행 커맨드

```bash
# cwd = exp3/<dir>.  Git Bash.  <FW> = ../fw-b 또는 ../fw-d
cat ../runs/sent-r1.txt | claude -p \
  --safe-mode --model opus --effort xhigh \
  --permission-mode acceptEdits --allowedTools Bash PowerShell \
  --append-system-prompt "$(cat <FW>/skills/spec/SKILL.md)" \
  --session-id <UUID> \
  --output-format json > ../runs/<label>-r1.json 2> ../runs/<label>-r1.stderr.txt
```

| 2 | `exp3/b2tb` | `fw-b` | `e1000000-0000-4000-8000-000000000001` | `b2tb-r1.json` |

**순차 단독 실행**(벽시계를 재므로). 채점: `node exp3/judge.mjs exp3/<dir> <label>-r1`.

**라운드 유효 판정**: `acRunOk: true` AND `permission_denials` 비어 있음. 그 외 사유로 재실행하지 않는다.

## 5. 미리 밝혀두는 예상 (사후해석 방지)

**실행 전에 적는다.**

1. **(b)는 `assetRun` 0/3.** 정의상 그렇다.
2. **(d)는 2/3을 예상한다.** 발견 가능성이 갈리기 때문이다 —

   | 앱 | `package.json` 스크립트 | 자산 위치 | 발견 난이도 |
   |---|---|---|---|
   | `d` | **`test:dev` 있음** | `tests/dev/todo.check.tsx` | 낮음 |
   | `db` | **`test:dev` 있음** | `tests/dev/todo.spec.tsx` | 낮음 |
   | `dc` | **없음** | `src/todo/todo.invariant.test.tsx` + `vitest.impl.config.ts` | **높음** |

   셋 다 `SPEC.md`에 자산을 언급하지만, `SPEC.md`를 읽을지는 에이전트 재량이다.
   **처치 §4는 "남겨라"만 말하고 "발견 가능하게 하라"는 말하지 않는다** — `dc`가 그 구멍이다.
3. **회귀는 양쪽 다 안 날 가능성이 높다.** 실험 1의 (a)는 변경 4건 연속 회귀 0이었다(`REPORT.md` §3.1).
   그러면 "테스트가 회귀를 잡았다"는 또 무정보가 된다. **그 경우에도 1·2번은 관측된다.**
4. **(d)가 (b)보다 비쌀 것이다.** 테스트를 읽고 돌리고 갱신하는 만큼 턴이 는다.

**2번이 빗나가 3/3 또는 0/3이 나와도 결함·조건·프롬프트를 바꾸지 않는다.**

## 6. 한계

1. **n=3, 단일 머신, 순서 효과 미통제.** 실험 1·2와 동일.
2. **변경 요구 1건뿐이다.** `todo-edit`이 자체 테스트를 안 깨뜨리면 "깨졌을 때의 대응"은 관측되지 않는다.
3. **`assetRun`은 "돌렸는가"이지 "값을 했는가"가 아니다.** 돌렸는데 아무것도 안 잡혔다면
   그것도 회수는 아니다. 이 구분은 2순위 지표로만 본다.
4. **(d)의 R0 산출물이 서로 다르다.** 발견 난이도가 앱마다 달라(§5-2) n=3 안에서도 조건이 균질하지 않다.
   **이것은 결함이 아니라 관측 대상이다** — 처치가 발견 가능성을 규정하지 않은 결과 그 자체다.
5. **실험 1·2의 한계가 전부 상속된다** (jsdom 상한, React 결합, 설계 편향 등).
6. **`--safe-mode`라 실사용 환경이 아니다.** 처치는 여전히 `--append-system-prompt`다.

## 7. 종료 조건 (등록 시점부터 유효 — 결과를 본 뒤에는 고칠 수 없다)

### 7.1 재실행 사유 화이트리스트

| 사유 | 처리 |
|---|---|
| `acRunOk: false` | 그 라운드만 재실행 |
| `permission_denials` ≠ 0 | 그 라운드만 재실행 |
| 계측기 버그 | **재실행 없음.** 전수 재측정 + 사유 기록 |

**그 외 전부 금지.** 특히 `assetRun`이 예상과 다름, 회귀가 안 남, n이 작아 보임은 재실행 사유가 아니다.

### 7.2 사전 등록 문장

| 결과 | 리포트에 쓸 문장 |
|---|---|
| (d) `assetRun` = 3/3 | "남은 자산은 새 세션에서도 **자발적으로 회수된다.** 3/3이 기존 테스트를 실행했다. n=3, 유의성 주장 없음." |
| (d) `assetRun` = 1~2/3 | "회수는 **조건부다.** N/3만 실행했고, 갈린 축은 §5-2의 발견 가능성과 대조해 보고한다. **처치가 '남겨라'까지만 말하고 '발견 가능하게 하라'는 말하지 않는다는 한계를 가리킨다.**" |
| (d) `assetRun` = 0/3 | "**남은 자산은 회수되지 않았다.** 실험 2의 `mutationScore` 3/4은 *우리가* 돌려서 나온 값이고, 에이전트는 새 세션에서 그것을 쓰지 않았다. 회귀 자산 가설에 대한 음성 데이터다." |

**어느 경우에도 실험은 성공이다.** 산출물은 "회수된다"가 아니라 **관측 리포트**다.
