## 1. 관측은 사람이 하지 않는다

**막힌 걸 사람이 받아적기 시작하면 이 트랙은 «재기»로 되돌아간다.** 20라운드에 63줄 나온 그 방식이다.

`hooks/spec-gate.mjs`가 차단할 때 대상 프로젝트 루트에 `.specgate-log.jsonl` 한 줄을 남긴다(구현됨).
사람이 남기는 건 **분류 한 글자**뿐이고, 그것도 나중에 몰아서 한다.

```bash
# jp-trip에서 — 무엇이 몇 번 막혔나
cat .specgate-log.jsonl | node -e "…"   # 또는 그냥 열어본다. 줄 수가 곧 마찰 횟수다
```

- 여행앱 리포의 `.gitignore`에 `.specgate-log.jsonl`을 넣는다. 여행앱의 산출물이 아니다.
- 분석할 때 proj3로 복사해 온다. 로그 원문이 실측 원문이다.
- **로그 실패가 게이트를 막지 않는다** — append가 터져도 차단은 그대로 간다(try/catch).

## 2. 사건을 넷으로 나눈다

로그 한 줄 = 사건 하나. 나중에 몰아서 분류한다. **분류가 곧 조치를 결정한다.**

| 분류 | 뜻 | 조치 |
|---|---|---|
| **정당** | 막아야 할 걸 막았다 | 없음. 게이트가 일한 것이다 |
| **오차단** | SPEC이 필요 없는 일인데 막혔다 | `SRC`에서 빼거나 `PRE` 축소 → 선택 대기 #4 번복 |
| **미차단** | 막았어야 하는데 통과했다 | `SRC` 확장 · 도구 확장 → 선택 대기 #2·#4 번복 |
| **마찰** | 막은 건 맞는데 비용이 과하다 | 시점(pre/stop)·메시지·검사 항목 조정 |

로그에 안 잡히는 두 가지는 **손으로 한 줄 남긴다** (이것만은 자동화가 안 된다):

- **미차단** — 로그에 안 남는다(막지 않았으니까). 지나고 나서 «어? 이거 그냥 됐네»를 적는다.
- **우회 유혹** — 빈 파일+Edit, Bash로 파일 생성, SPEC에 문장 ID 안 붙이기를 **실제로 하고 싶어졌는가.**
  했으면 했다고 적는다. 우회 자체는 죄가 아니고, **우회하고 싶어진 순간이 데이터다.**

### 예언에 없던 것 (2026-08-17 실측)

관문 A-3에서 예언 5개 중 아무것도 아닌 **설치 역학**이 먼저 걸렸다. 둘 다 README에 반영했다.

| # | 실측 | 증거 |
|---|---|---|
| F1 | **설치한 그 세션에는 훅이 안 붙는다.** 재시작해야 걸린다 | 설치 직후 `src/a.ts` 생성됨 → 재시작 후 같은 요청 정상 차단 |
| F2 | **캐시가 원본 변경을 따라오지 않는다.** 재설치가 필요하다 | 원본에 로그 코드를 넣었는데 캐시본 mtime이 전날 그대로 |
| F3 | **캐시는 git HEAD가 아니라 작업 트리를 복사한다** | 재설치했더니 커밋 안 한 README 수정까지 캐시본에 들어왔다 |

F3은 개발 루프에 유리하다 — **커밋하지 않고 고친 뒤 재설치만 해도 실물로 검증된다.**
대신 «캐시본이 어느 시점 코드인지»가 커밋 이력으로 추적되지 않으므로, §4의 grep 확인이 유일한 근거다.

**F2는 관측 자체를 무력화한다** — 고친 게이트를 재설치하지 않으면 옛 게이트를 계속 재게 된다.
게이트를 고칠 때마다 §4의 grep 확인을 건너뛰지 않는 이유다.

한 가지 더: 진단하려고 훅을 손으로 돌리면 **그 로그가 대상 프로젝트에 섞인다**(첫 로그 줄이 그렇게 생겼다).
손으로 돌릴 때는 `cwd`를 스크래치로 준다.

P1·P2가 맞으면 **선택 대기 #4의 번복 조건이 틀린 것**이다 — 거기엔 «오차단 발생 시»라고 적혀 있는데,
실제로 나올 건 오차단이 아니라 **미차단**이다. 그 문장부터 고친다.

## 4. 고치는 절차

게이트 수정은 **proj3에서** 한다. jp-trip에는 플러그인 소스를 두지 않는다.

```bash
# 1. proj3에서 고친다 (framework/hooks/spec-gate.mjs · spec-verify.mjs)
# 2. 자기검사 둘 다 통과해야 한다 — 하나라도 깨지면 커밋하지 않는다
node framework/spec-verify.mjs --selftest          # 픽스처 6장
node framework/hooks/spec-gate.mjs --selftest      # 게이트 분기 10건
# 3. 재설치한다 — 캐시는 원본을 따라오지 않는다(2026-08-17 실측, 확정).
#    /plugin uninstall specgate@proj3 && /plugin install specgate@proj3 → 세션 재시작
#    고친 줄이 캐시본에 있는지 grep으로 확인한다. 이걸 건너뛰면 옛 게이트를 계속 재는 것이다
# 4. 고친 근거를 커밋 메시지 한 줄로. 별도 판정 문서를 쓰지 않는다
```

**검사를 새로 추가할 때 지키는 것** (프레임워크 개발 규칙 5): 차단성 게이트에 LLM을 넣지 않는다.
«같은 입력에 항상 같은 답이 나오는가»가 기준이고, 아니면 Advisory(경고)로 둔다.

## 5. 하지 말 것

- **게이트를 끄고 앱만 만들기.** 그러면 실측이 0이 된다. 끄고 싶어지면 **끄기 전에 로그에 한 줄 남긴다** — 그게 P2의 증거다.
- **막힐 때마다 즉시 고치기.** 한 건으로 게이트를 바꾸면 여행앱 하나에 과적합된다. 5~6건 모아서 본다.
- **예언에 없던 개선을 미리 하기.** 선택 대기 #3(플러그인 루트 분리)·#4(확장자 설정화)는 번복 조건이 실제로 뜨기 전까진 추측성 코드다.
- **문서 라운드.** 이 가이드가 마지막 문서다. 다음 산출물은 코드거나 로그다.

## 6. 멈추고 정리하는 조건

셋 중 하나가 오면 앱을 멈추고 게이트 수정 라운드로 간다.

1. 분류된 사건이 **5~6건** 쌓였을 때
2. **같은 마찰이 3번** 반복될 때 (한 번은 우연, 세 번은 설계 문제)
3. **게이트를 끄고 싶어진 순간** — 횟수와 무관하게 즉시. 그게 이 도구가 죽는 방식이다

정리 산출물은 판정 문서가 아니라 **고쳐진 `spec-gate.mjs` + selftest 통과 로그**다.
